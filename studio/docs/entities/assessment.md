An Assessment is a Course-owned ordered learning activity whose purpose is to elicit evidence of previously taught Skills. It is neither an instructional Lesson nor a narrative Episode. Course, Module and Chapter may each directly contain Assessments, Lessons and Episodes; Course may also contain Modules and Chapters, Module may contain Chapters. The entire Course may end with an Assessment without an artificial Module or Chapter. Instructional Lessons remain independently useful; replace the assessment-only Lesson exception for new authoring without silently deleting or migrating existing content.

## Ownership and contract

Use independent `defineAssessment`, `assessment_Config_Schema`, `assessment_Props_Schema` and inferred types, with immutable UUID, camelCase slug, `type: 'assessment'`, localized title, languages and ordered Sections. Reuse actual Section/ContentBlock configurators, Quiz selection, grading and global Question resolution. A completed Assessment has **exactly one mandatory, enabled Quiz** as its dedicated `quiz` Configurator property; it cannot be removed, disabled or replaced by an override. Optional `before` and `after` collections contain only ordered Content Sections, never another Quiz. The completed runtime Props flatten the phase order into Sections while retaining the single-Quiz invariant. An independent `defineAssessmentDraft` produces explicitly marked `draft: true` Props with an enabled Content Section and an actual “Not implemented” Text ContentBlock, but no Quiz or fabricated Questions. Drafts may render in Course preview, never pass completed publication. No own Question Bank or Flashcard Bank, no Episode scenario/events, no Lesson wrapper, no duplicated Questions or new scoring engine. Flashcards remain learning/revision resources outside Assessment. The Assessment owns its selection and supporting content, not the source Questions. Use real imported Question Configurator IDs from reviewed Lesson banks, checking existence, supported locale and asset integrity. Do not invent IDs or silently select the entire bank. Independently validate literal draft selections against actual imported Question Configurators in trusted code.

## Course planning and dependencies

At **Course Stage 2**, the Methodologist decides whether and where Course-owned Assessments are necessary by inserting zero or more **ordered Assessment slots** directly into the appropriate Course, Module or Chapter `config.content.items` and `content.order`. **The presence/absence of these slots is the only Assessment-intent signal**; there is no separate Course/Module/Chapter Assessment-required flag or equivalent mirrored property. Course Stage 1 describes overall educational purpose and evidence, but does not declare a parallel Assessment necessity boolean. Record each Assessment slot's purpose and target evidence within its existing planning context, without duplicating Skills, owner-level fields or other editorial metadata. Stage 3 resolves dependencies against actual Lesson placements. Each Assessment has explicit production-only required Lesson dependencies, including additional Lessons when not covered by the owning scope. Use stable placement paths for not-yet-allocated Lessons and real UUID references for existing Lessons; resolve allocated identities during Course materialization. Reject unresolved references, ambiguous repeated placements and forward/cyclic dependencies within the Course. Distinguish educational/authoring readiness from runtime learner progression; do not invent a runtime dependsOn field. Before beginning Assessment production, verify required Lessons and their relevant reviewed Question Banks are ready and integrated into the Assessment branch ancestry; missing dependencies block Assessment production, not Course planning or draft preview.

## Canonical source layout

Assessment source is owned by its Course. Every Course/Module/Chapter child is stored directly beneath its owning source directory: **no structural `content/` directories** are generated. The directory uses the camelCase placement slug (not its UUID). For example, relative to the Course UUID root:

- Course-level: `finalAssessment/index.ts`.
- Module-level: `light/moduleAssessment/index.ts`.
- Chapter-level: `light/reflection/chapterAssessment/index.ts`.

The materialized Assessment exports its Configurator from `index.ts`; after independent verification a Coding Agent updates the immediate parent to import it from `./<assessmentSlug>`. Until then the parent must still import `./<assessmentSlug>/stub`. The Configurator's **TypeScript `content.items/order` fields are unchanged**; only the filesystem layout and its relative imports are flattened. Use the canonical existing Section and ContentBlock materializer directory layout, including slug-named Section folders under `sections/` and slug-named ContentBlock folders within each owning Section, with their normal `index.ts` and resource/specification files where applicable. Do not collapse independent owner levels or move a nested Assessment to the Course root. The separately authorized editorial `draft.ts` lives in that same future Assessment directory; initial Course materialization emits a blocked `stub.ts` exporting `defineAssessmentStub` and a separate typed `AssessmentWorkflowSeed` at the reserved `draft.ts` path. Full materialization atomically creates the owned modular files and consumes only the draft; parent import, stub, identity and order remain unchanged. Later agent-owned integration updates only that one import and deletes only the owned stub after validating dependencies, Scenes/resources, locales and runtime/TypeScript behavior. Test all three levels and exact paths, including nested blocks and collision/no-clobber behavior.
