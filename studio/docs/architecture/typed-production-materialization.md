# Typed production materialization

The canonical editorial input for Course, Episode, Lesson, Question Bank and Flashcard Bank is a single Stage-specific TypeScript object. Editorial inputs and materialized Configurators have distinct responsibilities; the trusted source-materialization workflows do not publish runtime Props.

## Entity-owned source flows

- **Course:** Stages 1–3 progressively author `draft.ts` using `CourseWorkflowStage1/2/3`; independent Stage 4 finalizes the existing exported object with `satisfies CourseWorkflowMaterializerInput` (alias to Stage 3), then reinspects and records the final source SHA. Stage 5 consumes those exact reviewed bytes. Trusted Stage 5 emits Course/Module/Chapter sources and minimal new Lesson and Episode Stage 1 `draft.ts` handoffs. Stages 6–7 own Course translation/review; mandatory human Stage 8 QA verifies the actual integrated Course at a pinned revision with complete required dependencies. Independent Episode QA remains separate. See the Course Skill for acceptance and evidence.
- **Episode:** The Course allocates the exact immutable placement, UUID, reviewed intent and locale plan. The Episode-owned Stage 1–2 `draft.ts` is reviewed at Stages 3–4, consumed atomically at trusted Stage 5, then completed at Stages 6–8; human Media Generation and QA at Stages 9–10 are independent release gates. See [Episode Flow](../../skills/episode-workflow/create-episode-flow.skill.md).
- **Lesson:** Stage 1/2 editorial `draft.ts` (`LessonWorkflowMaterializerInput` at final handoff) is reviewed at Stages 3–5. Authorized Stage 6.1 consumes the valid pinned draft atomically without parsing editorial or Course provenance evidence and creates `index.ts` and modular `defineLesson`, Sections and Blocks. Scene implementations/assets, Questions, Flashcards, translations and separate publications are not invented.
- **Questions/Flashcards:** Independently authored Stage 1–3 TypeScript banks, source-SHA-pinned independent Stage 4 reviews and trusted Stage 5 materialization. The draft deletion and creation of final `questions/index.ts` or `flashcards/index.ts` transition are no-clobber and atomic. Real all-bank resources, selected Sections, locales and media are independently verified.

Engine's concrete source materializers live under `shared/engine/generators/materializers/`; trusted commands live under `scripts/ci/{courseMaterialization,episodeMaterialization,lessonMaterialization,bankMaterialization}/`. Candidate PR TypeScript is statically inspected as inert data. Only default-branch trusted code executes, with read-only analyze and privileged manifest-checked publish separated. Git source/HEAD SHA, branch lease, path/symlink restrictions and exact file bytes are required. Course, Episode and Bank workflows additionally require accepted [review evidence](../../rules/independent-review.md); Lesson materialization does not. No Configurator `build.files()` is introduced.

## Publication and rollout boundaries

The separate `generateLessonProps`, `generateCourseProps` and `generateAssessmentResources` scripts consume **completed** typed Configurators. All emitted TypeScript must be syntactically and semantically valid against current contracts. Use valid typed placeholders and explicit `TODO (BLOCKER)` markers for legitimately unfinished production resources where applicable; editorial handoffs remain typed drafts, not runtime Configurators. A source scaffold or reviewed Stage 3 plan is not publishable. `TODO (BLOCKER):`, `TODO(asset)`, Nil UUIDs, missing real selections, physical assets, implemented Scenes or languages fail publication as appropriate. A known Course/Question/Flashcard bank does not imply the associated Section is complete.

Before invoking a typed command, verify the corresponding trusted workflow exists on the default branch. Verify an authorized Actions run on safe reviewed inputs, its pinned source SHAs (and review SHAs for workflows that require them) and resulting commit before declaring the pipeline operational.

## Historical source preservation

The 109 `content/math/data/lessons/**/lesson.yaml` files are **historical user-authored source** and were preserved. They are not instructions to regenerate a Lesson using a deleted converter. Migrating any such Lesson requires explicit non-destructive provenance and semantic review of its actual authored material; this infrastructure cleanup does not silently convert or delete editorial source. Prior prototypes and removed scripts remain recoverable from Git history. Do not restore their generated editor schemas or treat archived YAML as a second source of truth.

Review the current [Course Flow](../../skills/course-workflow/create-course-flow.skill.md), [Lesson Flow](../../skills/lesson-workflow/create-lesson-flow.skill.md), [Questions Flow](../../skills/lesson-workflow/create-questions-flow.skill.md) and [Flashcards Flow](../../skills/lesson-workflow/create-flashcards-flow.skill.md) for stage-specific approval and authoring rules.

All editorial roots use exactly one `draft.ts` and completed roots use `index.ts` (supported standalone Lesson `.data.ts` remains valid). Publishers never load editorial sources; draft-mode validation may omit unfinished roots, whereas strict release rejects unfinished or ambiguous roots. Materialization consumes the approved draft in the same Git commit that creates the final source. Provenance is the immutable reviewed parent commit and blob, not an extra live archive.
