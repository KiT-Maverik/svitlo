# Lesson resource readiness is not Config validity

**Status:** observed validation boundaries and proposed, **not implemented**, publication-readiness contract. Investigation for [Issue #591](https://github.com/KiT-Maverik/svitlo/issues/591), against the current Engine. Do not infer that a green Config validator, scoped Props Build, draft scaffolder or Props serializer certifies a completed Lesson.

The Lesson review artifacts generator has its **own** `reviewReady` output marker for successfully rendered localized Markdown (rejecting missing markers/failed commands). That marker means the **artifact can be reviewed**, not that anyone reviewed or approved the Lesson. See `scripts/generateLessonReviewArtifacts/generate-lesson-review-artifacts.mjs`.

The current dedicated `defineLesson.spec.ts` regression illustrates both cases: an `en`-only draft with intended `['en','uk']` passes runtime Config shape and an `en`-scoped Props Build but fails a two-language Build; a fully localized Lesson builds Props for both languages without conveying review/production metadata. This is not a claim that the source-only draft is TypeScript-complete.

## False-positive completion claims to avoid

1. **Config valid != all locales publishable.** The Config schema explicitly accepts a nonempty sparse locale map. This is intentional so source-only editorial stages can exist. Do not tighten Config validation to demand translations that have not been authored.
2. **Scoped Props valid != declared Lesson complete.** `build.props({ languages: ['en'] })` is a legitimate operation on a Lesson intending `['en','uk']`; it is not a whole-Lesson publication-readiness test. The current Props CLI requests all declared locales, but still cannot assess reviews or production resources.
3. **All-language Props valid != safe to deliver.** A completely shaped, serializable Lesson may lack reviewed scientific content, an accepted Props revision, external media, registered Scenes or accessible runtime behavior. Local referenced textbook media are now checked by the separate Props publisher (Production rejects missing and unresolved files), but that does not establish content quality, Scene readiness or review acceptance. The typed `LessonReview` file remains outside Config/Props; no gate binds its approvals to publication.
4. **Files or PRs present != reviewed.** Source SHA, assembled Props digest, actual accepted PRs, per-locale approvals and resource availability must be verified; never fabricate a `completed: true` property or infer acceptance from a generated `review.ts`.

## Smallest safe direction (recommendation; requires API decision)

Keep `defineLesson`, `config.validate` and `build.props` as **technical validators**. Keep `production` authoring-only and out of runtime Props/Configurator identity. Use the existing **Lesson Draft PR** as the coordination source, while any proposed separate read-only, build-time _readiness assessment_ must have its own approved contract and verified blockers rather than a mutable boolean. Historical Lesson Production Issues remain evidence, not trackers for new work.

The proposed assessment should take a **specific Lesson UUID and revision/digest**, declared locales, verified build/packaging results and **externally verified** review/evidence references. It should return separate facts for:

- **Technical:** full declared-locale Props resolution, referenced Skill/Scene registrations, local media/role files, accessibility artifacts and packaging checks.
- **Editorial:** methodology/experience/assessment acceptance and locale-by-locale translation and human sign-off tied to the same reviewed source and assembled Props revision.
- **Production progress:** per-resource/per-locale pending, blocked or verified work, allowing a Lesson to remain an incomplete draft without pretending whole-Lesson completion.

A positive readiness outcome requires all mandatory facts **for the requested publication scope**. Missing evidence must be **unknown/not verified**, never implicitly approved. Changing source or Props revision invalidates only dependent evidence. The assessment belongs at the build/publishing boundary; no `completed` Configurator property or unconditional runtime flag is warranted. The trusted typed materializer's non-clobber/immutable reviewed-source policy remains intact; the retired YAML-only `SKIP` scaffolder is not a live compatibility route. Generated review registers now use typed numeric `0` evidence placeholders plus a blocking review TODO; Ready/merge CI rejects zero references even if that TODO is removed. This is not an external-review verification or publication approval gate.

## API and acceptance decisions still required before enforcement

1. **Authority and storage:** Does the current Lesson PR, verifiable source/asset manifests and typed review register provide sufficient evidence for release readiness, or is a separate read-only build-time assessment necessary? Do not introduce another mutable status ledger. Do **not** equate a user-entered status with verified evidence.
2. **Revision identity:** Specify digest of assembled Props, source blob SHA, asset manifest revision, review PR references and invalidation rules. The current `review.ts` type records references, not verified state.
3. **Eligibility:** Define which locales/resources/Scene implementations are mandatory for an individual publishable Lesson and how invariant strings/media, intentionally disabled content and optional Flashcards are treated. Decide whether partial-locale publication is a supported release product or only an internal preview.
4. **Enforcement point:** Should `generateLessonProps --write/--check` reject any unapproved Lesson, skip only unapproved Lessons while still checking stale output, or remain a technical stage behind an explicitly separate release command? Define CI failure mode and safe migration of already-published Lessons **before** changing the CLI.
5. **Required regression acceptance:** negative cases for missing locale, absent asset, unregistered Scene, missing/stale review, wrong revision and incomplete per-locale approval; positive cases for all required resources and matched reviews. Also prove trusted source materialization does not publish Props, no release runs on unfinished drafts, and create-only/no-clobber source transactions remain intact.

**Until these decisions are approved:** do not add an unverified status field, route draft scaffolding into publication, or represent technically valid Props as production-ready. Publication gating itself is **not implemented by this document or Issue #591's focused tests**.
