# Lesson production — Git-first Draft PR coordination

**Current design:** [Create Lesson Flow](../../skills/lesson-workflow/create-lesson-flow.skill.md) replaces the former mandatory Lesson Production Issue tracker for **new** Lesson authoring. One Draft Lesson PR per immutable UUID is the sole operational stage/review/status register; Git files are the authored source of truth. Historical fixed-scope Issues remain verifiable evidence to reconcile and cross-link, **not** erase. The distinct Translation Production Issue protocol remains unchanged.

Each Lesson resolves to `content/<book>/data/lessons/<last-hex>/<uuid>/` via the Engine UUID resolver. A Lesson remains standalone, reusable and Course-neutral. A Course-originated Lesson PR targets its verified Course parent integration branch and carries the literal `svitlo-course-lesson:v1` / `Course` / `Lesson` / `Parent PR` marker specified in #639; Course PR status synchronization manages only **Course inventory**, not Lesson editorial stages. Methodology presence alone does not establish Course provenance. Reuse existing Lesson PR/branch/UUID when resuming.

Ten parent Lesson stages: (1) Methodology, (2) Content Creation, (3) independent Content Review in a new chat, (4) Learning Experience Expert audit in the same chat, (5) Methodologist compliance audit in the same chat, (6) **source preparation** with separately checked materialization, accessibility source audit, offline source audit and source validation, (7) **Questions** coordinating a seven-stage child Question Bank workflow or documented own-bank N/A, (8) **Flashcards** coordinating a separate seven-stage child workflow or justified N/A, (9) Translation, and (10) independent Translation Review. Each child PR retains its own stages, approvals and localization, while the parent stage records verifiable review/branch integration. **Stage 6 does not implement Scenes, create media or integrate banks.** Maintain one separate resource blocker per unfinished Scene/physical asset, with owner, file/Block, specification and evidence; these prevent final QA/Ready, not Stage 6 completion. Final QA and Development Review are not an eleventh Lesson stage.

Existing eight-stage Lesson PR descriptions are migrated **in place**: preserve original SHA-reviewed Stage 1–6 status, add Stage 6.1–6.4 boxes with only verified checks, add new Stages 7 Questions/8 Flashcards with actual child/N/A evidence, and renumber old Translation/Review to 9/10 without carrying their checked values into bank stages. Preserve old child PR ancestry and Stage 3–5 review evidence.

New work progressively enriches exactly one temporary `lesson.yaml` with `config` and nested authoring-only `production` and source `production.documentLanguage`, retaining full planned `config.params.languages`. Standalone Lesson Builds use those declared languages; Course-originated effective requested languages must be validated as a subset and passed to the Lesson Build, then to Flashcard Build as the effective Lesson scope, without persisted Course coupling or fallback. Separate historic `methodology.md`/`content.yaml` inputs need non-destructive source/review provenance migration. Do not insert `draft`, `approved`, `stage` or `reviewStatus` into YAML, methodology prose/frontmatter, Engine Config or Props. Incomplete editorial YAML remains allowed through Stage 5; **one** complete structural preflight at Stage 6 uses the Engine-Zod-derived `lesson.scaffold.schema.json` + manual production schema. The existing `lessonBuilder` is draft-only/create-only and does **not** validate complete YAML.

Finalization must verify source file SHA/bytes, Builder not skipped, exact generated source/Markdown/Code and all YAML-owned production instructions faithfully represented in persistent sources before deleting the **unchanged** `lesson.yaml`. On failed/partial/skipped/conflicting/stale source, YAML remains. Never remove `questions.yaml`/`flashcards.yaml` or fabricate translations/assets to make Draft CI green; document specific expected errors and investigate unexpected ones.

**Trusted Stage 6 PR-command mechanism (once deployed on main):** `/lesson materialize` on the existing Draft Lesson PR invokes pinned, trusted Engine source validation and create-only TypeScript/Markdown/specification generation with source SHA/allowlisted commit evidence. It verifies completed Stages 1–5, the UUID bucket, original blob and Course-origin parent branch; bank-pending Quiz/Flashcards Sections may use `preflight-draft`/`handoff` and honest `TODO (BLOCKER)`, while complete input uses strict source-preserving finalization. It creates no banks, Scenes/media or translations; optional `/lesson finalize` still fails closed. A genuine Actions success supports **substep 6.1**, not the complete parent Stage 6. Check 6.2 accessibility and 6.3 offline source specifications and 6.4 source-fidelity/technical validation separately. Physical Scene/media files and bank selections remain blockers for external specialists, Lesson Stages 7/8, or final readiness rather than Stage 6. There is no permission to invent unavailable resources.

**Strictly forward-only Lesson editorial review:** Stage 3 is the sole new independent review chat; the qualified reviewer may document defects and fix bounded content as an explicitly attributed Screenwriter. Stage 4 continues in that chat as Learning Experience Expert, consumes the **completed** Stage 3 review and fixes experience defects without reopening Stage 3. **Stage 5 is the final comprehensive editorial/methodological review**: it consumes **both completed** Content and Experience reviews, checks the latest entire YAML against approved Stage 1 methodology, immediately fixes methodological/consistency defects in its own role, commits, verifies the whole corrected source and **directly hands off to Stage 6**. Each stage records its actual baseline/final source SHA, node findings, fixes and verdict in the Lesson PR. **Never uncheck or re-review Stage 3/4 as a consequence of Stage 5 repairs.** Earlier reviews remain valid evidence **only for their actual historical SHA**; Stage 5's final signed-off SHA is the integrated pedagogical acceptance for resource production. Unapproved curriculum, Skill or assessment-bank decisions block **Stage 5** with an owner decision, then resume Stage 5, without a backward referral. Stage 6 may follow in the same chat if authorized. Neither Stage 4 nor 5 is an extra independent approval. `review.ts` remains a **separate typed assembled-Props digest evidence register**, not an eight-stage status tracker; do not fabricate hashes/PR IDs. Owner explicitly controls Ready and merge.
