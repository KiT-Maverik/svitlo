# Independent Question and Flashcard banks

**Status:** Current architecture. The Lesson/bank separation and global UUID assessment publication are the current contract. This is a maintained contract, **not** an implementation migration checklist, an alternate production workflow or evidence that a specific bank has educational approval.

**Workflow owners:** [Create Lesson Flow](../../skills/lesson-workflow/create-lesson-flow.skill.md) owns the parent Lesson; [Create Questions Flow](../../skills/lesson-workflow/create-questions-flow.skill.md) and [Create Flashcards Flow](../../skills/lesson-workflow/create-flashcards-flow.skill.md) own separate independently reviewed, seven-stage child Draft PRs. Read the [Questions authoring standard](../../skills/lesson-workflow/create-lesson-questions.skill.md), [Flashcards authoring standard](../../skills/lesson-workflow/create-lesson-flashcards.skill.md) and current Engine implementation for details.

## Source and ownership

- A Lesson Config/Props owns ordered Sections, **not** embedded Questions or Flashcards. A Quiz or Flashcards Section selects explicit resources but does not serialize a bank in Lesson JSON, Course overrides, SSR payloads or screen ContentBlocks.
- **Typed Questions workflow:** the Lesson-owned `questions/draft.ts` starts as `QuestionBankWorkflowStage1` at an authorized Lesson Stage 7 handoff, becomes `QuestionBankWorkflowStage2` with a complete typed bank and `QuestionBankWorkflowStage3` with Quiz _intent_. The independent reviewer corrects that same file; the Question Bank Stage 5 source transition atomically consumes the draft and creates `questions/index.ts` and canonical Question Configurator exports **only after explicit source-SHA verification**. Existing outputs are never overwritten. The draft is never a publishable bank. There is no invented bank UUID, duplicate YAML or second selection list. Actual Quiz Section selection imports the approved Question Configurators and stores their `.id` values only in `params.selection.questionIds`.
- **Canonical Question Code layout:** `questions/index.ts` imports type-level indexes and exports the complete `questions` bank; every `questions/<questionType>/index.ts` re-exports all `questions/<questionType>/<questionSlug>.ts` Question definitions of that type. The type folder name is the exact Engine Question discriminant. Nested `<questionSlug>/` directories may hold Question-owned ContentBlocks, but not the Question entrypoint. Flat Question modules at bank root and `<type>/<slug>/index.ts` Question entrypoints are obsolete and not supported by the current review adapter. Existing authored banks using either obsolete layout require verified, non-destructive migration before reference generation; this architecture decision does not authorize rewriting independently reviewed content.
- **Typed Flashcard workflow:** the Lesson-owned `flashcards/draft.ts` is one progressively enriched `FlashcardBankWorkflowStage1 → Stage2 → Stage3` editorial source, initially a bank-only handoff (no cards) after the Question-first gate. Stage 2 stores real Card Config nodes, ordered front/back/hint Side ContentBlocks (including plain `CarouselSource` / `CheckpointSource` composite trees supported by the merged source renderers) and one canonical `config.relationships: {items,order}` edge map; Stage 3 records the independent optional in-Lesson Section decision. The independently reviewed Stage 3 type is also the sole Stage 5 materializer input. [Typed workflow contract](../../../shared/engine/types/workflow/flashcardBankWorkflow.types.ts) and [Flashcards Flow](../../skills/lesson-workflow/create-flashcards-flow.skill.md) govern new work. Flags remain `parameters.flags: Flashcard_Flag_Config[]`, not a keyed map, in source and published Props. Historical YAML is retained as provenance only; the old YAML-only Builder is retired.
- Historical Lesson YAML transfers used `sectionDrafts: {items,order}`. In the typed Lesson Stage 8 handoff, preserve any approved Section identity/order separately and create **only** the minimal bank-owned Stage 1 `draft.ts` after the verified Question prerequisite. Do **not** call Card/Side materializers, invent cards or generate an in-Lesson Flashcards Section merely because a future bank is required. The Section owner resolves a Stage 3 selection using imported completed Card `.id` values; old `sectionDrafts` are historical handoff data, not published Props.
- The Methodologist makes separate decisions about own Question Bank, local Quiz and local Flashcards Section. A substantive instructional bank can exist without a Quiz; an assessment-only Lesson can consume reviewed upstream banks without an own bank. Flashcards normally follow completed/integrated own Questions or an explicit justified own-Questions N/A decision. Never create an empty bank PR merely for status accounting.
- Keep review approvals, evidence matrices, blockers, version SHAs and next actions in each child PR description. For a typed Question Bank, `production` contains methodology and per-Question diagnostic rationale, **never** approval flags, a duplicate Question-ID selection ledger, stage status or a second schema. Do not create parallel YAML/TS sources, `lesson-questions.schema.json`, `toc.yaml`, `config.yaml` or an issue ledger.

## Typed Question Bank ownership and Stage 1–5 handoff

The incomplete Stage 1 file has `config.ownerLessonId` (the verified Lesson UUID) and `production.languages.document/planned`, approved assessment decisions and Lesson source evidence. The Lesson Stage 7 handoff creates only this file when own-bank creation is authorized; it does **not** generate Questions or Sections. Stage 2 uses the nine actual Question Config/Zod contracts, nested plain ContentBlock Config nodes, immutable real UUIDs and explicit ordered collections. Stage 3 adds only local Quiz placement/selection _rationale_, or `kind:'none'`. No local Quiz is mandated just because a reusable bank exists. Distinguish `quizSectionRequired` from `quizRequiredForCompletion` and own-bank N/A from Quiz-selection N/A.

Stage 4 is independent assessment review **with direct correction** of the same typed source and baseline/final SHA evidence in the owning Questions PR. Stage 5 must verify complete grouped bank, order/identity uniqueness, real source locale, nine kind-specific rendering and all-member publisher manifest. TypeScript acceptance alone cannot prove editorial correctness. Historical YAML is preserved as source provenance; do not author it in parallel to the typed bank.

## Selection and independent source production

- `defineQuizSection` uses `params.selection.questionIds`, an explicitly chosen candidate subset. `mode: all` refers to **all listed candidates**, not every Question in the bank. Sampling must preserve the approved eligible pool. `defineFlashcardsSection` uses explicit unique `params.selection.flashcardIds`; the Section's presentation order is separate from the Flashcard flag design.
- Unselected bank members remain authored and published for other justified assessments and eventual Custom Practice. The bank author does not edit a different Lesson's external assessment-only Section.
- Question Bank **typed source materialization** after independent review consumes `QuestionBankWorkflowMaterializerInput`, the exact Stage 3 type, and delegates to nine concrete Question-kind materializers. The trusted bank writer implements the reviewed, source-SHA-pinned and no-clobber transition from `questions/draft.ts` to `questions/index.ts`; using it requires a trusted deployed workflow, explicit authorized invocation and pinned typed source. Independent Stage 4 approval remains an editorial workflow responsibility, not a technical gate. It does not edit Lesson Sections, author missing media/translations, grant approval or publish Props. Use only the exact `/questions materialize` or `/flashcards materialize` commands after the trusted workflow is deployed to default `develop`. No format selector is supported. No live typed deployment has been verified in this integration branch. Preserve every authored source on conflicts.
- A Section owner integrates reviewed, typed Question references (including eligible upstream Lesson banks) into real Quiz Sections, e.g. `questionIds: [firstQuestion.id, secondQuestion.id]`, and imports completed Flashcard Configurators into `flashcardIds: [firstCard.id, secondCard.id]` for a deliberately small, reviewed Section selection. The published contract remains `UUID[]`, not a bank embedded into Section Props. A Stage 3 Section `notApplicable` decision still permits complete bank publication for future practice. Missing referenced Questions/Flashcards, localizations and physical assets remain explicit blockers until resolved by strict textbook publication.

## UUID publication, locales and portable loading

- [Assessment publisher](../../../shared/engine/scripts/generateAssessmentResources/README.md) reads **completed** typed banks, emits independent `generated/assessmentStages/<kind>` artifacts, and combines them under `generated/assessments/` for the textbook's portable static distribution. This is separate from trusted typed Stage 5 source materialization, which never publishes assessment Props. An incomplete Stage 1/2/3 source is never publishable; missing media, unresolved Question imports, source-only locales and unreviewed members must fail closed.
- Public paths are `data/questions/<last-hex>/<uuid>/base.json`, genuine locale siblings, corresponding `data/flashcards/<last-hex>/<uuid>/` files, and one **textbook-scoped** `data/assessments/manifest.json`. There are no Lesson-relative assessment URL aliases or per-Lesson manifests. Manifest metadata indexes globally unique IDs, kind, available locales and optional `ownerLessonId` provenance, **not** bank bodies. Reject UUID collisions across Lessons and kinds, unsafe paths and missing/inconsistent metadata.
- UI Kit consumes selected entries through host-injected loaders rather than importing textbook-authored TypeScript or hard-coded host URLs. Preserve selection, cancellation, caching, RTL, accessible equivalent stimulus, missing-resource states and offline distribution. A real published English locale can be a **runtime** fallback; missing required declared translations must still fail strict publication, and fallback must not be presented as a completed translation.
- Verify all bank members (including unselected items), the actual selected UUIDs, effective Lesson locales, manifest, required media and real textbook build before declaring resources complete. Cross-Lesson Quiz selection requires reviewed upstream bank PRs integrated into the target branch and actual global resource resolution, not guessed IDs or merely proposed Course methodology.

## Review and limitations

Independent assessment and memory review, translation and independent linguistic review cover the **entire bank**, factual validity, answer models, cognitive distinctness, memory atomicity, flags/relationships, accessible alternatives, and exact locales. Scene/media placeholders, unresolved Question field imports, missing localized acronyms, or unsupported grading stay visible blockers. Custom Practice and secure proctoring are **not** implemented merely by independently publishing banks. Current code and tests determine what has shipped; report mismatches rather than resurrecting old APIs or migration procedures.
