# Independent Question and Flashcard banks

**Status:** Current architecture. The Lesson/bank separation and global UUID assessment publication were merged in PRs #606 and #668. This is a maintained contract, **not** an implementation migration checklist, an alternate production workflow or evidence that a specific bank has educational approval.

**Workflow owners:** [Create Lesson Flow](../../skills/lesson-workflow/create-lesson-flow.skill.md) owns the parent Lesson; [Create Questions Flow](../../skills/lesson-workflow/create-questions-flow.skill.md) and [Create Flashcards Flow](../../skills/lesson-workflow/create-flashcards-flow.skill.md) own separate independently reviewed, seven-stage child Draft PRs. Read the [Questions authoring standard](../../skills/lesson-workflow/create-lesson-questions.skill.md), [Flashcards authoring standard](../../skills/lesson-workflow/create-lesson-flashcards.skill.md) and current Engine implementation for details.

## Source and ownership

- A Lesson Config/Props owns ordered Sections, **not** embedded Questions or Flashcards. A Quiz or Flashcards Section selects explicit resources but does not serialize a bank in Lesson JSON, Course overrides, SSR payloads or screen ContentBlocks.
- Approved, Lesson-owned `questions.yaml` lives beside the Lesson UUID root and contains real Engine-shaped Question Configs grouped by type and slug; Quiz selection lives only in typed Quiz Section Config: import the approved Question Configurators and reference their stable `.id` values as a deliberate UUID subset. There is no parallel `questions.yaml` selection ledger. See [Questions Builder](../../../shared/engine/scripts/questionsBuilder/README.md) and actual `yamlQuestion_Schema`.
- **Canonical Question Code layout:** `questions/index.ts` imports type-level indexes and exports the complete `questions` bank; every `questions/<questionType>/index.ts` re-exports all `questions/<questionType>/<questionSlug>.ts` Question definitions of that type. The type folder name is the exact Engine Question discriminant. Nested `<questionSlug>/` directories may hold Question-owned ContentBlocks, but not the Question entrypoint. Flat Question modules at bank root and `<type>/<slug>/index.ts` Question entrypoints are obsolete and not supported by the current review adapter. Existing authored banks using either obsolete layout require verified, non-destructive migration before reference generation; this architecture decision does not authorize rewriting independently reviewed content.
- **Target typed Flashcard workflow (PR #784, integrating through #775):** the Lesson-owned `flashcards/index.ts` is one progressively enriched `FlashcardBankWorkflowStage1 → Stage2 → Stage3` editorial source, initially a bank-only handoff (no cards) after the Question-first gate. Stage 2 stores real Card Config nodes, ordered front/back/hint Side ContentBlocks (including plain `CarouselSource` / `CheckpointSource` composite trees supported by the merged source renderers) and one canonical `config.relationships: {items,order}` edge map; Stage 3 records the independent optional in-Lesson Section decision. The independently reviewed Stage 3 type is also the sole Stage 5 materializer input. [Typed workflow contract](../../../shared/engine/types/workflow/flashcardBankWorkflow.types.ts) and [Flashcards Flow](../../skills/lesson-workflow/create-flashcards-flow.skill.md) govern new work when integrated. Flags remain `parameters.flags: Flashcard_Flag_Config[]`, not a keyed map, in source and published Props. **Existing** `flashcards.yaml` banks and the old YAML-only Builder are supported legacy inputs until a verified, non-destructive transition; neither is a parallel editor for new typed work.
- The older Lesson Stage 6 transfer may retain incomplete Section nodes under `sectionDrafts: {items,order}` in legacy Question/Flashcard YAML. In the target typed Lesson Stage 8 handoff, preserve any approved Section identity/order separately and create **only** the minimal bank-owned Stage 1 `index.ts` after the verified Question prerequisite. Do **not** call Card/Side materializers, invent cards or generate an in-Lesson Flashcards Section merely because a future bank is required. The Section owner resolves a Stage 3 selection using imported completed Card `.id` values; old `sectionDrafts` are historical handoff data, not published Props.
- The Methodologist makes separate decisions about own Question Bank, local Quiz and local Flashcards Section. A substantive instructional bank can exist without a Quiz; an assessment-only Lesson can consume reviewed upstream banks without an own bank. Flashcards normally follow completed/integrated own Questions or an explicit justified own-Questions N/A decision. Never create an empty bank PR merely for status accounting.
- Keep review approvals, evidence matrices, blockers, version SHAs and next actions in each child PR description; do **not** duplicate them in YAML status fields, a parallel `lesson-questions.schema.json`, `toc.yaml`, `config.yaml` or an issue ledger.

## Selection and independent source production

- `defineQuizSection` uses `params.selection.questionIds`, an explicitly chosen candidate subset. `mode: all` refers to **all listed candidates**, not every Question in the bank. Sampling must preserve the approved eligible pool. `defineFlashcardsSection` uses explicit unique `params.selection.flashcardIds`; the Section's presentation order is separate from the Flashcard flag design.
- Unselected bank members remain authored and published for other justified assessments and eventual Custom Practice. The bank author does not edit a different Lesson's external assessment-only Section.
- **Legacy observed behavior:** the Questions and Flashcards Builders create-only typed source drafts from their corresponding YAML; `/questions materialize` and `/flashcards materialize` are their current opt-in YAML-based CI routes. They do **not** consume Stage 3 typed objects, modify Lesson Sections, grant editorial approval, or publish Props. Do not invoke those commands on new typed sources, remove active legacy scripts, or rewrite conflicting authored files before the parent #775 orchestration supplies a verified replacement. **Typed Flashcard Stage 5 boundary:** #777–#780 concrete Section, Card/Side and ContentBlock renderers have been merged into the integration branch, but they accept **complete individual Config-shaped sources**, not Stage 1 or Stage 3 bank envelopes. The separate parent #775 bank orchestration must validate the complete reviewed Stage 3, expand the one-edge bank graph to both endpoint Card UUIDs, translate the Card/Side child callbacks, and atomically transfer the SHA-pinned staged `flashcards/index.ts` into the complete final bank export (no blind create-only overwrite). It must maintain no-clobber, asset, language and release guards. Section integration remains independently owned; mere presence of concrete renderers is not an implemented complete bank writer.
- A Section owner integrates reviewed, typed Question references (including eligible upstream Lesson banks) into real Quiz Sections, e.g. `questionIds: [firstQuestion.id, secondQuestion.id]`, and imports completed Flashcard Configurators into `flashcardIds: [firstCard.id, secondCard.id]` for a deliberately small, reviewed Section selection. The published contract remains `UUID[]`, not a bank embedded into Section Props. A Stage 3 Section `notApplicable` decision still permits complete bank publication for future practice. Missing referenced Questions/Flashcards, localizations and physical assets remain explicit blockers until resolved by strict textbook publication.

## UUID publication, locales and portable loading

- [Assessment publisher](../../../shared/engine/scripts/generateAssessmentResources/README.md) reads **completed** typed banks, emits independent `generated/assessmentStages/<kind>` artifacts, and combines them under `generated/assessments/` for the textbook's portable static distribution. This is separate from either older YAML draft scaffolding or the proposed typed Stage 5 source materialization. An incomplete Stage 1/2/3 source is never publishable; missing media, unresolved Question imports, source-only locales and unreviewed members must fail closed.
- Public paths are `data/questions/<last-hex>/<uuid>/base.json`, genuine locale siblings, corresponding `data/flashcards/<last-hex>/<uuid>/` files, and one **textbook-scoped** `data/assessments/manifest.json`. There are no Lesson-relative assessment URL aliases or per-Lesson manifests. Manifest metadata indexes globally unique IDs, kind, available locales and optional `ownerLessonId` provenance, **not** bank bodies. Reject UUID collisions across Lessons and kinds, unsafe paths and missing/inconsistent metadata.
- UI Kit consumes selected entries through host-injected loaders rather than importing textbook-authored TypeScript or hard-coded host URLs. Preserve selection, cancellation, caching, RTL, accessible equivalent stimulus, missing-resource states and offline distribution. A real published English locale can be a **runtime** fallback; missing required declared translations must still fail strict publication, and fallback must not be presented as a completed translation.
- Verify all bank members (including unselected items), the actual selected UUIDs, effective Lesson locales, manifest, required media and real textbook build before declaring resources complete. Cross-Lesson Quiz selection requires reviewed upstream bank PRs integrated into the target branch and actual global resource resolution, not guessed IDs or merely proposed Course methodology.

## Review and limitations

Independent assessment and memory review, translation and independent linguistic review cover the **entire bank**, factual validity, answer models, cognitive distinctness, memory atomicity, flags/relationships, accessible alternatives, and exact locales. Scene/media placeholders, unresolved Question field imports, missing localized acronyms, or unsupported grading stay visible blockers. Custom Practice and secure proctoring are **not** implemented merely by independently publishing banks. Current code and tests determine what has shipped; report mismatches rather than resurrecting old APIs or migration procedures.
