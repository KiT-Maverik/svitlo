# Create Flashcards Flow

**Owner:** Coding Agent coordinates one Lesson-owned Flashcard Bank. The Flashcard Learning Architect authors Stages 1–3, an **independent** Memory Design Reviewer reviews Stage 4, Coding Agent materializes Stage 5, Technical Translator owns Stage 6, and a different independent linguistic reviewer owns Stage 7. Read root `AGENTS.md`, [Lesson Workflow](./README.md), [Create Lesson Flashcards](./create-lesson-flashcards.skill.md), [Flashcard Learning Architect](../../personas/flashcard-learning-architect.persona.md), [Questions Flow](./create-questions-flow.skill.md), [Lesson Flow](./create-lesson-flow.skill.md), Engine Flashcard/Side/ContentBlock Config, actual materializers, and the [independent-bank architecture](../../docs/architecture/lesson-assessment-bank-separation.md) before acting.

## Ownership, identity and the one authored source

An existing Lesson UUID or Lesson PR identifies the owning Lesson. Resolve its **actual** UUID directory, parent branch/PR, current approved Lesson methodology, source and derived purpose-`flashcards` reference SHA, true document language and planned languages, and complete upstream Questions evidence. Reuse the existing Draft Flashcards child PR or, when independently authorized, open **one Draft Flashcards PR** targeting the active Lesson branch (or verified integration branch after Lesson merge). The parent Lesson Stage 8 hands off a bank but does not silently create the child PR. Keep Course → Lesson → Questions/Flashcards branch relationships; do not create a new Lesson ID, bank ID, new translation PR, review PR or production Issue.

**Canonical editorial source:** `content/<textbook>/data/lessons/<last-hex-digit>/<lesson-uuid>/flashcards/draft.ts`, a single progressively enriched **typed plain object** satisfying `FlashcardBankWorkflowStage1`, then `FlashcardBankWorkflowStage2`, then `FlashcardBankWorkflowStage3`. The same file is advanced **in place**. Only after independent Stage 4 approval does Stage 5 turn that completed editorial object into individual `defineFlashcard` and `defineFlashcardSide` modules and the full `flashcards/index.ts` bank export. The workflow input is **not** a `defineFlashcard`, bank Props, an additional approval/status Config, or a parallel `flashcards.yaml`. For a bank already using a durable typed `flashcards/index.ts`, inspect and non-destructively reconcile existing authored resources; never clobber them with a staged handoff. The materializer must consume the reviewed `draft.ts` while creating the final bank `index.ts` and all members in one Git commit.

**Canonical types:** [Flashcard Bank workflow](../../../shared/engine/types/workflow/flashcardBankWorkflow.types.ts), shared `CourseWorkflowStage1Languages` and `LessonProductionAssessmentRequirements`, real `Flashcard_Config`, `FlashcardSide_Config`, ContentBlock Configs, and `FlashcardsSection_Config`. A bank has the owning Lesson's ID, not an independent UUID. A Side has no identity. `parameters.flags` is a typed array; bank `relationships.items/order` is the sole authored graph, not a second mirrored list in each Card.

Follow the [independent review rule](../../rules/independent-review.md) for Stage 4 and parent Questions N/A. The existing **Flashcards PR description** (marker `<!-- svitlo-create-flashcards-flow:v1 -->`) is the **sole stage/status/review ledger**: parent Lesson PR, UUID, source and Questions SHAs, reviewed source SHA, methodologist N/A evidence when applicable, seven stage checkboxes, unresolved blockers, translator/reviewer identity, source/review revisions, per-locale coverage and next action. Keep stage verdicts, approvals, asset requests and review notes out of Config/Props. Stale source SHAs invalidate only dependent editorial approvals. These records are not technical materializer inputs; actual Question references, source identity and integrity remain checked.

## Editorial prerequisites: Questions-first ordering

1. Read the **approved assembled Lesson source** and purpose-`flashcards` reference from the verified source SHA. The curated Lesson media candidates are the starting asset index; inspect specific linked resources only as necessary. Do not invent Lesson methodology, facts or media.
2. Read the **entire** independently reviewed Question Bank at its current SHA, not only the default Quiz selection. It must be **completed, reviewed and integrated**, or the Lesson PR must explicitly record **Questions: Not Applicable** with verified Methodologist rationale and source SHA. Missing, unreviewed, empty or blocked Questions, or merely having no Quiz, never passes. Re-evaluate affected card reuse when Questions change.
3. Check the Lesson's four independent `LessonProductionAssessmentRequirements` decisions: `questionBankRequired`, `flashcardBankRequired`, `quizSectionRequired`, `flashcardsSectionRequired`. A full bank is independent of any embedded Section; a justified assessment-only Lesson may use upstream banks. An own required but incomplete Question Bank **blocks** Flashcard Stage 1 handoff. If the own Flashcard Bank is not required, do not fabricate an empty bank to track N/A.
4. Read the actual Engine Config/Build API, the primitive ContentBlock, composite/Scene, Card/Side and Flashcards Section source materializers, full authored bank directory, publisher and translation-review generator. Check the current parent HEAD before invocation: concrete per-entity renderers existing in the codebase do **not** prove bank-level orchestration, safe Stage 3 source replacement or publication is implemented.

## Seven stages

### 1. Lesson Analysis — Flashcard Learning Architect

Create only the **minimal bank-owned typed Stage 1 source**, `const bank = { production: ... } satisfies FlashcardBankWorkflowStage1` in the Lesson-owned bank location. `production.lesson` holds the **existing** Lesson UUID, reviewed source SHA and reference path/SHA, `CourseWorkflowStage1Languages` (document and nonempty planned tuple), and four existing assessment decisions. Record Questions completion or justified N/A in the existing PR as editorial evidence, not in the typed bank input. The Stage 1 contract contains only `production.lesson` and `production.analysis`; do not add an editorial `production.questions` field. `production.analysis` has recall objectives, source facts/concepts, misconceptions, exclusions, rationale for inventory size, and source grounding. Keep source-derived editorial detail in this one TS source, not another YAML or Markdown plan.

**No Flashcard IDs, side IDs, card content or Flashcards Section are created at Stage 1.** No call to `materializeFlashcard`, `materializeFlashcardSide`, the YAML Builder or the resource publisher is permitted. The Stage 1 handoff is explicitly non-publishable. The parent Lesson Stage 8 may create only this minimal typed source after verified Questions; it does not claim the Flashcards child PR is complete.

### 2. Flashcard Design — Flashcard Learning Architect

Advance **the same object** to `FlashcardBankWorkflowStage2`: preserve all Stage 1 `production`, add `production.design` audits and a complete source-language `config.flashcards: { items, order }` with named Card nodes containing real immutable Card UUID/slug, `parameters.tags`, optional disability restrictions, **`parameters.flags: Flashcard_Flag_Config[]`**, and `content.front/back/hint` as real ordered `FlashcardSide` ContentBlock Config collections. Use real immutable ContentBlock IDs. No Side UUID/slug. Only source-language values are authored at this stage, while `production.lesson.languages.planned` retains the full intended translation scope; do not fake other locales.

Use [Create Lesson Flashcards](./create-lesson-flashcards.skill.md) for the complete atomicity, concise answer, bidirectional recall, typed Text/Code/Markdown variables, lists, acronym connector-letter mapping, custom flags, source references, accessible media and per-direction disability guidance. Ensure Card `parameters.relationships` is **not** manually authored. Instead, author each semantic relation **once** in bank `config.relationships: { items, order }` as `{relationshipId,type,source,target}` with real card slug endpoints and one of nine exact Engine relationship types. At Stage 5 the source-to-endpoint projection preserves `relationshipId`, uses the _other Card's UUID_ and generates `peer` for symmetric or `source/target` for directed links; no duplicates, self-relations or reversed semantics.

To reuse Question fields, pin the exact Question export/field/locale/source SHA as editorial `production.questionReuse` **without** placing fake `kind: questionField` nodes into Config. A materializer may emit a direct verified typed import when implemented. Until then, that card is **blocked**, not silently copied or fabricated. New Flashcard-owned ContentBlocks get their own UUIDs; intentional reuse of an existing Question-owned Configurator retains that existing identity only after collision/ownership review. Do not invent asset paths, missing-media values, or translations.

### 3. Flashcards Section Design — Flashcard Learning Architect and Section owner

Advance to `FlashcardBankWorkflowStage3` with **one explicit** `production.section` decision:

- `{kind:'notApplicable',rationale}` when the complete bank is useful for independent or future practice but has no pedagogically warranted in-Lesson Section.
- `{kind:'selected',section:{id,slug},existingSection,placement,selectedCardSlugs,rationale,lessonSourceSha}` for a **small, justified ordered** in-Lesson selection, expressed as existing Card _keys_, **not a competing UUID list**.

Preserve the existing approved Section ID, slug, learner copy and original order, including a provisional blocked Section left by Lesson Stage 6, when present. No bank is embedded into Lesson/Section Props. **Only the owning Lesson Section integration step**, after Card materialization, imports completed Card Configurators and assigns `defineFlashcardsSection.params.selection.flashcardIds: [cardOne.id, cardTwo.id]`, replaces any reserved `feedc0de-` placeholders and verifies every chosen real published resource. A bank materializer must **never** rewrite Lesson root, Section registries or Questions. Unselected Card members still belong to the full bank and must be published.

### 4. Memory Design Review — independent qualified reviewer

Different agent/context independently reviews the **full Stage 3 TS source** at the verified Lesson and Question SHAs. Examine factual correctness, concise atomic targets, front/back/hint accessibility, direction and duplication, list counts, mnemonic decompositions and localized strategy, flags and colors, per-direction restrictions, media/answer leakage, exact Question export validity, all graph edges and direction, Card count and the actual proposed Section subset or N/A. Record reviewer identity, findings, source SHA and decision **in the same Flashcards PR**. Reviewer may correct this **same TS source** and record the final reviewed SHA. **No Stage 4 type/file** or approval/status in Config/Props. Typechecking or passing lightweight Draft CI is not independent review.

### 5. Resource Production — Coding Agent

Use **`FlashcardBankWorkflowMaterializerInput = FlashcardBankWorkflowStage3`** only after the recorded independent Stage 4 approval at the exact source SHA. The concrete `materializeFlashcard` and `materializeFlashcardSide` implementations have adjacent tests registered by the Engine package runner. They render **individual complete Cards/Sides**, not a Stage 1 bank or the Stage 3 bank collection. The bank materializer owns the bank-level edge expansion, atomic reviewed `draft.ts` deletion and final `index.ts` creation, safe writer, shared exports, full dispatch and release gates. Revalidate current APIs and source/review SHA; expand the **one** canonical bank relationship graph deterministically into the exact two endpoint `parameters.relationships` collections expected by the Card renderer. Validate real UUIDs, slug keys, source locale and distinct front/back/hint ContentBlock objects. For nested Carousel/Checkpoint blocks, use the canonical **plain source types** (`CarouselSource`, `CheckpointSource`), not the final `ContentBlock_Carousel_Config` / `ContentBlock_Checkpoint_Config` child-Configurator shapes; follow each real child renderer's ordered Config-only contract. Delegate nested Text/Code/Markdown/media to the actual registered ContentBlock materializers; no generic fabricated materializer registry.

Emit durable `flashcards/<card>.ts`, Card-owned `flashcards/<card>/content/<front|back|hint>/` and `flashcards/index.ts` exporting **every** Card. Use the concrete renderer contracts: `FlashcardNode` has `{config, production?}`, its `config.content` holds distinct Side Config maps, while `FlashcardSideContext.materializeBlock` receives `{config, production?}` with a child directory and `documentLanguage`. The Stage 3 Card `production` fields are **editorial**, not passed wholesale into the limited renderer `production?: {pending?,specification?}` contract; check unresolved Question/media dependencies before any call. Renderers may produce source-only TODO blockers for missing media, unresolved Question imports and other non-publishable dependencies; do not claim completion or build/publication in those cases. Writes must be deterministic, **create-only/no-clobber**, symlink/path safe and source-SHA checked; do not replace a hand-edited index or another bank. Produce required source-derived review artifacts only from real finalized source, not a second editorial ledger. Delete the approved Stage 3 `draft.ts` in the same commit as final source creation; keep exact source/review provenance in Git. Section integration is explicitly owned by the Lesson Section owner, not this bank materializer.

After source completion, run the independent `generateAssessmentResources --kind flashcard` production publisher and strict owning textbook build. Confirm full `base.json`, required locale JSON and textbook-scoped manifest, including **unselected** Cards. Verify Section UUID refs against published resources and accessible candidate filtering. Missing physical assets, reserved Nil UUID/media placeholders, `TODO(asset)`, unresolved references, uncovered required locales, failed validation and incomplete bank must **block publication**. Materialization alone is never a successful Stage 5.

**Typed materialization:** the trusted `/flashcards materialize` command requires an explicitly authorized invocation and valid pinned Stage 3 bank source; it is available for live use only after default-branch deployment. Stage 4 review and Questions-first ordering remain editorial, not machine-parsed prerequisites. The old YAML Builder was retired; the command has no YAML fallback. See [Bank materialization](../../../scripts/ci/bankMaterialization/README.md). Preserve historic authoring bytes and review provenance when migrating legacy work.

### 6. Translation — Technical Translator

On the **same Flashcards PR**, translate the **entire authored bank**, not merely Section-selected cards, into the verified Lesson planned languages: every front/back/hint block, learner-facing custom flag and acronym, alt/caption/transcript and other media alternatives. Reused Question fields retain their real localized typed references; never clone translations or fill other locales with source copy. Mnemonic values often need independently designed locale-specific versions. Track each Card/field × locale, translator and source SHA in the PR. A Course's smaller locale subset never narrows a globally reusable bank.

### 7. Translation Review — independent Linguistic Reviewer

An independent linguistic reviewer in a different context reviews **the complete bank** against source-SHA-pinned, full-bank Code-derived Markdown/manifest references, not the Lesson design-context Markdown or only selected Card IDs. Use the existing [Flashcard reference adapter](../../../shared/engine/scripts/generateFlashcardReviewArtifacts/README.md) and verified [agent CI artifact protocol](../../docs/architecture/agent-ci-artifacts.md); fail closed if a source-scoped adapter/workflow is unavailable on the actual branch. Check meaning, correct answers, mathematical/code syntax, terminology, acronym reconstruction, accessibility equivalents, RTL, punctuation, media and locale parity. Authorized fixes occur on the **same Flashcards PR**; regenerate/review affected sources and record reviewer, source/fix/final SHAs plus per-locale verdicts. No new review PR, Issue, status file or translation sidecar.

## Stage report and handoff

On every resume, completion or blocker, fetch the exact child PR, its parent Lesson PR, source revisions, verified Question approval and current branch ancestry. State parent/child PR and Lesson UUID, source and Question SHAs, **all seven stages** in order (completed/in-progress/not-started/blocked/stale, with evidence), last completed stage, first actually eligible next stage, blockers and **one** concrete copyable `do flashcards stage N for PR #...` instruction. A contextless `go` is permission only for the specific previously proposed action in the current chat. Never self-approve Memory/Translation review, auto-merge, infer completion from checked boxes, or invent missing source/review/CI evidence.

When all seven stages are independently verified: **"All seven Flashcards workflow stages are complete. There is no next Flashcards stage. You can assign new work."** Bank completion does not itself authorize Ready/merge or parent Lesson Stage 8 completion; verify child integration first. For **production Flashcards entity PRs**, remain Draft while work is still being authored or blocked; after the assigned authorized work is complete and fit for review, follow the current CI policy to transition to Ready, inspect target-specific checks and return to Draft for fixes. Ready never authorizes merge or publication.

## Mapping the retired YAML workflow to the single TS source

| Previous `flashcards.yaml` / workflow item                           | Typed destination or PR-only evidence                                                                |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `lessonId`                                                           | `production.lesson.id`, reused Lesson UUID                                                           |
| `documentLanguage`, `supportedLanguages`                             | `production.lesson.languages.document/planned`, shared typed language contract                       |
| source Lesson reference, methodology, Question prerequisites         | `production.lesson.sourceSha/reference/assessment`; Questions completion/N/A in PR only (editorial)                 |
| analysis inventory/exclusions                                        | `production.analysis` (Stage 1)                                                                      |
| `flashcards.items/order`                                             | `config.flashcards.items/order` (Stage 2)                                                            |
| individual Card `id/slug/parameters/content`                         | each `config.flashcards.items[key].config` (Stage 2); real Engine Config                             |
| `parameters.flags`                                                   | real `Flashcard_Flag_Config[]` array; values localized only when authored                            |
| `content.front/back/hint.items/order`                                | each `FlashcardBankWorkflowSideSource`, no Side identity                                             |
| `relationships.items/order` with `relationshipId/type/source/target` | `config.relationships.items/order` (Stage 2), expanded once at Stage 5                               |
| `sectionDrafts` / proposed Section IDs                               | `production.section` selected/N/A (Stage 3); existing Lesson Section source remains owner-controlled |
| Stage 4 memory review, Stage 5 materialization evidence              | existing child PR only, pinned to Stage 3 source/review SHA                                          |
| Stages 6/7 translation/review per Card × locale                      | durable typed localized Card sources; evidence and manifest/reviewer in same PR only                 |

**Validation boundary:** Stages 1–3 are editorially progressive and do **not** need to be publishable or pass full materializer schemas. The exact reviewed final Stage 3 **does** require strict typecheck, materializer validation, safe-write checks, resource build, publication/locale verification and independent reviews before release. A successful Draft fast gate is never evidence of a full Engine typecheck.
