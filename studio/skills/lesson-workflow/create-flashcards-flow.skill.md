# Create Flashcards Flow

**Owner:** Coding Agent coordinates one Lesson-owned Flashcard bank; Flashcard Learning Architect, independent Memory Design Reviewer, Technical Translator and independent Linguistic Reviewer own their respective evidence. Read the repo root instructions, this workflow index, the complete [Flashcard authoring skill](./create-lesson-flashcards.skill.md), [Flashcard Learning Architect persona](../../personas/flashcard-learning-architect.persona.md), current Engine Config/Props/YAML schemas, and the independent-assessment architecture before starting.

## Invocation, identity, and branch ancestry

Start with either an existing **Lesson UUID** or **Lesson PR number**. Resolve the same-repository active Lesson PR (if any), canonical UUID directory, actual owner and source SHA, original methodology, support languages, and Question-bank stage. Do not create another Lesson, assign another UUID, or infer approval from file existence. Reuse any existing Flashcards PR for this Lesson. Otherwise create exactly one **Draft Flashcards PR**: target the active Lesson PR head branch, or the verified current integration branch (normally `develop`) if the Lesson was already merged. Record original Lesson PR provenance. Follow GitHub naming and labels; do not apply mutually exclusive `pr: integration` and `pr: agent-subtask` to the same PR. Confirm nested Course→Lesson→Flashcards ancestry with the actual open PRs.

The Flashcards PR description is the **single resumable process record**. Mark it `<!-- svitlo-create-flashcards-flow:v1 -->`, with Lesson UUID, parent PR, source SHA, Question source SHA and approval/N/A rationale, reference Markdown revision, document language, owning Lesson languages, optional verified Course subset, seven stage checkboxes, blockers, verified reviewer IDs and next action. Keep no workflow status in Flashcard YAML, Config or Props. Stale source SHA invalidates only dependent evidence.

## Hard prerequisites

1. Read **actual approved Lesson content** and methodology from the Lesson Markdown reference generated by PR #645, purpose `flashcards`, at the pinned Lesson source SHA. Use only its curated source Section/Block/media candidates; resolve a specific linked resource directly when necessary. Do not scan all Lesson files or textbook assets.
2. Read the **complete current approved Question bank**, not merely default Quiz selection. Questions must be marked **Completed** with a verifiable bank source revision, or explicitly **Not Applicable** in the owning Lesson PR with Methodologist rationale. A missing, unreviewed, empty, unfinished or blocked bank, and the absence of a Quiz, are **not** N/A. If upstream Questions change, re-evaluate dependent cards and field references.
3. Confirm a canonical typed Lesson identity, language tuple, relevant Engine schemas, real UI Kit support and publication rules. If the Lesson is still a speculative draft without assembled source/context, mark **Blocked** in the PR. Do not synthesize lesson content or false translations to pass this gate.

## Mandatory user-facing stage report and next-action handoff

On each completion, pause, blocker or status/resume request (including a new-chat message containing only a Flashcards PR number), re-fetch the exact Flashcards child PR, parent Lesson PR, branch ancestry, Lesson UUID and current approved Lesson/Question evidence SHAs. Reconcile the child checklist with actual YAML/typed resources, independent reviewer evidence and locales. A bare PR number is **status plus recommendation only**, not permission to start or continue authoring. The child PR body remains the sole progress tracker; no workflow status goes into Flashcard YAML, Lesson Config/Props or a second ledger. **If invoked from the owning Lesson PR without an existing Flashcards child PR**, report `Flashcards PR: Not started` and all seven stages as not started; first verify that Flashcards are justified and Questions are completed/reviewed/integrated or explicitly `Not Applicable` with Methodologist evidence. Then offer the concrete command `do flashcards for lesson <lesson-uuid> related to PR #<lesson-pr-number>` without executing it; never invent a child PR number.

Always include:

1. **Identity:** Lesson UUID/slug, parent Lesson PR `#N`, Flashcards child PR `#M`, verified source/head SHA; state the Question Bank source SHA or Methodologist-backed own `Questions: Not Applicable` decision.
2. **All seven Flashcards stages in order:** 1. Lesson Analysis; 2. Flashcard Design; 3. Flashcards Section Design; 4. Memory Design Review; 5. Resource Production; 6. Translation; 7. Translation Review. Mark each `✅ completed`, `▶ in progress`, `⬜ not started`, `⛔ blocked` or `↻ stale` with evidence, source/review SHA and per-locale status. A full Flashcard Bank **does not require** an embedded Flashcards Section; report justified `Section selection: Not Applicable` separately, without automatically declaring the _entire bank workflow_ N/A.
3. **Last completed stage:** name the latest verified `Stage N — <name> completed`, or `No new stage completed`; identify stale reviews and blockers.
4. **Next Flashcards stage:** first eligible pending stage, or `None — all seven Flashcards stages are complete`.
5. **Recommended next action:** one specific copyable **chat instruction** in a fenced `text` block, for example `do flashcards stage 2 for PR #<flashcards-pr-number>`; explain its prerequisites. Invite the user to paste the command or answer `go` to the single concrete action proposed **in the current chat**. A PR number or contextless `go` requests no mutation; the phrase is a chat request, **not a CLI command**. Never auto-author, self-review, merge or fabricate missing Questions evidence.

**Question-first gate:** if own Questions remain required but uncompleted/unreviewed/unintegrated, mark the Flashcards handoff blocked and recommend the real Questions PR/next action instead. The only bypass is the parent Lesson PR's explicit, verified **`Questions: Not Applicable` with Methodologist rationale**; no local Quiz or a blank bank is not an exemption. If Flashcards themselves are pedagogically `Not Applicable`, do not create an empty Flashcards PR merely to show seven unchecked stages.

**Handoff/terminal state:** when all seven Flashcards stages are independently verified complete, explicitly say **"All seven Flashcards workflow stages are complete. There is no next Flashcards stage. You can assign new work."** If the child PR is not yet integrated, recommend the authorized final QA/review/integration action; once actually integrated, recommend returning to the Lesson parent for its remaining stage(s) or final acceptance. After real child review and integration, the parent agent may check **Lesson Stage 8 — Flashcards**, then propose `do lesson stage 9 for PR #<lesson-pr-number>` for Translation or the final gates if already completed. Show one concrete chat instruction **only when that stage is truly next and authorized**. Bank stage completion is not by itself permission to mark Ready, merge, publish or auto-continue the Lesson.

**Authoring validation boundary:** Stages 1–4 do not require a separate manual technical-schema or TypeScript check for every incomplete `flashcards.yaml` edit; the existing Stage 5 Flashcard Builder validates the reviewed final bank before creating any files. Preserve Stage 4 independent Memory Design Review, real Question/Lesson dependencies, source SHA, safe creation, all required media/locale checks and production CI. See the [four-flow validation audit](../../docs/architecture/yaml-config-scaffolding.md#validation-boundaries-across-the-four-entity-workflows).

## Seven-stage production

### 1. Lesson Analysis — Flashcard Learning Architect

Extract a source-grounded **memory-objective inventory**: durable facts, dates, terminology, formulas, useful contrasts, misconceptions and brief conceptual relationships. Identify objectives that belong in Lessons or Questions rather than recall cards. There is no fixed number of cards per Skill, paragraph or Question. Record the inventory and justified exclusions **in the Flashcards PR description or comments**, not a second canonical content file.

### 2. Flashcard Design — Flashcard Learning Architect

Create exactly one source-language `flashcards.yaml` at the canonical Lesson UUID root, immediately compatible with the current Engine `yamlFlashcard_Schema` and `flashcard_Config_Schema` shapes: stable UUIDs, bank `items/order`, front/back/optional hint ContentBlocks, concrete learner-facing values, Flashcard-owned flags, canonical relationships and `parameters.disabilities`. **Both current Engine authoring Config and published Props use `parameters.flags: []`**. Flag order has no semantic significance, and `build.overrides` replaces the entire flag array; do not resurrect named `items/order` patches or a competing schema. The bank is a single technical authoring source, not a prose-only editorial plan. The independent source language and supported Lesson language plan remain explicit in its authoring envelope; translation is a later stage.

Use the detailed atomicity, list-count, acronym, relation and variable guidance in [Create Lesson Flashcards](./create-lesson-flashcards.skill.md). Do not duplicate Question-localized factual values: reference verified actual typed Question exports/fields and use the complete selected locale shape in eventual TS. A Question link must have a verified export and type-compatible field path, never a guessed property chain.

Choose whether each retrieval **direction** genuinely needs a distinct card. Preserve one canonical relationship edge per meaningful pair; connect both endpoints by UUID on materialization. Derive media only from #645's curated Lesson media references. A new Flashcard-owned ContentBlock gets a fresh UUID while keeping the physical media UUID and extension. A reverse audio card can reuse the same file, but each direction gets independent eligibility restrictions.

For each card, choose `parameters.disabilities: Disability[]` using the existing Engine union. Empty `[]` means compatible with the available accessible modes. Annotate only a retrieval task that truly lacks an equivalent accessible alternative, and explain any nonempty restriction in PR review evidence. Avoid diagnosis, blanket multimedia restrictions and gratuitous overexclusion.

### 3. Flashcards Section Design — Flashcard Learning Architect / Lesson Section owner

The complete Lesson-owned Flashcard Bank is independent of its embedded Flashcards Section. The bank may retain cards for later Custom Practice; the Lesson Section selects a deliberately small, pedagogically justified, explicit ordered subset from the reviewed bank. Do not mechanically insert every bank UUID or assume a bank needs a Section.

Inspect the latest generated Lesson `sections/index.ts`, actual Section modules and current Question-flow handoff from PR #647. Stage 6 may already have emitted a **blocked but schema-valid** Flashcards Section with a reserved `feedc0de-` synthetic `flashcardIds` entry: reuse its authored UUID/order/copy, replace provisional IDs only with independently reviewed Flashcards and resolve all TODOs before production. A reserved UUIDv8 marker must never become an authored Flashcard, even if it parses as `z.uuid()`. Integrate the Questions child PR into the Lesson branch **before** rebasing a Flashcards child PR that may edit the same narrow Section registry. Reuse existing `defineFlashcardsSection` UUID/slug when suitable; otherwise create the minimum new Section and update only its owned module plus necessary registry import/order. Never regenerate the Lesson root, alter Question sources, or create another Lesson PR.

Record the chosen Flashcard UUIDs, rationale, Section placement, source SHA and conflict-safety notes in the child PR. Section selection must respect the separate accessibility metadata filter at runtime, and an excluded card must not count as completed.

### 4. Memory Design Review — independent reviewer

Review the **actual complete YAML and proposed Flashcards Section placement/selection** against pinned Lesson and Question SHAs, target coverage, scientific accuracy, atomicity, repetition, direction diversity, flags, acronym letters, relationship semantics, Question field reuse, media stimulus/answer leakage, access equivalence and intended locales. Record per-card findings, reviewer identity, exact SHA and verdict in the PR. YAML syntax, author assertions and status checkboxes never count as independent approval.

### Stage 5 CI command for approved bank YAML

After Stage 4 Memory Design Review has accepted the exact `flashcards.yaml` source and parent Lesson Questions are completed/integrated or expressly verified Not Applicable, the Coding Agent can use the opt-in [bank materialization workflow](../../../scripts/ci/bankMaterialization/README.md) once deployed on `main`. On the **existing Flashcards child Draft PR**, verify its Lesson UUID, Course/Lesson branch ancestry, reviewed YAML SHA and completed Stage 1–4 checklist, then post the exact top-level comment `/flashcards materialize` (or workflow-dispatch `bank=flashcards` with PR number). Trusted Actions runs the existing Flashcard Builder `--preflight` → `--write` → `--check`, commits only `flashcards/index.ts` into that **Flashcards PR branch**, and preserves source `flashcards.yaml`; it does not touch Lesson/Question files, Sections or translated resources. Check the actual run link and resulting commit/source SHAs before continuing the _same_ Stage 5 with media/accessibility, Section UUID validation and separate publication. The created TS draft is **not** Stage 5 completion, a Memory Review approval or permission to merge. If not deployed to `main`, use the documented local Builder with honest execution evidence.

### 5. Resource Production — Coding Agent

Use the implemented, tested [Flashcard Builder](../../../shared/engine/scripts/flashcardBuilder/README.md) to derive typed `defineFlashcard`, `defineFlashcardSide` and nested `define*` modules beneath the **existing** Lesson UUID's `flashcards/`. Validate against the one Engine/Zod-derived Config projection; do not introduce a parallel manual editorial schema or overwrite Lesson/Question source. Use creation-only writes, reject symlinks/unsafe paths, unresolved imports or media, duplicate IDs/relations, and conflicting existing TypeScript. The temporary YAML is removable **only after verified byte-complete, faithful materialization**; retain it on every skip/failure and preserve Git history.

Complete authored assets as needed, then use `generateAssessmentResources --kind flashcard --preflight/--write/--check` for separate UUID-addressed resources. Keep authored planned languages; any source-only TS draft scope from #643 is provisional and must not masquerade as complete publication. Published manifest metadata must carry disability restrictions so the loader filters Section candidates **before fetching** incompatible bodies. Preserve requested order, return a clear unavailable state on an empty eligible set, and never infer or expose learners' private access requirements.

### 6. Translation — Technical Translator

Translate all required actual learner-facing card text, alt/caption/hint, custom flag, accessible alternatives and culturally valid acronyms to the **Lesson's actual language plan** directly on the **existing Flashcards PR branch**. Track each card/field × locale, translator and exact source SHA there; **do not create an extra translation PR, reviewer PR, integration branch or Issue**. Reuse localized Question fields by reference rather than cloning them. A Course may request a verified subset without narrowing the globally reusable bank or Lesson.

### 7. Translation Review — independent Linguistic Reviewer

An **independent authorized reviewer in a different chat/context and linguistic persona** reviews complete Code-derived localized **Flashcard Bank** references and a manifest pinned to the **same Flashcards PR source SHA**. The source must include all bank members (front/back/optional hint and flags), not just Lesson Section `flashcardIds`; existing Lesson Markdown `--purpose flashcards` is a *design context*, **not proof of reviewed card translations**. If a complete bank adapter is unavailable, report a scoped review blocker instead of inventing evidence. Check scientific meaning, RTL, punctuation, terminology, alt/hints, media parity, answer leakage and acronym reconstruction. Owner-authorized fixes occur **on the same Flashcards PR**, then re-generate/review affected content; record distinct reviewer identity, source/fix/final SHAs, findings and language decision in its tracker. No separate reviewer PR.

### Publication and missing-asset release requirement

A complete `flashcards.yaml` or a successful create-only `flashcardBuilder` is **not** a published bank. Every generated media draft with `TODO(asset)`, Nil UUID, missing `fileName`/`posterFileName`, unavailable physical file, caption/transcript or unresolved referenced Question field remains **Draft-only**; keep the real dependency visible and never fabricate a replacement. Before final Flashcards PR acceptance, remove temporary `flashcards.yaml` only after faithful manual materialization, verify every bank member through `generateAssessmentResources --kind flashcard` in production mode (not `--draft`), and run the owning textbook's strict `package:build` for the required Lesson languages. Confirm actual generated Flashcard `base.json`, advertised localized JSON and textbook-scoped assessment manifest, including unselected members. Verify all Flashcards Section candidate UUIDs resolve to published resources, while keeping the full bank independent of Section selection. The final PR must contain no `TODO(asset)` or reserved Nil UUID media filenames in its authored bank modules. Source SHA, review approvals, accessibility evidence, translation coverage and production checks are separate mandatory evidence in the bank PR. A child bank PR checks its own resources; the parent Lesson PR checks the entire Lesson and all included banks before release.

## Final QA (checklist, not an eighth stage)

Verify one Lesson UUID and one Flashcards PR; pinned upstream source evidence; no duplicate/stale YAML/TS; Config, Props, source locales and requested publications; unique IDs and mirrored relation edges; Question/media references; accessibility compatibility pre-fetch selection and empty eligible state; independent reviews, source and translation approval; full Engine/UI Kit/content package checks and package builds. Confirm the active PR's actual CI and target base before requesting the owner's sign-off. **Remain Draft** until the owner explicitly marks Ready.
