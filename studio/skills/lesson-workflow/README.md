# Lesson Workflow

Each task is an **independent specialist skill**. The Lesson UUID directory is stable and Course-neutral; editors explicitly approve each role-owned artifact before downstream work. For an authorized new Lesson production scope, **locate or initialize one standard GitHub Issue for the entire frozen Lesson UUID set** before opening specialist PRs; reuse it through all stages and across chats. Do not create an Issue per Lesson or step. For Lessons identified by [Match Course TOC Lessons](../course-workflow/match-course-toc-lessons.skill.md), **resume the exact fixed-scope Issue handed off by Course Workflow**, including Course ID, matched slot keys, Methodologist Drafts and current approvals. Do not allocate replacement Lesson UUIDs, duplicate matching work, or confuse creation of an Issue with Methodology approval.

1. [Create Lesson Brief](./create-lesson-brief.skill.md) — **Methodologist Persona**. Creates `methodology.md` with pedagogical scope, verified Skill links, separate `documentLanguage` vs `supportedLanguages`, and an **explicit `assessmentPlan`**. This can declare zero, one or multiple pedagogically necessary Quizzes, each with verified Skill IDs and typed `AssessmentMethodKey` values. See [Methodology frontmatter schema](./lesson-methodology-frontmatter.schema.json). The [Course Lesson matcher](../course-workflow/match-course-toc-lessons.skill.md) reuses these same requirements when drafting missing Lessons.
2. [Create Lesson Content](./create-lesson-content.skill.md) — **Educational Screenwriter Persona**, after Methodology approval. Creates **`content.yaml`** — ordered, machine-readable Section/ContentBlock/Quiz plan with source-language learner copy, accessibility and implementation dependencies. See [Lesson Content schema](./lesson-content.schema.json). Optional `scenes/*.scene-spec.md` documents provide the independent source for bespoke Scene implementation.
3. [Review Lesson Experience](./review-lesson-experience.skill.md) — independent [Learning Experience Expert](../../personas/learning-experience-expert.persona.md). Checks educational effectiveness, interaction appropriateness, accessibility and production dependencies; writes `experience-review.md` tied to a `content.yaml` source revision.
4. [Review Lesson Methodology](./review-lesson-methodology.skill.md) — independent Methodologist. Confirms subject correctness, Skill/outcome/prerequisite coverage and Quiz/Assessment Method alignment; writes `methodology-review.md` tied to the **current** source revision.
5. [Manage Lesson Production](./manage-lesson-production.skill.md) — GitHub coordinator for **one or multiple Lessons in one fixed-scope Issue**, using [the Issue Form](../../../.github/ISSUE_TEMPLATE/lesson-production.yml), per-Lesson status rows and cross-chat PR handoffs. An authorized specialist may process all ready Lessons in a batch; do not ask for "continue" after every Lesson.

6. [Create Lesson Questions](./create-lesson-questions.skill.md) — **Learning Assessment Architect Persona**, after approved Methodology and Screenwriter content/reviews. Writes one source-language, machine-readable `questions/questions.yaml` bank per Lesson with exact assessment method/Skill mappings, type-specific answer models, evidence coverage and deliberate non-duplication. **Retains the full Question bank for future Custom Practice, but selects only an explicit, pedagogically justified subset for each ordinary Lesson Quiz** through `quizAssignments[].selection`; the future builder must write that selection to generated Quiz Section parameters without modifying the Screenwriter-owned `content.yaml`. See [Lesson Questions schema](./lesson-questions.schema.json). This is a distinct specialist production stage, **not automatically launched** by prior approval.
7. [Create Lesson Flashcards](./create-lesson-flashcards.skill.md) — **Flashcard Learning Architect Persona**, separately authorized after the full Question Bank is approved. Authors one canonical `flashcards/flashcards.yaml` with Question-field references, typed flags and relationships. This stage is independent of Scene coding.
8. [Build Lesson from YAML](../../docs/architecture/lesson-yaml-builder.md) — **deterministic Node.js/TypeScript Builder**, not an AI skill. After editorial approvals, it validates the Methodology, Content, Question Bank and, when present, approved Flashcard YAML; emits typed Lesson/Question/Flashcard data, explicit Quiz selection, resource handoffs and an output manifest. The Builder never translates or creates Scene implementations.
9. [Implement Scene](./implement-scene.skill.md) — **Coding Agent Persona**, after approved Scene specifications and deterministic scaffold generation. Implements Scene behavior, source-language-only typed text, tests and lazy registry integration, without implementing the YAML Builder.
10. **Other subsequent stages, not automatically launched:** Media Production, Translation Production and publication; these depend on resolved requirements and independent approvals.

## Language and generation boundary

The canonical Screenwriter and Assessment Architect YAML plans each have **one** `documentLanguage`, included in its planned `supportedLanguages`. The [deterministic Lesson Builder](../../docs/architecture/lesson-yaml-builder.md) scaffolds file/folder structure and writes learner-facing source content **only in `documentLanguage`**, using the actual Lesson/Section/ContentBlock creator API where available. It must not invent values for missing locales or bypass TypeScript. Missing-locale TS errors during intermediate authoring are expected signals to the translator; publishing waits until actual supported-language coverage and normal checks pass.

Existing `content.md` files are legacy editorial materials. Do not duplicate competing canonical content sources or migrate them without explicit approval. `methodologist-brief.md` is the legacy Methodology filename and is retained in place when revising an existing Lesson.

## Approval and group-production handoffs

Review files are independent, source-revision-specific recommendations: a reviewer `pass` does not automatically give editorial approval. The Screenwriter revises `content.yaml` for accepted changes; affected reviews must be repeated against the new source. [Lesson Production lifecycle](../../docs/architecture/lesson-production-workflow.md) defines the per-Lesson approval and status model, while the GitHub Issue holds the batch's persistent cross-agent coordination. The Question bank and Flashcard YAML require **separate editorial sign-offs for their exact source revisions** before generation. A later material change to approved Questions requires rechecking dependent Flashcards and generated references. The Issue can contain many Lessons; do not create a new Issue or PR for every short step by default.

## Code-visible unfinished Scene work

Source `TODO(scene/asset/i18n/a11y/test)` comments remain beside real unresolved implementation paths and link the Lesson Production Issue. Remove each TODO in the fix that genuinely resolves and verifies it; do not drop unresolved blockers to claim completion. See [Implement Scene](./implement-scene.skill.md).

## Flashcard authoring — downstream of the approved Question bank

[Create Lesson Flashcards](./create-lesson-flashcards.skill.md) — **[Flashcard Learning Architect](../../personas/flashcard-learning-architect.persona.md)**. This is a separate, subsequently authorized authoring stage and a **hard downstream dependency** of the _approved_ full Question bank produced by [Create Lesson Questions](./create-lesson-questions.skill.md). Do not write Flashcards before that bank exists and is approved, regardless of whether the Lesson includes a built-in Quiz. If Question TypeScript exports are not ready, author approved YAML references but block their generated TS imports until the real exports exist.

It writes exactly one source-language `flashcards/flashcards.yaml` per Lesson, following [Lesson Flashcards schema](./lesson-flashcards.schema.json), with brief front/back/hint ContentBlocks, **typed list/warning/acronym/custom flags**, named TextBlock variables, mnemonic-construction metadata inside the acronym flag, Question-field references, and **nine canonical Flashcard relation types, authored once and mirrored onto both endpoint cards with actual IDs**. Runtime flags are discriminated objects, and UI Kit automatically maps them to localized MUI Chips (custom value, color and optional safe icon). Future generation must import matching Question objects rather than duplicating their localized fields; translations of locale-dependent custom labels and acronyms are still required. Typed relations and the Engine link materializer are already implemented; UI graph navigation/scheduling remains future work.
