# Create Lesson Brief — Methodology

**Persona:** [Methodologist](../../personas/methodist.persona.md). **Coordinator:** [Create Lesson Flow](./create-lesson-flow.skill.md), Stage 1. First inspect real Lesson UUID/workspace, approved Skill source/taxonomy, relevant subject reference and actual Lesson/Course evidence. Do not require an Issue, source file `methodology.md` or literal “Methodologist status: Approved” frontmatter as a new-work gate.

For a **Course-originated** Lesson first inspect verified Course PR slot and actual pre-authored Lesson methodology; assess its **completeness and adequacy**, reuse what is sound and repair omissions in the same Lesson `draft.ts` `production.methodology`. For a **standalone** Lesson, create substantive Methodology **from scratch** if none exists; otherwise inspect/reuse/improve what is already there. Existing methodology **alone never proves Course origin**.

Establish audience/entry knowledge, approved Skill UUID/source links, goals and observable outcomes, prerequisites and conceptual sequencing, scientific facts/sources, misconceptions, subject boundaries, depth and accessibility/offline needs. Distinguish actual `production.languages.document` from the nonempty planned `production.languages.planned`; source-only locales are authored now, not invented translations. Define explicit `assessmentPlan`: justified zero/one/multiple Quizzes with target Skills and canonical `AssessmentMethodKey` cognitive operations. Do not invent actual Questions, scoring, user-facing Section scenes, Course storyline, target translations or Runtime Props. Faithfully preserve any reviewed legacy methodology when explicitly migrating it.

Before recording Stage 1, make **all four** independent, explicit `LessonProductionAssessmentRequirements` decisions: `questionBankRequired`, `flashcardBankRequired`, `quizSectionRequired`, `flashcardsSectionRequired`. Bank necessity is distinct from Section necessity. Preserve the separate `config.params.quizRequiredForCompletion` runtime choice (if true, a completed Lesson must contain an enabled Quiz). Decide whether the completed Lesson needs one or more Quiz Sections and/or Flashcards Sections. Set every `production.assessment` boolean explicitly (no omitted decisions), and explain the educational rationale in `production.methodology`. Do not embed a `lesson-assessment-sections` fence or any mandatory assessment inventory. Define separate pedagogical intentions for multiple Sections in readable methodology prose. Independently authored Question/Flashcard banks do not automatically imply in-Lesson Sections; do not invent bank UUIDs, grading, or runtime defaults.

Record exact current SHA, quality findings, author and next handoff in **Lesson PR**. Stage 1 must `satisfies LessonWorkflowStage1` but intentionally cannot yet contain Sections or ContentBlocks; full structural validation belongs to Stage 6 only. Missing verified Skills, ambiguous audience/depth and unsupported subject claims block the stage; a missing artificial approval marker does not.

**Mandatory handoff gate:** use the [Lesson methodology completeness contract](../../docs/entities/lesson.md#lesson-methodology-completeness--pedagogical-technical-specification) to decide whether `production.methodology` is a usable technical pedagogical specification. An independently working Screenwriter must be able to author substantive learner-facing content and resource requirements without inventing educational objectives, definitions, misconceptions, example boundaries or assessment intent. If not, record precise blockers and revise Stage 1. No word/token quota and no duplicate `methodology.md`/`content.yaml` as a new source.

## Detailed methodological quality checks

Consult `assessment-methods/<language>.md` in the verified one-day Actions ZIP when available, choosing the learner's frontend language for short labels. The extended explanations remain **English**. The reference lists all canonical Assessment Methods and distinguishes the **cognitive operation assessed** from a **Question UI type**; it is a read-only convenience view, not a replacement for Assessment Method identifiers in Engine. If absent, inspect the canonical Engine schemas, English Engine methodology and UI Kit translations instead of making up methods or assuming defaults.

In `production.methodology`, decide whether this Lesson needs any **Quiz Sections**, based on the intended Skills, observable outcomes and the kind of evidence necessary to evaluate them. When justified, describe which canonical `AssessmentMethodKey` values would elicit that evidence for each targeted Skill/outcome and why distinct Methods are needed; do not mechanically assign one method per Skill or mandate a Quiz in every Lesson. This is an **assessment intent and handoff**, not an implementation of Questions, UI interaction formats, scoring, mastery thresholds or retries. The Learning Assessment Architect owns those decisions.

1. **Inspect before authoring.** Resolve the textbook path, existing Lesson directory/Methodologist Brief (if any), generated taxonomy descriptions, approved unpromoted staging entries when applicable, relevant references and actual implementation only if needed to validate the Code link. Preserve all existing unrelated specialist files.
2. **Establish the pedagogical contract.** Describe the desired conceptual change, observable outcomes, prior knowledge, prerequisite gaps, depth appropriate to the audience, and why the selected Skills belong together. Distinguish teaching a Skill from assessing its mastery.
3. **Specify the subject matter.** Identify essential facts, concepts, mechanisms, relationships, terminology, valid examples or counterexamples, common misconceptions, and hard exclusions. Include enough accurate substance for the Educational Screenwriter to work without inventing facts or objectives; do not write a Section-by-Section instructional plan.
4. **Design the learning progression conceptually.** Identify conceptual dependencies and the necessary transition from known to new material. Suggest appropriate kinds of understanding and transfer, without prescribing general Section count, UI widgets, concrete Questions, scoring, gamification or narrative.
   4a. **Define the Lesson assessment contract.** Make a positive decision about Quiz necessity: `assessmentPlan.quizRequired: false` with `quizzes: []`, or `true` with one or more distinct Quiz requirements, each with a stable `key`, pedagogical `purpose`, target Skill UUIDs and a non-empty list of typed `requiredAssessmentMethods`. Use exact `AssessmentMethodKey` strings (e.g. `retrieval`, `interpretation`, `application`), not method UUIDs or UI Question types. An Assessment Method specifies the **cognitive operation to assess**, not how the learner inputs an answer. A required Quiz must be justified by its assessment purpose; never add one by default. You may require several distinct Quizzes. Do **not** choose actual questions, correct answers, distractors, scoring thresholds, retries, Quiz UI layout or Section implementation details; delegate those to the appropriate specialists.
5. **Check scope and independence.** One Lesson may target multiple Skills when they form a coherent learning objective; if it becomes an entire course, propose a split for editor approval rather than silently splitting, merging, adding or renaming Skills. No grade ceilings or instructional modes may be written back into the taxonomy.
6. **Honor cross-cutting constraints.** Specify localization-sensitive terms and examples, disability-aware alternatives the experience must enable, offline completeness and low-device pedagogical equivalence. Note factual uncertainty and sources. Do not invent runtime APIs, Note events or assessment guarantees.
7. **Escalate conflicts.** The Methodologist Persona's mandatory Skill-versus-Question and disciplinary ownership gates still apply. Report specific choices in the editor handoff and do not alter approved taxonomy identities or another specialist's approved section.

## Methodology quality checklist (retained specialist standards)

1. **Scope and identity:** confirm textbook workspace, immutable Lesson ID, actual Skill source links, package boundaries, audience and subject. One Lesson may teach multiple related Skills; split an incoherent course-sized scope only with owner approval. A Course slot is compatibility evidence, not ownership of the Lesson.
2. **Prior knowledge and outcome evidence:** distinguish learner _exposure_, _practice_ and _demonstrated mastery_. Describe the conceptual change, observable outcomes, expected entry knowledge, likely prerequisite gaps and misconception boundaries. State supported simplifications and claims requiring sources; do not invent standards alignment.
3. **Assessment intent:** for each justified Quiz, define a stable key, purpose, exact assessed Skill IDs and a nonempty list of real `AssessmentMethodKey` values describing cognitive operations. Distinguish these keys from Question types and UI widgets. Explicitly record a justified no-Quiz choice where appropriate; no fixed Quiz count. Do **not** choose actual Questions, correct answers, distractors, scoring, retry limits or layout — those belong to Assessment Architect and the independent Questions Flow.
4. **Learner access:** record language intent (source and all targets), terminology/cultural constraints, accessible representations, offline/weak-device needs and legitimate media restrictions. Do not make a pending Scene/asset seem already available.
5. **Evidence and decision trail:** verify source facts against relevant canonical material, capture unresolved editorial decisions and handoff details in the Lesson PR at an exact source SHA. Substantive later changes to intended Skills, outcomes or assessment intent require a new Methodologist review; they cannot inherit an unrelated approval.

Where legacy approved Methodologist text has a meaningful existing evidence structure, preserve its prose and methodology rationale when moving into the typed Lesson `draft.ts` `production.methodology`. No new mandatory frontmatter or duplicated ongoing `methodology.md` source is created before Stage 6.

**Typed handoff:** export the UUID-addressed single source object with `satisfies LessonWorkflowStage1`. For a new Course-originated Lesson, preserve the reviewed `CourseWorkflowStage3NewLesson` methodology, objective/depth/sequence/assessment evidence, all four assessment decisions, verified Skills, and Course source/planned languages in exactly the approved initial `draft.ts` (no `defineLesson`, Sections, Question IDs, or bank instances). Source verification and pedagogical completeness remain separate from compiler success; record the Stage 1 source SHA in the Lesson PR.
