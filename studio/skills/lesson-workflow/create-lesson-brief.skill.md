# Create Lesson Brief — Methodology

**Persona:** [Methodologist](../../personas/methodist.persona.md). **Coordinator:** [Create Lesson Flow](./create-lesson-flow.skill.md), Stage 1. First inspect real Lesson UUID/workspace, approved Skill source/taxonomy, relevant subject reference and actual Lesson/Course evidence. Do not require an Issue, source file `methodology.md` or literal “Methodologist status: Approved” frontmatter as a new-work gate.

For a **Course-originated** Lesson first inspect verified Course PR slot and actual pre-authored Lesson methodology; assess its **completeness and adequacy**, reuse what is sound and repair omissions in the same `lesson.yaml` `production.methodology`. For a **standalone** Lesson, create substantive Methodology **from scratch** if none exists; otherwise inspect/reuse/improve what is already there. Existing methodology **alone never proves Course origin**.

Establish audience/entry knowledge, approved Skill UUID/source links, goals and observable outcomes, prerequisites and conceptual sequencing, scientific facts/sources, misconceptions, subject boundaries, depth and accessibility/offline needs. Distinguish `production.documentLanguage` from the full planned `config.params.languages`. Define explicit `assessmentPlan`: justified zero/one/multiple Quizzes with target Skills and canonical `AssessmentMethodKey` cognitive operations. Do not invent actual Questions, scoring, user-facing Section scenes, Course storyline, target translations or Runtime Props. Faithfully preserve any reviewed legacy methodology when explicitly migrating it.

Record exact current SHA, quality findings, author and next handoff in **Lesson PR**. Stage 1 may have an incomplete Engine Config tree; full structural validation belongs to Stage 6 only. Missing verified Skills, ambiguous audience/depth and unsupported subject claims block the stage; a missing artificial approval marker does not.
