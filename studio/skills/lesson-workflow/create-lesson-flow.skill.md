# Create Lesson Flow

**Generated-source blocker semantics:** Follow the [Coding Agent's actionable TODO contract](../../personas/coding-agent.persona.md#actionable-generated-source-blockers): a `TODO (BLOCKER):` must explain the real implementation and removal criterion; keep a reviewed temporary brief in **one** safe multiline comment rather than a detached specification. Preserve all unfinished publication blockers, independent approvals and the entity-owned source of truth. This is guidance for materialized technical scaffolds, not permission to complete a workflow stage.

**Stage 6.1 trusted handoff:** The final reviewed `draft.ts` is one inert default-exported object with `satisfies LessonWorkflowStage2`; it contains no `materializeLessonStage6()` invocation, runtime imports, spread expressions or executable content. After separate authorization, the existing `/lesson materialize` PR command reads the exact pinned bytes through the shared static Draft Reader, validates the canonical Stage 2 Zod contract and invokes the concrete Lesson source materializer in trusted code. TypeScript shape checks alone are not a sandbox, and source materialization is not resource, Scene, bank, locale or release completion. See [declarative source architecture](../../docs/architecture/typed-production-materialization.md).

**Authority:** the primary Git-first, staged TypeScript workflow for one standalone or Course-originated Lesson. One **Draft Lesson PR** is the sole canonical progress tracker; Git owns authored files and independent reviewer evidence. Do not introduce workflow status to Engine Config/Props or preserve competing Issue/YAML progress trackers. Before every action read root `AGENTS.md` and `README.md`, the applicable Studio rules, Persona(s), Skill(s), architecture/entity docs and current code/tests.

## Typed authoring contract and rollout boundary

The **single editable Lesson planning source** is `draft.ts` exporting one evolving object. Stage 1: `satisfies LessonWorkflowStage1`; Stage 2: extend the **same object** with ordered Sections/ContentBlocks and use `satisfies LessonWorkflowStage2`. Stages 3, 4 and 5 correct and audit the exact same Stage 2 source; there is **no Stage 3/4/5 authoring type or second document**. At Stage 5 handoff the reviewed object must `satisfies LessonWorkflowStage2` and have verified source/review SHAs. All types are defined in `shared/engine/types/workflow/lessonWorkflow.types.ts`. TypeScript catches missing required structural decisions; it does **not** verify real UUIDs, factual correctness, locale coverage, bank ownership or review evidence.

`config` holds actual Lesson Config identity, Skills, source title and mandatory Methodologist decision `params.quizRequiredForCompletion`; optional Section navigation, skipping and index visibility may be specified throughout Stages 1–5. Stage 6.1 defaults only omitted `sections.allowNavigation`, `sections.allowSkipping` and `sections.showIndexes` to `true`, preserving explicit values; `production` holds source language, planned language scope, methodology and independent bank/Section assessment decisions. `production.languages.document` is the **actual** authored source locale; `production.languages.planned` is a nonempty target plan. Never add `config.params.languages` to a Stage 1–5 authoring object or invent target translations. Only full Lesson materialization produces the final Engine Config `params.languages`. An authored Section/ContentBlock is a plain `{ config, production? }` node with root `children` and direct slug-keyed child collections, not a Configurator or a published Props fragment.

Course Stage 5 may emit a UUID-addressed `draft.ts satisfies CourseWorkflowLessonSeed` with substantive methodology, Skill IDs, intended outcomes, assessment intent and Course-derived language context. This is one possible editorial input, not a Lesson Stage 1 deliverable. An operator's brief in conversation or other authorized material is equally valid; no Course origin, parent PR or programmatic conversion is required. During authorized Lesson Stage 1, assess completeness, reuse adequate substance, resolve real gaps with the operator and replace/complete the seed at the same path with `satisfies LessonWorkflowStage1`. Preserve allocated identity and placement references. Course and Lesson authoring contracts are independent.

**Trusted materialization:** use the [Lesson Stage 6.1 runbook](../../../scripts/ci/lessonMaterialization/README.md). Verify the workflow on the default branch and obtain explicit invocation authorization before invoking `/lesson materialize`. The command requires a valid typed object at one unambiguous canonical changed draft path, not a parsed checklist, review or Course-parent record. A Draft check or local source parse is not completion.

## 0. Resolve identity, provenance, and current state

- **Resume by PR:** fetch the latest PR body, head/base SHA, comments/reviews, statuses, all child PRs and canonical Lesson files. Reconcile source and verified approvals. A bare PR number requests a stage report and next-action proposal only; execute the first authorized unfinished stage **after** a separate, clear user instruction. Never duplicate the PR or rely on a prior chat.
- **Resume by UUID:** use Engine's UUID resolver for `content/<book>/data/lessons/<bucket>/<uuid>/`; search active and historical PRs, old Lesson Production Issues, Course associations and real files. Reuse existing identity/branch/PR. Missing languages on an implemented Lesson require localization, not a new Lesson.
- **Course-originated:** before starting **or continuing** Lesson Production, the Coding Agent must inspect the actual Course PR, the **SHA-pinned Course Stage 5 Actions summary**, the committed Course composition/methodology, and the canonical Lesson `draft.ts` (which may still hold the Course seed). Verify the exact Course UUID, Course slot, assigned Lesson UUID and source SHA directly against those artifacts; never infer membership from a matching slug/title or invent a second registry. Record the verified Course/Lesson relationship in the Lesson PR. A new Lesson PR targets the parent Course PR's **actual integration branch** and includes `<!-- svitlo-course-lesson:v1 -->` with literal `Course: <uuid>`, `Lesson: <uuid>`, `Parent PR: #N` on separate lines. This linkage is editorial coordination only; the trusted `/lesson materialize` command does not parse it or query the Course PR. Lesson workflow progress and evidence remain in the Lesson PR.
- **Standalone:** if authorized and truly absent, allocate one immutable UUID/slug and open one new Draft Lesson PR targeting `develop` or the designated integration parent. If existing material already exists, inspect it first. The presence of methodology alone **does not** imply Course provenance.
- **Historical Issues:** read and preserve their full evidence, approvals and links, but **do not create mandatory new Lesson Production Issues**. Map each distinct UUID to its actual Lesson PR. For **new** Lesson translation/review Stages 9/10, use that existing Lesson PR without a separate Translation Production Issue or additional translator/reviewer PR. Historic translation PRs/Issues remain recoverable.

An **instructional** Lesson remains Course-neutral and reusable. An explicitly approved **assessment-only** Lesson may require preceding Course Lessons' Skills and Question Banks, as specified in its Course-originated methodology; it is still an ordinary `defineLesson` and must **not** embed a Course UUID, storyline, mascot, plot, new Runtime subtype or `dependsOn` field in Engine Config/Props. Preserve Course origin and upstream dependencies in the existing Course plan and PR tracker. Use repository naming/labels: a Lesson PR subordinated to a Course uses `pr: agent-subtask`; a standalone Lesson coordinating child bank PRs can use `pr: integration`. Both roles are **never assigned together**: even if a Course's Lesson PR receives Question/Flashcard children, its `pr: agent-subtask` role is retained and real nested ancestry gives context. All agent PRs start Draft.

## Mandatory user-facing progress report and next-action handoff

After **every completed or paused stage**, at a review/authorization blocker and on every status/resume request (including a new chat containing only a Lesson PR number), first reconcile the current Lesson PR head/base, immutable UUID, source files, stage checklist, independent reviewer/source SHAs and child PRs. A bare PR number asks for **status plus recommendation**, not immediate stage execution or a new PR. Do not treat a checked box alone, a source-only scaffold or a previous chat as proof of completion. The PR description remains the sole workflow tracker; **no** stage/status fields belong in TypeScript production data, Engine Config/Props or a parallel ledger.

Always finish with a compact, explicit report containing:

1. **Lesson identity**: exact Lesson UUID, verified Lesson PR and, if Course-originated, the Course parent PR/UUID and verified `svitlo-course-lesson:v1` linkage; source/head SHA when available.
2. **All ten Lesson stages in order**, marking each `✅ completed`, `▶ in progress`, `⬜ not started`, `⛔ blocked`, or `↻ stale`. Under Stage 6, report **each of its three independently checked substeps** with evidence. Stages 7/8 are Questions/Flashcards with child PR or justified N/A status, including review/integration evidence; show their child seven-stage workflows separately. Show locale coverage under Stages 9/10. A `✅` requires verified deliverables at pinned source/review SHAs, not a checkbox alone.
3. **Last completed stage**: explicitly `Stage N — <name> completed` with verified evidence (or `No new stage completed`), plus blockers/stale reviews.
4. **Recommended next stage**: the first authorized eligible incomplete stage, with its prerequisite, or `None — all ten Lesson stages are complete`.
5. **Recommended next action**: a single concrete copyable **chat instruction** on its own fenced `text` line, e.g. `do lesson stage 2 for PR #<lesson-pr-number>`. When starting an independently authorized, materialized Course Lesson that has no Lesson PR yet, use **exactly** `do lesson <verified-lesson-uuid> related to PR #<course-pr-number>` and resolve/reuse the existing Course parent integration branch; do not create a duplicate PR. For a standalone Lesson, identify its UUID and actual intended base branch. The command is a recommendation, **not** something to execute as a side effect of reporting. Invite the user to send it, or reply `go` to an unambiguous single proposal made in this chat; other clear instructions work too. Vague `go` without a concrete current target and a bare PR number cannot cross the separately scoped Lesson-authorization boundary.

Only recommend an action justified by verified sources and current approval/branch boundaries. If Stage 3 requires the separate independent-review chat, or a stage needs an owner decision, Questions/Flashcards completion or upstream published banks, state the blocker and propose the appropriate **authorized** handoff. Stages 4–5 may continue in the Stage 3 chat; do not require another independent agent or chat for them. Keep the PR progress checklist current when performing authorized work, but preserve concurrent edits and exact evidence. A Course Stage 5 materialization is **not** Lesson Stage 1 completion or a Lesson Production PR.

**Terminal message:** when **all ten Lesson stages** are individually complete at current evidence SHAs, explicitly say: **"All ten Lesson workflow stages are complete. There is no next Lesson stage. You can assign new work."** Stop rather than continuing without instruction. Stage 6 completion now requires implemented, registered and tested Scenes, not only their Config drafts. Report remaining full-locale publication, final QA, CI or merge gates separately; these are **not extra stages**, and workflow completion never authorizes Ready/merge.

### Assessment Section decisions and independent bank handoff

Stage 1 Methodologist fills **all four** mandatory `production.assessment` booleans: `questionBankRequired`, `flashcardBankRequired`, `quizSectionRequired`, `flashcardsSectionRequired`. They are independent: the Lesson can require its own Question Bank without a Quiz Section, a Quiz can select Questions from verified upstream banks, and the existence of either bank does not automatically create a Section. State the pedagogical rationale, target Skills and intended `AssessmentMethodSlug` cognitive operations in the substantive `production.methodology`; do not author bank members, answers, grading or fake UUIDs. `config.params.quizRequiredForCompletion` is a **different mandatory Stage 1 Methodologist decision**, with no default; when true, final materialization must have an **enabled** Quiz Section. A disabled Quiz or an empty selection does not satisfy it.

Stages 2–5 review each approved assessment Section in the normal root `config.children` plus direct Section placement tree. Its `config.params` may remain **partial** pending independent bank decisions. Preserve authored Section identity, source copy, position and specifications; leave unavailable selections absent instead of inventing real or reserved Question/Flashcard IDs at editorial stages. Stage 5 verifies that every required Section intent is represented, or documents a precise blocker to be resolved before Stage 6.

Stage 6.1 must first verify that every required Quiz/Flashcards Section is **present and enabled** in the Stage 2 root `config.children` plus direct Section placements; `quizRequiredForCompletion: true` likewise requires an enabled Quiz. The `materializeLesson` **throws before generating files** for a missing/disabled required Section; a `TODO (BLOCKER)` comment or automatic disabled/empty Section is not a substitute. For an already-authored enabled Section with incomplete selection/config parameters, the concrete Quiz/Flashcards Section renderer can emit a visibly **nonpublishable** source draft with diagnostics; this does not prove Engine Config completeness, generated TypeScript compilation, or Stage 6.2/production readiness. The orchestrator must derive/check `params.languages`, bridge Stage 2 plain `{config,production?}` children to the completed `Lesson_Config` expected by `materializeLesson`, and consume the reviewed `draft.ts` and create the renderer's output `index.ts` atomically, with exact Git commit/blob provenance. At publication, invoke the real `assertLessonSourceReleaseReady` gate **and** validate reviewed bank UUID ownership, complete selections, locales and final Build/Props; this release helper exists but is **not yet wired** into the parent publisher. Do not fabricate reserved references, grades, translations or missing pedagogy. Independently owned Questions/Flashcards workflows supply selections only after review/integration; never create a second YAML `sectionDrafts` editable source or call legacy `/lesson finalize` on the typed Lesson.

### Stage 7/8 independent child-bank handoff

**Questions and Flashcards are separate parent Lesson Stages 7 and 8**, while each actual bank is authored, independently reviewed, translated and materialized in its own seven-stage child Draft PR. These are not part of Stage 6. The parent tracks the two stage checkboxes and child PR/source/review/integration evidence; child PRs retain their own stage checklists. Only propose bank work after verified typed Lesson sources and current derived `methodology.md` and source references exist.

- **Stage 7 — Questions:** verify whether an own bank is required even when there is no Quiz. Reuse the matching child PR and propose `do questions stage <next> for PR #<questions-pr>`, or propose `do questions for lesson <lesson-uuid> related to PR #<lesson-pr>` when none exists. The user may use the command **in this chat or a new chat**. Do not create a child PR without explicit authorization. Check parent Stage 7 only after all seven Questions stages, review and actual integration, or an evidence-backed Methodologist own-bank N/A; an unfinished bank is not N/A.
- **Assessment-only Lesson:** own Questions can be N/A with documented Methodologist rationale and verified upstream bank ownership, but unresolved external Question/Quiz selection remains an explicit downstream blocker with PR/SHA/locale evidence; do not invent an empty bank or treat absent Quiz as N/A.
- **Stage 8 — Flashcards:** after verified Questions completion/integration or legitimate own-bank N/A, reuse an existing child PR and propose `do flashcards stage <next> for PR #<flashcards-pr>`, or propose `do flashcards for lesson <lesson-uuid> related to PR #<lesson-pr>` when pedagogically required and missing. The same chat or a new chat is allowed. Check Stage 8 after all seven child stages and actual integration, or documented Methodologist Flashcards N/A. An existing Questions bank does not make Flashcards mandatory.
- **Pause/handoff:** report the actual child PR and next eligible action, and offer **one** copyable chat command; never start child authoring, review, merge or source replacement implicitly. After Stage 8, recommend Stage 9 Translation.

**Authoring validation boundary:** During Stages 1–5 use `satisfies LessonWorkflowStage1` / `satisfies LessonWorkflowStage2` and the actual Engine contracts, while separately requiring semantic approvals and pinned source SHAs. CI owns normal typechecking; follow the Draft/Ready lifecycle and react to actual current-head results instead of imposing an additional per-stage manual typecheck. The final reviewed source must satisfy `LessonWorkflowStage2`, but **passing TypeScript is neither source validation nor review approval**. Stage 6.1 must use the tested typed source materializers, not the historical YAML builder/finalizer. The Stage 6.2/6.3 checks verify complete Engine Config, actual resources and executable Scenes.

### Stage 6.2 — Direct Skill references in authored Lessons

Every Lesson defines its **own** `skills` array by referencing verified, standalone Skill definitions (`skill.id`, the canonical immutable Skill UUID), or verified Skill UUIDs during editorial TypeScript planning. **Never derive or copy the Skills array from another Lesson's Config**, even if the Lessons teach identical Skills; this rule also applies to Playground fixtures. Reusing the same canonical Skill definition is correct; depending on another Lesson's `skills` property is not.

- **Correct:** `skills: [testExplainLightTravel.id]` (a direct import of that Skill definition).
- **Incorrect:** `skills: otherLesson.config.base.skills` (a dependency on another Lesson rather than the Skill source).

The reviewed Stage 1 object supplies actual verified Skill UUIDs: preserve the same identity and import direct Skill definitions where possible when materializing the Lesson. If an existing Lesson uses the same Skill, import the **Skill definition itself**, not the other Lesson's `config.base.skills`. Legitimate reuse of Sections or other Lesson-owned resources does not change this rule for the Lesson's Skills metadata.

This is an **authoring instruction**, not a request for regex/AST/ESLint validation or migration of existing content. It does not prohibit intentional cross-Lesson Question Bank references.

## Stage 6 resource and Scene blockers

**Stage 6 owns completing generated Lesson resources and implementing all required Scenes.** Track each physical illustration/audio/video/3D, transcript and Scene with its exact Section/Block/asset identity, approved specification, responsible agent/specialist, status and verification SHA in the parent Lesson PR. In 6.2, resolve generated code/type errors and necessary media references through verified real resources; do not remove `TODO(asset)` or Nil UUID placeholders to fabricate progress. In 6.3, actually implement, test and register Scenes using [Implement Scene](./implement-scene.skill.md); an unimplemented Scene is a **Stage 6.3 blocker**, not an optional Final QA handoff. Missing essential media and equivalent accessibility/offline paths block the affected completion checkbox. Final QA independently validates deployed/runtime behavior and required locales; Stage 6 source-level checks alone do not prove release readiness.

### ContentBlock production briefs

Stage 2 Screenwriting must author Text, Markdown, Code and Checkpoint question/answer text **as final content** in Config/locale or source code. Do not write or materialize separate `specification.md` for these blocks. A new Image must carry a substantive, concrete `production.prompt` describing the exact visible composition and its instructional relationships so an asset producer can generate it directly; generic “create an accessible diagram” intent is not enough. Video/Audio/Subtitles should retain only the scripts, storyboard or production content genuinely necessary to make the media. Global accessibility, offline, weak-device requirements and readiness statuses are mandatory workflow and publication checks, **not per-media `production` boilerplate**. The renderer preserves unfinished media input in one removable source comment, and the true missing-asset/alt/caption/review blockers remain enforced.

## Single authoring source

Stages 1–5 edit **one** `draft.ts` object at the canonical Lesson UUID address (`content/<book>/data/lessons/<bucket>/<uuid>/draft.ts`). The root is `{ config, production }`. Stage 1 owns Lesson immutable ID, type, slug, verified Skill UUIDs, source title, mandatory explicit quiz completion policy and optional audience/Section Config parameters, and `production` methodology/language/assessment decisions. No Section or ContentBlock Configurator can be passed here, and no new user-facing content is generated by the Course handoff. Stage 2 adds root `config.children` and direct Section placement keys with actual typed, source-language `{config,production?}` child trees, stable reviewed identities and explicit Scene/media/Quest production specifications. Ordered collections use direct slug keys and explicit `children` order, not positional arrays or nested Configurator instances. Quest Stage/Task maps keep their own Engine-required keys and are **not yet runtime-publishable**.

Actual source-language localized fields belong to `config.locale` or nested node locales; future planned languages in `production.languages.planned` are **not** fabricated strings. At Stage 6 the materializer derives `config.params.languages` from the reviewed plan while preserving the actual effective Course subset at publication; translation follows on real materialized source in Stages 9/10. Never infer progress from `draft`, `approved`, `stage` or `reviewStatus` keys in the object. Record review/authorization state only in the Lesson PR, with source commit/blob SHAs.

Any approved legacy `lesson.yaml`, `content.yaml`, `methodology.md` or reviewer evidence requires an **explicit non-destructive migration** with byte preservation/provenance; the old files remain historical inputs until verified transfer. Existing Questions/Flashcards YAML is historical bank provenance; its independent owner must authorize and verify any non-destructive transfer into the typed bank source. It is not an active production workflow. Do not create a duplicate editable Lesson `lesson.yaml`, methodology file or progress ledger.

## Lesson editorial review continuity: one independent entry, immediate role-owned fixes

**Independence boundary:** Stages 1 (Methodologist) and 2 (Screenwriter) may share their authoring context. **Stage 3 follows the [independent review rule](../../rules/independent-review.md) with a qualified Content Reviewer.** Read the actual complete canonical Lesson TypeScript object, methodology, prior evidence and current Git/PR state; the new chat is not a substitute for source inspection. This is the **only mandatory independent chat handoff in Lesson Stages 3–5**. Stages 4 (Learning Experience Expert) and 5 (Methodologist compliance) run as distinct, evidence-producing **specialist audits in that same Stage 3 chat**, with explicit persona switches and their own criteria, not new independent-review assignments. Do not call Stages 4 or 5 independent approvals. Stage 10 translation review and independent bank reviews retain their own independence gates.

**Review-and-repair in the current stage:** A clear request to execute Stage 3, 4 or 5 authorizes that stage's reviewer/specialist to **record findings and immediately correct actionable, in-scope defects in the same canonical `draft.ts` and PR branch** rather than merely asking the Stage 2 Screenwriter to fix every finding. First inspect and pin the unmodified baseline commit and TypeScript source **blob SHA**, then record each finding's stable ID, node path, severity, evidence and proposed repair in the existing Lesson PR tracker. Before any edit, identify the accountable persona and stay within its competence: Stage 3's independent Content Reviewer can act as the qualified editorial Screenwriter for bounded content fixes; Stage 4's Learning Experience Expert can directly repair presentation, accessibility, pacing, feedback and Scene/media **experience specifications** within approved content/methodology; Stage 5's Methodologist can directly repair compliance wording, mapping and evidence within the already-approved educational scope. When a fix crosses roles, **explicitly switch to the appropriate authoring persona within this same review chat**, document which role authored each change, and apply that persona's Skill and constraints. Never conceal authoring as a read-only review or call correction work a second independent sign-off.

**Verification and SHA accounting:** Record each final Stage 3, 4 and 5 verdict and the actual reviewed commit/blob SHA in the PR description as readable editorial evidence; no prescribed machine-readable format is required. Commit source fixes, verify the changed nodes **and their dependent Sections/blocks within the active stage**, then complete that stage's own audit on its final source SHA. Record the original reviewed commit/blob SHA, correction commit/new blob SHA, findings-to-fixes mapping, commands actually run, remaining risks and **active-stage verdict on the resulting source blob** in the PR. Stage 3 independence is from the Stage 1–2 authors; disclose reviewer-authored corrections rather than implying a second independent sign-off. Stage 4 is a subsequent experience audit of its then-current source. **Stage 5 is the last editorial review and the final integrated acceptance of the complete latest TypeScript authoring object**. A later revision does not retroactively rewrite the earlier stage's review SHA or remove its completed status; the current downstream stage takes responsibility for evaluating the consequences of its own edits.

**Strictly forward-only Stage 3 → 4 → 5 → 6:** Stage 3 independently reviews the Stage 2 source and applies its own fixes. Stage 4 **consumes the completed Stage 3 review**, checks the current complete source, directly fixes experience defects and evaluates the effects of **its own changes as part of Stage 4**; it does not reopen Stage 3. **Stage 5 consumes BOTH completed Stage 3 Content Review and Stage 4 Learning Experience Review**, including their recorded findings, fixes and commit/blob SHAs. Stage 5 is the **final comprehensive editorial/methodological review**: examine every Section, ContentBlock, Scene/media specification and assessment intent against approved Stage 1 methodology; identify any remaining methodology or consistency defect; **make the authorized corrections directly; commit; verify the whole corrected lesson and the effect of those corrections on content and experience as part of Stage 5 itself**. Mark Stage 5 complete with its own final source blob SHA, then hand off **directly to Stage 6 Resource Production**. **Never route Stage 5 back to Stage 3, Stage 4 or Stage 2; never require re-approval/re-review of earlier completed stages because Stage 5 changed the TypeScript source.** Stage 3/4 checkboxes remain completed, each linked to the SHA it actually reviewed. Preserve the historical evidence rather than claiming the old reviews covered the final Stage 5 SHA; Stage 5's integrated verdict provides that final coverage.

**True authority blockers, not loops:** If an essential correction would redefine approved Stage 1 outcomes, prerequisite/Skill scope, Quiz/Flashcards Section intent, cognitive Assessment Methods, or Assessment Architect-owned Questions/scoring, record the exact blocked decision and obtain approval from its owner. Once resolved, **resume and finish Stage 5 itself** on the corrected TypeScript authoring object; do not send it backward to Stage 3/4. Missing approved decisions or inability to verify educational correctness block **Stage 5** without a false approval, but they do **not** create an independent-review cycle. Stage 6 verifies actual structural/technical readiness, not a new pedagogical review. Stage 10 and the independent Stage 7–8 bank reviews keep their own gates.

**Authorization and commands:** Stage 3's next-action command explicitly says **open a new chat**. After Stage 3, offer `do lesson stage 4 for PR #N` **in this same chat**; after Stage 4, offer `do lesson stage 5 for PR #N` **in this same chat**. After a successful Stage 5, **mark Stage 3, Stage 4 and Stage 5 completed in the existing PR tracker, retain their original SHA evidence, record the final Stage 5 TypeScript source SHA and hand off directly to `do lesson stage 6 for PR #N`**, which may be executed in the **same chat** if explicitly authorized. Never recommend Stage 3/4 as the next task from Stage 5, even when Stage 5 made corrections. An explicit instruction to execute multiple stages permits a forward-only continuous review/repair/handoff; a single-stage instruction alone does not silently authorize Stage 6. Preserve Lesson UUID, Course parent/branch and source-language copy. Do not merge, mark an **unfinished** Lesson PR Ready, create duplicate tracker files, fabricate runtime assets/translations/bank IDs or bypass Stage 6 checks. Once specifically authorized work is genuinely complete and reviewable, follow the [CI Draft → Ready policy](../../rules/ci-workflow.md), verify current-head checks and leave merge to the owner.

## Stages (record role, source SHA, evidence, verdict and next action after each)

### 1. Methodology

**Persona:** [Methodologist](../../personas/methodist.persona.md). **Skill:** [Create Lesson Brief](./create-lesson-brief.skill.md). Verify real Skill UUID/source links, learner audience/entry knowledge, prerequisites, aims, conceptual scope, source references, misconceptions, accuracy, desired depth, supported locales/accessibility and assessment intent including whether and why zero/one/multiple Quiz Sections are needed and required cognitive `AssessmentMethodSlug` values.

Use any authorized editorial input: a Course seed, operator brief in conversation, or other supplied work. Assess completeness and adequacy, including genuine assessment-only dependencies when applicable. Reuse sufficient substance, fill real gaps and resolve decisions with the operator; if no input exists, author methodology from scratch. Preserve any existing allocated UUID and replace/complete the canonical `draft.ts` in place. **Output of Stage 1 is `draft.ts satisfies LessonWorkflowStage1`**, not the Course seed; no parent PR or Course-specific contract is required. Do not require a storyboard or a literal `Methodologist status: Approved` frontmatter. Missing actual pedagogical substance or unverified Skills block stage; no extra progress property belongs in YAML. **Output:** complete pedagogical method and stage evidence in Lesson PR.

### 2. Content Creation

**Persona:** [Educational Screenwriter](../../personas/educational-screenwriter.persona.md). **Skill:** [Create Lesson Content](./create-lesson-content.skill.md). Enrich the **same** Lesson `draft.ts` Stage 1 object into `LessonWorkflowStage2` with ordered Sections/blocks; actual intelligible source-language explanations, examples/counterexamples, worked demonstrations, learner actions, meaningful feedback, misconceptions, transitions and reflections. Specify `production.purpose`/`pedagogicalIntent` and complete implementable `production.specification`/`prompt`/`script`/`storyboard` for Scenes, media and any Quest, with accessibility, offline and weak-device equivalents. Follow real registered Config and renderer support; draft-only features are not shipped. No arbitrary minimum block counts, fake locales or Quiz answer banks. One short passive Text-only Section is a review warning, not an automatic schema failure. **Output:** full instructional blueprint, or for an approved assessment-only Lesson a complete accessible Quiz/evidence experience without invented teaching material, and production requirements in Git with Screenwriter SHA/handoff; unresolved material gaps block.

### 3. Content Review

**Persona:** independent Content Reviewer (qualified Educational Screenwriter **other than the Stage 1–2 author**) in a **new chat**. **Skill:** [Review Lesson Content](./review-lesson-content.skill.md). Inspect every Section/ContentBlock, correctness, explanation depth, examples and common mistakes, age-appropriate terminology, transitions, feedback and accessibility of copy. Flag empty/filler/thin material and factual deficiencies without quotas. Pin baseline SHA and record node-specific findings before editing; **repair bounded editorial defects directly in the same chat**, switch explicitly to the Screenwriter role for authoring, commit and re-audit affected content against the corrected SHA. Mark complete only with full coverage and disclosed reviewer-authored repairs; escalate changes to approved learning/assessment scope. **Output:** genuinely independent Stage 3 entry, traceable corrections and final source-SHA verdict in PR; no YAML review field.

### 4. Experience Review

**Persona:** [Learning Experience Expert](../../personas/learning-experience-expert.persona.md), **same Stage 3 chat**, with an explicit specialist role switch; this is **not another independent reviewer gate**. **Skill:** [Review Lesson Experience](./review-lesson-experience.skill.md). Examine the complete current TypeScript authoring object and production specifications for purposeful interaction, pacing/cognitive load, feedback, keyboard/touch/screen reader/RTL/reduced motion, captions/nonvisual alternatives, offline and low-end devices; distinguish planned Scenes/Quest from implemented renderers. Record node-specific findings and baseline SHA, **fix actionable experience defects in scope immediately**, commit, verify their effects on content quality as part of Stage 4 (without reopening Stage 3), and record a final-source-SHA specialist verdict. **Output:** role-owned experience audit and repairs, blocked only for genuine unresolved design/authority dependencies.

### 5. Methodology Compliance

**Persona:** [Methodologist](../../personas/methodist.persona.md), **same Stage 3/4 chat**, now acting in a methodology-compliance role, **not a third independent review**. **Skill:** [Review Lesson Methodology](./review-lesson-methodology.skill.md). Compare every Section in the latest TypeScript authoring object, learner-facing explanation/example, misconception/feedback and complete Scene/image/audio/video/Quest specification against the verified Stage 1 scope, Skills, prerequisites, sources, accessibility and assessment intent. Verify actual Quiz intentions, not Assessment Architect-owned Questions. Verify Methodologist decisions about Quiz/Flashcards Section requirements against normal authored Sections and flag missing implementation work; verify that any intentionally incomplete assessment Sections are identified for the independent Stages 7–8. Read the completed Stage 3 Content Review and Stage 4 Experience Review findings and their original SHAs before auditing the **entire latest TypeScript authoring object**. Record coverage, node-specific findings and baseline SHA; **directly repair in-scope methodological and consistency defects**, commit and verify the whole corrected Lesson (including any content/experience consequences) **within Stage 5, without reopening Stage 3/4**. Learning-outcome or approved assessment/scope changes require the owner's decision; resume Stage 5 after resolution. Pending binary/locale is a production dependency, not a content defect. **Output:** final comprehensive pedagogical compliance verdict on the Stage 5 source blob SHA, completed Stage 3/4/5 checkboxes and direct Stage 6 handoff; no frontmatter token.

### 6. Resource Production — typed resources and Scenes

**Owner:** Coding Agent for 6.1–6.2, and Coding Agent acting as Scene Implementer for 6.3. **Skills/tools:** the trusted typed Lesson Stage 6.1 orchestrator/writer, the existing concrete [Lesson source materializer](../../../shared/engine/generators/materializers/lesson/README.md) (a pure renderer, **not** a runnable standalone CLI), [Implement Scene](./implement-scene.skill.md), and optionally the [React Scene draft scaffolder](../../../shared/engine/scripts/sceneScaffolding/README.md). Only [typed Lesson Materialization](../../../scripts/ci/lessonMaterialization/README.md) may be used for reviewed Stage 2 `draft.ts`. This is **one parent Lesson stage with three separately evidenced, ordered substeps**; no extra 6.4 or separate mandatory Scene stage. A Scene Config and a generated TSX scaffold alone never satisfy 6.3.

**6.1 Materialize Lesson sources.** Require successful Stage 1/2 authoring and completed Stages 3–5 reviewer/source SHA evidence on **the same final `draft.ts satisfies LessonWorkflowStage2` object**. Verify the actual Lesson identity, source language, Skill IDs and assessment intent. Course ancestry is not a technical prerequisite. Check the actual latest source blob SHA, never only an earlier review or unrelated CI result.

After verifying the trusted typed orchestrator on the default branch, authorize and run it on this reviewed input; inspect its **preflight/check/write** path security, create-only/no-clobber behavior, stable UUIDs and imports, correct child dispatch to the Section and ContentBlock concrete materializers, derived human-readable `methodology.md`, and real generated modular `defineLesson` source. Do not pass an incomplete Course Stage 1 file to a full Lesson materializer, invoke any retired YAML command, or claim that compiling an isolated source stub proves Engine type safety. Record the command/run, input and output SHAs, exactly generated files and excluded/blocked drafts.

Any incomplete Quiz/Flashcards Section is an explicitly **provisional, nonpublishable** Config with tracked Section identity and unresolved real bank references. If `quizRequiredForCompletion: true`, the intended Quiz Section must remain **enabled** even in a temporary blocked scaffold; neither a disabled Quiz nor a placeholder Question ID satisfies the production gate. Parent Stages 7/8 authorize independent bank Stage 1 `draft.ts` handoffs only, not automatic full Question/Flashcard materialization. No fake translations, answers, grade policy, assets or Scene React code are created by Stage 6.1. If no trusted typed pipeline is deployed yet, **6.1 remains blocked**, not completed by the old YAML job.

**6.2 Complete and validate generated Lesson resources.** Inspect **every** generated Lesson/Section/ContentBlock Config, Markdown/Code source, imports and required media reference; correct the generated drafts against the approved methodology and actual Engine Build API without changing entity IDs or inventing copy. Supply/coordinate the genuine required source-locale resources and their physical UUID-named files, accessible descriptions/transcripts and offline packaging when the Lesson depends on them. Keep any unavailable essential asset as an actionable blocker; do not replace missing assets with dummy files, Nil UUIDs, silent fallback or disabled functionality. Validate strict TypeScript for **all Lesson-owned generated .ts modules and their real imported contracts**, using the owning project's compiler settings (a strict scoped check is permitted only to isolate unrelated Course sibling failures; never omit changed files or weaken TypeScript). Run relevant source, generator and content checks; fix errors introduced by these resources. Audit source-level keyboard/nonvisual alternatives, RTL, reduced motion, focus, offline/fallback and low-end-device constraints as part of this step. Record the actual command, scope, exit status, resource inventory and SHA. **6.2 is not complete with unresolved in-scope TypeScript diagnostics or essential unproduced resources.** Missing planned target-language translations are owned by Stages 9/10: validate the real active source language rather than fabricating translations or declaring full-locale publication.

**6.3 Implement and integrate Scenes.** Resolve the complete inventory of Scene Config UUIDs in the Lesson (including nested Carousel/Quest Scene nodes). For every Scene, read the reviewed production specification embedded in the corresponding textbook-scoped generated Scene TSX draft (and trace it to the reviewed Stage 2 source), execute [Implement Scene](./implement-scene.skill.md), and **create executable React components**, not just Config modules or skeleton TSX. If the textbook lacks Scene-capable TSX, renderer wiring, `./scenes` export, registry generator, dependencies or tests (for example an existing Skills-only textbook), first arrange/implement the required package-owned capability and do not mark 6.3 complete while it is absent. The opt-in Scene scaffolder can create **create-only drafts** after those prerequisites exist; it neither registers nor implements Scenes. Match immutable Scene UUIDs, type the source-locale `locales` contract, implement all approved learner interactions and accessible states, handle semantic RTL/reduced motion/offline behavior, and deliver or block on required media. Run co-located substantive Scene tests, TypeScript, registry generation/check, actual loader-to-Scene resolution, focused accessibility/interaction checks and any affected package build. Record component/test/registry paths, exact commands, outcomes and implementation/review SHAs. **Complete only after every required Scene is implemented, registered and tested**; an essential missing Scene/interaction/asset is a blocker, not a passing TODO. If the reviewed Lesson has genuinely **zero Scenes**, record the verified zero-Scene inventory and mark 6.3 **N/A** (not a silently skipped required check).

**Stage 6 completion:** Close 6.1 → 6.2 → 6.3 with real evidence in the same Lesson Draft PR, then check the parent Stage 6. A subsequent source change requires revalidating the affected checks. Questions/Flashcards still belong to Stages 7/8, translations to 9/10; no competing bank/media approval is fabricated. Accessibility and offline **source and Scene implementation** checks are included in 6.2/6.3 rather than separate source-only stages, while real complete-locale publication and runtime offline/a11y acceptance remain Final QA gates. If Scene work is delegated to child Draft PRs, Stage 6.3 is complete only after reviewed work is integrated into the same Lesson branch and validated. Do not call Stage 6 complete when only typed Configs exist.

## Independent bank workflow evidence

Questions and Flashcards are **parent Lesson Stages 7/8**, with independent seven-stage child PRs and their own responsible specialists. The parent owns each stage checkbox, child PR/source/review/integration evidence or explicit Methodologist N/A rationale. A substantive teaching Lesson normally needs a full Question Bank even without a Quiz. Questions must be completed, reviewed and integrated before Flashcards, unless own Questions are verified N/A; missing/unfinished Questions and no Quiz are never N/A. An assessment-only Lesson with N/A own Questions still tracks the reviewed external banks and Quiz dependencies. The seven-stage [Questions Flow](./create-questions-flow.skill.md) and [Flashcards Flow](./create-flashcards-flow.skill.md) continue independently. Preserve their existing source ownership and phased typed migration; do not embed banks into Lesson Config, create them during Stage 6 or substitute parent checkboxes for child evidence.

### Assessment-only Lesson upstream dependencies

An assessment-only Lesson Production PR is opened **only when that exact Lesson is separately authorized**, and for Course-originated work retains its existing `svitlo-course-lesson:v1` identity marker and real parent Course integration branch. Before selecting or finalizing Quiz candidates, the Lesson agent must:

1. Read the approved Course Stage 3 typed source revision (or its Stage 5 materialized Course sources/methodology), resolve the exact **upstream Lesson slot keys, UUIDs, Skills and intended Question Bank owners**, and record the Course review SHA. Never infer dependency edges from titles or create additional Engine fields.
2. Record **each upstream Lesson PR, Question Bank child PR URL, head/source and independent review SHA, actual target/base branch, merge/integration status and required locales** in this Lesson PR. If a branch/PR does not yet exist, record that as a dependency, not as an invented ID or approval. The upstream Lessons are allowed to contain their own Questions with **no Quiz Section**.
3. Verify that each required bank was authored and independently reviewed, is **actually present in the assessment Lesson branch ancestry**, and that its Questions have been published with the expected owning Lesson UUID and complete selected resource/locale files. A successful GitHub check on an unmerged child branch is not integration. When bank selection spans Lessons, the global UUID resolver and locale/build gates from [PR #668](https://github.com/KiT-Maverik/svitlo/pull/668) must be integrated and **verified**, not merely described in a Draft PR.
4. Until all gates are satisfied, leave final `params.selection.questionIds`, Quiz resource validation and publication **blocked** with the precise missing owner/PR/SHA/locale. Independent methodology/content work may continue if it does not falsify a completed Quiz; the earlier Course Stage 4 methodology approval is unaffected. If the actual `defineQuizSection` requires nonempty UUIDs, leave the authored Quiz config as an explicitly incomplete draft rather than fabricating placeholders or claiming the Lesson builds.
5. Only the Assessment Architect approves the small deliberate Question UUID candidate set and scoring/coverage; the Section owner changes only the approved Quiz Section. Validate actual IDs, ownership, availability per requested locale and real rendered loading/build results, retaining the complete upstream banks unchanged.

This is a **downstream-only dependency**: never block or rewrite a source Lesson's own valid bank production because the Course assessment Lesson is pending. No new Lesson status file, approval YAML or Runtime dependency resolver is part of this policy.
