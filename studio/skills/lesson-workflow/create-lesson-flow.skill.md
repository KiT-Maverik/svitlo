# Create Lesson Flow

**Authority:** the primary Git-first workflow for one standalone or Course-originated Lesson. One **Draft Lesson PR** is the sole canonical progress tracker; Git owns authored files and independent reviewer evidence. Do not introduce workflow status to Engine Config/Props or preserve competing Issue/YAML progress trackers. Before every action read root `AGENTS.md` and `README.md`, the applicable Studio rules, Persona(s), Skill(s), architecture/entity docs and current code/tests.

## 0. Resolve identity, provenance, and current state

- **Resume by PR:** fetch the latest PR body, head/base SHA, comments/reviews, statuses, all child PRs and canonical Lesson files. Reconcile source and verified approvals. A bare PR number requests a stage report and next-action proposal only; execute the first authorized unfinished stage **after** a separate, clear user instruction. Never duplicate the PR or rely on a prior chat.
- **Resume by UUID:** use Engine's UUID resolver for `content/<book>/data/lessons/<bucket>/<uuid>/`; search active and historical PRs, old Lesson Production Issues, Course associations and real files. Reuse existing identity/branch/PR. Missing languages on an implemented Lesson require localization, not a new Lesson.
- **Course-originated:** verify actual Course PR, Course UUID, Lesson slot and Lesson UUID from the Course inventory (#639). New Lesson PR targets that Course PR's **actual integration branch** and includes the linkage marker `<!-- svitlo-course-lesson:v1 -->` with literal `Course: <uuid>`, `Lesson: <uuid>`, `Parent PR: #N` on separate lines. Do not invent link from a slug/title. Parent Course PR owns Course inventory; Lesson PR owns Lesson stage evidence. #639's automatic status sync works only after its workflow reaches the default branch; use verified manual links until then.
- **Standalone:** if authorized and truly absent, allocate one immutable UUID/slug and open one new Draft Lesson PR targeting `develop` or the designated integration parent. If existing material already exists, inspect it first. The presence of methodology alone **does not** imply Course provenance.
- **Historical Issues:** read and preserve their full evidence, approvals and links, but **do not create mandatory new Lesson Production Issues**. Map each distinct UUID to its actual Lesson PR. The separate Translation Production Issue protocol remains unchanged.

An **instructional** Lesson remains Course-neutral and reusable. An explicitly approved **assessment-only** Lesson may require preceding Course Lessons' Skills and Question Banks, as specified in its Course-originated methodology; it is still an ordinary `defineLesson` and must **not** embed a Course UUID, storyline, mascot, plot, new Runtime subtype or `dependsOn` field in Engine Config/Props. Preserve Course origin and upstream dependencies in the existing Course plan and PR tracker. Use repository naming/labels: a Lesson PR subordinated to a Course uses `pr: agent-subtask`; a standalone Lesson coordinating child bank PRs can use `pr: integration`. Both roles are **never assigned together**: even if a Course's Lesson PR receives Question/Flashcard children, its `pr: agent-subtask` role is retained and real nested ancestry gives context. All agent PRs start Draft.

## Mandatory user-facing progress report and next-action handoff

After **every completed or paused stage**, at a review/authorization blocker and on every status/resume request (including a new chat containing only a Lesson PR number), first reconcile the current Lesson PR head/base, immutable UUID, source files, stage checklist, independent reviewer/source SHAs and child PRs. A bare PR number asks for **status plus recommendation**, not immediate stage execution or a new PR. Do not treat a checked box alone, a source-only scaffold or a previous chat as proof of completion. The PR description remains the sole workflow tracker; **no** stage/status fields belong in YAML, Engine Config/Props or a parallel ledger.

Always finish with a compact, explicit report containing:

1. **Lesson identity**: exact Lesson UUID, verified Lesson PR and, if Course-originated, the Course parent PR/UUID and verified `svitlo-course-lesson:v1` linkage; source/head SHA when available.
2. **All ten Lesson stages in order**, marking each `✅ completed`, `▶ in progress`, `⬜ not started`, `⛔ blocked`, or `↻ stale`. Under Stage 6, report **each of its four independently checked substeps** with evidence. Stages 7/8 are Questions/Flashcards with child PR or justified N/A status, including review/integration evidence; show their child seven-stage workflows separately. Show locale coverage under Stages 9/10. A `✅` requires verified deliverables at pinned source/review SHAs, not a checkbox alone.
3. **Last completed stage**: explicitly `Stage N — <name> completed` with verified evidence (or `No new stage completed`), plus blockers/stale reviews.
4. **Recommended next stage**: the first authorized eligible incomplete stage, with its prerequisite, or `None — all ten Lesson stages are complete`.
5. **Recommended next action**: a single concrete copyable **chat instruction** on its own fenced `text` line, e.g. `do lesson stage 2 for PR #<lesson-pr-number>`. When starting an independently authorized, materialized Course Lesson that has no Lesson PR yet, use **exactly** `do lesson <verified-lesson-uuid> related to PR #<course-pr-number>` and resolve/reuse the existing Course parent integration branch; do not create a duplicate PR. For a standalone Lesson, identify its UUID and actual intended base branch. The command is a recommendation, **not** something to execute as a side effect of reporting. Invite the user to send it, or reply `go` to an unambiguous single proposal made in this chat; other clear instructions work too. Vague `go` without a concrete current target and a bare PR number cannot cross the separately scoped Lesson-authorization boundary.

Only recommend an action justified by verified sources and current approval/branch boundaries. If Stage 3 requires the separate independent-review chat, or a stage needs an owner decision, Questions/Flashcards completion or upstream published banks, state the blocker and propose the appropriate **authorized** handoff. Stages 4–5 may continue in the Stage 3 chat; do not require another independent agent or chat for them. Keep the PR progress checklist current when performing authorized work, but preserve concurrent edits and exact evidence. A Course Stage 5 materialization is **not** Lesson Stage 1 completion or a Lesson Production PR.

**Terminal message:** when **all ten Lesson stages** are individually complete at current evidence SHAs, explicitly say: **"All ten Lesson workflow stages are complete. There is no next Lesson stage. You can assign new work."** Stop rather than continuing without instruction. Report outstanding physical Scene/media blockers, final QA, publication, CI or merge gates separately; these are **not extra stages**, and workflow completion never authorizes Ready/merge.

### Assessment Section decisions and independent bank handoff

At Stage 1, the Methodologist decides whether the eventual Lesson needs Quiz and/or Flashcards Sections using optional root authoring-only `production.quizRequired` and `production.flashcardsRequired` booleans in `lesson.yaml`. Omitted/false does not require a Section. Pedagogical reasons, targeted Skills and assessment operations remain in plain methodology; no mandatory `lesson-assessment-sections` fence or separate machine-readable intent inventory is allowed.

Stages 2–5 preserve and review the planned normal `config.section.items/order` entries, their stable UUIDs, source-language content, placement and accessibility. Missing bank IDs are allowed in those editorial source nodes; never invent Question/Flashcard IDs or scoring defaults.

Stage 6.1 creates **schema-valid assessment Section Config drafts immediately**, including required Quiz/Flashcards Sections that do not yet have independently reviewed banks. Approved Sections preserve their UUID, slug, authored copy and order; missing required Sections receive a minimal deterministically identified draft. The temporary `questions.yaml`/`flashcards.yaml` `sectionDrafts` retains original unfinished approved details for Stages 7–8 but is not another published source. Missing selections use deterministic reserved `feedc0de-` UUIDv8 syntax and adjacent `// TODO (BLOCKER):` comments on the Section, every pending field, and Lesson root. Missing screen labels are conspicuous drafts, never fabricated translations or instructional prose. `config.params.quizRequiredForCompletion` stays unchanged, including `true`. Stage 6 typed/Markdown draft checks are **not** resource publication: production and Ready/merge fail closed on reserved or unresolved Question/Flashcard IDs, incomplete approvals or TODOs. Stages 7–8 replace all provisional selection/interaction/results values only with reviewed genuine resources and prove strict Engine Props and ownership/locale verification.

One-time `/lesson materialize` preserves `lesson.yaml`. A separately authorized `/lesson finalize` may retire **only** its original unchanged bytes after verified committed source transfer; it never regenerates or overwrites authored files.

### Stage 7/8 independent child-bank handoff

**Questions and Flashcards are separate parent Lesson Stages 7 and 8**, while each actual bank is authored, independently reviewed, translated and materialized in its own seven-stage child Draft PR. These are not part of Stage 6. The parent tracks the two stage checkboxes and child PR/source/review/integration evidence; child PRs retain their own stage checklists. Only propose bank work after verified typed Lesson sources and current derived reference Markdown exist.

- **Stage 7 — Questions:** verify whether an own bank is required even when there is no Quiz. Reuse the matching child PR and propose `do questions stage <next> for PR #<questions-pr>`, or propose `do questions for lesson <lesson-uuid> related to PR #<lesson-pr>` when none exists. The user may use the command **in this chat or a new chat**. Do not create a child PR without explicit authorization. Check parent Stage 7 only after all seven Questions stages, review and actual integration, or an evidence-backed Methodologist own-bank N/A; an unfinished bank is not N/A.
- **Assessment-only Lesson:** own Questions can be N/A with documented Methodologist rationale and verified upstream bank ownership, but unresolved external Question/Quiz selection remains an explicit downstream blocker with PR/SHA/locale evidence; do not invent an empty bank or treat absent Quiz as N/A.
- **Stage 8 — Flashcards:** after verified Questions completion/integration or legitimate own-bank N/A, reuse an existing child PR and propose `do flashcards stage <next> for PR #<flashcards-pr>`, or propose `do flashcards for lesson <lesson-uuid> related to PR #<lesson-pr>` when pedagogically required and missing. The same chat or a new chat is allowed. Check Stage 8 after all seven child stages and actual integration, or documented Methodologist Flashcards N/A. An existing Questions bank does not make Flashcards mandatory.
- **Pause/handoff:** report the actual child PR and next eligible action, and offer **one** copyable chat command; never start child authoring, review, merge or source replacement implicitly. After Stage 8, recommend Stage 9 Translation.

### Physical resource blockers outside Stage 6

Scene implementation, physical illustrations/audio/video/3D files, missing captions/transcripts for those media and specialist assets are **separate per-resource blockers** in the parent Lesson PR, with exact Section/Block/asset path, approved specification, accountable human/specialist, pending status and verification evidence. **Do not generate or implement these as Stage 6 work.** Preserve `TODO(asset)`, `TODO (BLOCKER)` and Nil UUID media placeholders until actual delivery; incomplete assets block final QA/Ready/merge, not the four Stage 6 source-preparation checks. Accessibility/offline audits validate authored source contracts and specified alternatives, not imaginary physical runtime behavior. Verify real assets and Scene runtime at final QA without fabricated proofs.

## Single authoring source

Stages 1–5 progressively author exactly one temporary `lesson.yaml` with root/nested `config` (Engine Config, one immutable UUID per entity) and optional `production` (Methodologist source, learner purpose, specs, prompts, scripts and source `documentLanguage`). Its `config.params.languages` contains the full intended locale tuple; source-language copy lives only in the actual `production.documentLanguage` locale. Missing translations remain missing. Ordered entities use the real Engine `items/order` contracts, not invented arrays or a second `content.yaml`.

**Effective language scope (handoff to #639, #646, #647):** a standalone Lesson builds against its own declared languages. A Course requesting that Lesson must pass its actual effective requested languages to the Lesson Build, and validate that the requested scope is a subset of the Lesson-supported languages; do not shrink the persisted standalone Lesson tuple or embed the Course in Lesson Config. A Flashcard Build receives the **Lesson's actual effective language scope**, without Course-specific persisted coupling or silent fallback. The existing Lesson Markdown generator enhancement in [#645](https://github.com/KiT-Maverik/svitlo/pull/645) is an external dependency to verify, not a generator to duplicate in this PR.

**No** `draft`, `approved`, `stage`, `reviewStatus` fields, approval frontmatter, Methodologist-approved strings, or stage-specific Zod/JSON Schema families. YAML must stay syntactically sound while editorially incomplete. Legacy `methodology.md`, `methodologist-brief.md`, `content.yaml` or other approved inputs require explicit, non-destructive migration into `lesson.yaml`, retaining the full authored prose and original review/source SHA. Never silently delete legacy files, overwrite hand-authored sources or invent missing content. Separate `questions.yaml`/`flashcards.yaml` sibling files are owned by their own independent workflows, not Lesson Config.

## Lesson editorial review continuity: one independent entry, immediate role-owned fixes

**Independence boundary:** Stages 1 (Methodologist) and 2 (Screenwriter) may share their authoring context. **Stage 3 must start in a genuinely new chat/context with a qualified Content Reviewer who did not perform Stages 1 or 2 or their corrections.** Read the actual complete canonical Lesson YAML, methodology, prior evidence and current Git/PR state; the new chat is not a substitute for source inspection. This is the **only mandatory independent chat handoff in Lesson Stages 3–5**. Stages 4 (Learning Experience Expert) and 5 (Methodologist compliance) run as distinct, evidence-producing **specialist audits in that same Stage 3 chat**, with explicit persona switches and their own criteria, not new independent-review assignments. Do not call Stages 4 or 5 independent approvals. Stage 8 translation review and independent bank reviews retain their own independence gates.

**Review-and-repair in the current stage:** A clear request to execute Stage 3, 4 or 5 authorizes that stage's reviewer/specialist to **record findings and immediately correct actionable, in-scope defects in the same canonical `lesson.yaml` and PR branch** rather than merely asking the Stage 2 Screenwriter to fix every finding. First inspect and pin the unmodified baseline commit and YAML **blob SHA**, then record each finding's stable ID, node path, severity, evidence and proposed repair in the existing Lesson PR tracker. Before any edit, identify the accountable persona and stay within its competence: Stage 3's independent Content Reviewer can act as the qualified editorial Screenwriter for bounded content fixes; Stage 4's Learning Experience Expert can directly repair presentation, accessibility, pacing, feedback and Scene/media **experience specifications** within approved content/methodology; Stage 5's Methodologist can directly repair compliance wording, mapping and evidence within the already-approved educational scope. When a fix crosses roles, **explicitly switch to the appropriate authoring persona within this same review chat**, document which role authored each change, and apply that persona's Skill and constraints. Never conceal authoring as a read-only review or call correction work a second independent sign-off.

**Verification and SHA accounting:** Commit source fixes, verify the changed nodes **and their dependent Sections/blocks within the active stage**, then complete that stage's own audit on its final source SHA. Record the original reviewed commit/blob SHA, correction commit/new blob SHA, findings-to-fixes mapping, commands actually run, remaining risks and **active-stage verdict on the resulting source blob** in the PR. Stage 3 independence is from the Stage 1–2 authors; disclose reviewer-authored corrections rather than implying a second independent sign-off. Stage 4 is a subsequent experience audit of its then-current source. **Stage 5 is the last editorial review and the final integrated acceptance of the complete latest YAML**. A later revision does not retroactively rewrite the earlier stage's review SHA or remove its completed status; the current downstream stage takes responsibility for evaluating the consequences of its own edits.

**Strictly forward-only Stage 3 → 4 → 5 → 6:** Stage 3 independently reviews the Stage 2 source and applies its own fixes. Stage 4 **consumes the completed Stage 3 review**, checks the current complete source, directly fixes experience defects and evaluates the effects of **its own changes as part of Stage 4**; it does not reopen Stage 3. **Stage 5 consumes BOTH completed Stage 3 Content Review and Stage 4 Learning Experience Review**, including their recorded findings, fixes and commit/blob SHAs. Stage 5 is the **final comprehensive editorial/methodological review**: examine every Section, ContentBlock, Scene/media specification and assessment intent against approved Stage 1 methodology; identify any remaining methodology or consistency defect; **make the authorized corrections directly; commit; verify the whole corrected lesson and the effect of those corrections on content and experience as part of Stage 5 itself**. Mark Stage 5 complete with its own final source blob SHA, then hand off **directly to Stage 6 Resource Production**. **Never route Stage 5 back to Stage 3, Stage 4 or Stage 2; never require re-approval/re-review of earlier completed stages because Stage 5 changed YAML.** Stage 3/4 checkboxes remain completed, each linked to the SHA it actually reviewed. Preserve the historical evidence rather than claiming the old reviews covered the final Stage 5 SHA; Stage 5's integrated verdict provides that final coverage.

**True authority blockers, not loops:** If an essential correction would redefine approved Stage 1 outcomes, prerequisite/Skill scope, Quiz/Flashcards Section intent, cognitive Assessment Methods, or Assessment Architect-owned Questions/scoring, record the exact blocked decision and obtain approval from its owner. Once resolved, **resume and finish Stage 5 itself** on the updated YAML; do not send it backward to Stage 3/4. Missing approved decisions or inability to verify educational correctness block **Stage 5** without a false approval, but they do **not** create an independent-review cycle. Stage 6 verifies actual structural/technical readiness, not a new pedagogical review. Stage 10 and the independent Stage 7–8 bank reviews keep their own gates.

**Authorization and commands:** Stage 3's next-action command explicitly says **open a new chat**. After Stage 3, offer `do lesson stage 4 for PR #N` **in this same chat**; after Stage 4, offer `do lesson stage 5 for PR #N` **in this same chat**. After a successful Stage 5, **mark Stage 3, Stage 4 and Stage 5 completed in the existing PR tracker, retain their original SHA evidence, record the final Stage 5 YAML SHA and hand off directly to `do lesson stage 6 for PR #N`**, which may be executed in the **same chat** if explicitly authorized. Never recommend Stage 3/4 as the next task from Stage 5, even when Stage 5 made corrections. An explicit instruction to execute multiple stages permits a forward-only continuous review/repair/handoff; a single-stage instruction alone does not silently authorize Stage 6. Preserve Lesson UUID, Course parent/branch and source-language copy. Do not merge, mark Ready, create duplicate tracker files, fabricate runtime assets/translations/bank IDs or bypass Stage 6 checks.

## Stages (record role, source SHA, evidence, verdict and next action after each)

### 1. Methodology

**Persona:** [Methodologist](../../personas/methodist.persona.md). **Skill:** [Create Lesson Brief](./create-lesson-brief.skill.md). Verify real Skill UUID/source links, learner audience/entry knowledge, prerequisites, aims, conceptual scope, source references, misconceptions, accuracy, desired depth, supported locales/accessibility and `assessmentPlan` including whether and why zero/one/multiple Quiz Sections are needed and required cognitive `AssessmentMethodKey` values.

For a **Course-originated** Lesson, first inspect its _already-authored_ methodology (Lesson YAML and proven Course handoff), including whether it is an approved assessment-only Lesson and which earlier Course Lesson slots/banks it requires. Evaluate **completeness and adequacy**; reuse if sufficient, repair real gaps in the same `production.methodology`, and record the updated SHA. For a **standalone** Lesson with no existing Methodology, author it substantively from scratch; if it exists, review/improve it just as for Course work. Do not require a storyboard or a literal `Methodologist status: Approved` frontmatter. Missing actual pedagogical substance or unverified Skills block stage; no extra progress property belongs in YAML. **Output:** complete pedagogical method and stage evidence in Lesson PR.

### 2. Content Creation

**Persona:** [Educational Screenwriter](../../personas/educational-screenwriter.persona.md). **Skill:** [Create Lesson Content](./create-lesson-content.skill.md). Enrich the **same** `lesson.yaml` with ordered Sections/blocks; actual intelligible source-language explanations, examples/counterexamples, worked demonstrations, learner actions, meaningful feedback, misconceptions, transitions and reflections. Specify `production.purpose`/`pedagogicalIntent` and complete implementable `production.specification`/`prompt`/`script`/`storyboard` for Scenes, media and any Quest, with accessibility, offline and weak-device equivalents. Follow real registered Config and renderer support; draft-only features are not shipped. No arbitrary minimum block counts, fake locales or Quiz answer banks. One short passive Text-only Section is a review warning, not an automatic schema failure. **Output:** full instructional blueprint, or for an approved assessment-only Lesson a complete accessible Quiz/evidence experience without invented teaching material, and production requirements in Git with Screenwriter SHA/handoff; unresolved material gaps block.

### 3. Content Review

**Persona:** independent Content Reviewer (qualified Educational Screenwriter **other than the Stage 1–2 author**) in a **new chat**. **Skill:** [Review Lesson Content](./review-lesson-content.skill.md). Inspect every Section/ContentBlock, correctness, explanation depth, examples and common mistakes, age-appropriate terminology, transitions, feedback and accessibility of copy. Flag empty/filler/thin material and factual deficiencies without quotas. Pin baseline SHA and record node-specific findings before editing; **repair bounded editorial defects directly in the same chat**, switch explicitly to the Screenwriter role for authoring, commit and re-audit affected content against the corrected SHA. Mark complete only with full coverage and disclosed reviewer-authored repairs; escalate changes to approved learning/assessment scope. **Output:** genuinely independent Stage 3 entry, traceable corrections and final source-SHA verdict in PR; no YAML review field.

### 4. Experience Review

**Persona:** [Learning Experience Expert](../../personas/learning-experience-expert.persona.md), **same Stage 3 chat**, with an explicit specialist role switch; this is **not another independent reviewer gate**. **Skill:** [Review Lesson Experience](./review-lesson-experience.skill.md). Examine complete current YAML and production specifications for purposeful interaction, pacing/cognitive load, feedback, keyboard/touch/screen reader/RTL/reduced motion, captions/nonvisual alternatives, offline and low-end devices; distinguish planned Scenes/Quest from implemented renderers. Record node-specific findings and baseline SHA, **fix actionable experience defects in scope immediately**, commit, verify their effects on content quality as part of Stage 4 (without reopening Stage 3), and record a final-source-SHA specialist verdict. **Output:** role-owned experience audit and repairs, blocked only for genuine unresolved design/authority dependencies.

### 5. Methodology Compliance

**Persona:** [Methodologist](../../personas/methodist.persona.md), **same Stage 3/4 chat**, now acting in a methodology-compliance role, **not a third independent review**. **Skill:** [Review Lesson Methodology](./review-lesson-methodology.skill.md). Compare every latest YAML Section, learner-facing explanation/example, misconception/feedback and complete Scene/image/audio/video/Quest specification against the verified Stage 1 scope, Skills, prerequisites, sources, accessibility and `assessmentPlan`. Verify actual Quiz intentions, not Assessment Architect-owned Questions. Verify Methodologist decisions about Quiz/Flashcards Section requirements against normal authored Sections and flag missing implementation work; verify that any intentionally incomplete assessment Sections are identified for the independent Stages 7–8. Read the completed Stage 3 Content Review and Stage 4 Experience Review findings and their original SHAs before auditing the **entire latest YAML**. Record coverage, node-specific findings and baseline SHA; **directly repair in-scope methodological and consistency defects**, commit and verify the whole corrected Lesson (including any content/experience consequences) **within Stage 5, without reopening Stage 3/4**. Learning-outcome or approved assessment/scope changes require the owner's decision; resume Stage 5 after resolution. Pending binary/locale is a production dependency, not a content defect. **Output:** final comprehensive pedagogical compliance verdict on the Stage 5 YAML blob SHA, completed Stage 3/4/5 checkboxes and direct Stage 6 handoff; no frontmatter token.

### 6. Resource Production — source preparation

**Persona:** [Coding Agent](../../personas/coding-agent.persona.md). **Tools:** [Lesson Materialization](../../../scripts/ci/lessonMaterialization/README.md), [Finalize Lesson](../../../shared/engine/scripts/finalizeLesson/README.md). Stage 6 has **four separately checked substeps** in the parent PR. **No Scene/media implementation or independent assessment-bank authoring/integration** belongs here.

**6.1 Materialize Lesson sources.** Verify reviewed Stages 1–5, canonical identity and YAML blob SHA. When deployed, post exact `/lesson materialize` on the existing Draft Lesson PR; verify real Actions resolve/analyze/publish, SHA256 artifact, complete generated TS/Markdown/Code/specification inventory, committed diff and preserved YAML. Bank-pending Sections use `preflight-draft` / `handoff`, others strict `preflight` with source preservation. Do not overwrite edited source. A distinct, authorized `/lesson finalize` removes only the fully transferred unchanged YAML after materialization. Record run/commit/source SHAs. If unavailable, report deployment blocker or use an explicitly authorized trusted local checkout.

**6.2 Accessibility source audit.** Inspect generated Sections/ContentBlocks and Screenwriter specifications for keyboard and screen-reader semantics, focus, RTL, reduced motion, media alternative text, captions/transcripts plans and equivalent nonvisual paths. Correct in-scope source/specification problems and record coverage plus SHA; list missing physical assets as **separate resource blockers** with owners. Do not implement Scene components or media assets.

**6.3 Offline source audit.** Inspect local-resource paths, offline/fallback design and low-end-device needs against real Engine/UI Kit/textbook contracts. Repair source-level errors only, log missing Scene/media assets as separately assigned blockers, and record actual checks and SHA. Do not fabricate an offline runtime or binaries.

**6.4 Validate source and handoff.** Run applicable Engine schema/preflight, Builder source-fidelity/inventory checks, typed Section/Config source checks and available scoped tests. Record commands/results, source/output SHAs, expected Draft-only failures vs unexpected corruption. **This is source readiness, not strict production Props/publication validation**; unresolved bank selections, missing physical media and future translations are not Stage 6 prerequisites. A successful materializer alone does not satisfy 6.2–6.4.

**Completion:** Check 6.1–6.4 individually with verifiable evidence, then check the parent Stage 6. Preserve temporary `lesson.yaml` for safe reconciliation if necessary; `/lesson materialize` never deletes it; only a separately authorized, verification-backed `/lesson finalize` can do so. Stages 7–8 own Questions/Flashcards; Stages 9–10 own locale work. Keep Scene/media TODOs as independent blockers for final QA/Ready/merge even after Stage 6 is checked.

### 7. Questions — child workflow

**Owner:** Learning Assessment Architect and [Create Questions Flow](./create-questions-flow.skill.md). Stage 7 coordinates one separately authorized seven-stage Questions child Draft PR targeting the actual Lesson branch. On entry, offer a copyable `do questions for lesson <uuid> related to PR #<lesson-pr>` (new) or `do questions stage <next> for PR #<questions-pr>` (resume), usable in the same or a new chat. Parent Stage 7 is complete only after reviewed child-workflow completion, actual integration and approved local Quiz selections, or documented Methodologist own-bank N/A. Do not treat a missing bank or no Quiz as N/A.

### 8. Flashcards — child workflow

**Owner:** Flashcard Learning Architect and [Create Flashcards Flow](./create-flashcards-flow.skill.md). Require reviewed and integrated Questions or verified own Questions N/A. On entry, offer a copyable `do flashcards for lesson <uuid> related to PR #<lesson-pr>` (new) or `do flashcards stage <next> for PR #<flashcards-pr>` (resume); the user may continue in this or a new chat. Parent Stage 8 is complete only after reviewed child-workflow completion and actual integration, or Methodologist-backed Flashcards N/A. Neither Flashcards nor a Flashcards Section is automatically required by having Questions.

### 9. Translation

**Persona:** [Technical Translator](../../personas/technical-translator.persona.md). **Skills:** [Technical Translation](../translation-workflow/technical-translation.skill.md), [Manage Translation Production](../translation-workflow/manage-translation-production.skill.md). Translate real persistent generated source — typed locale dictionaries, Markdown/Code-derived text, Scenes, media captions and blocks — after YAML finalization, per entity×locale under the planned language tuple. Use the existing/new authorized fixed-scope Translation Production Issue and verified child ownership. Do not fake target-language coverage, copy English as translation or lower `params.languages`. **Output:** real translated source and precise per-locale PR/SHA/progress; outstanding locales remain blocked.

### 10. Translation Review

**Persona:** an independent Technical Translator reviewer. **Skill:** [Review Translation](../translation-workflow/review-translation.skill.md). Review correct **Lesson-family Code-derived** per-locale Markdown and manifest, pinned source SHA, exact entity coverage, terminology, fidelity, scientific meaning, RTL, accessibility and captions. A Skills Markdown artifact does _not_ review a Lesson. Missing/stale/incomplete artifact blocks affected locale; owner controls reviewer start and chosen source PR/SHA. Remove tracked temporary `.agent-ci-artifacts` before merge. **Output:** independent per-locale verdict/sign-off tied to source revisions.

## Independent bank workflow evidence

Questions and Flashcards are **parent Lesson Stages 7/8**, with independent seven-stage child PRs and their own responsible specialists. The parent owns each stage checkbox, child PR/source/review/integration evidence or explicit Methodologist N/A rationale. A substantive teaching Lesson normally needs a full Question Bank even without a Quiz. Questions must be completed, reviewed and integrated before Flashcards, unless own Questions are verified N/A; missing/unfinished Questions and no Quiz are never N/A. An assessment-only Lesson with N/A own Questions still tracks the reviewed external banks and Quiz dependencies. The seven-stage [Questions Flow](./create-questions-flow.skill.md) and [Flashcards Flow](./create-flashcards-flow.skill.md) continue independently. Preserve their YAML and source ownership; do not embed banks into Lesson Config, create them during Stage 6 or substitute parent checkboxes for child evidence.

### Assessment-only Lesson upstream dependencies

An assessment-only Lesson Production PR is opened **only when that exact Lesson is separately authorized**, and for Course-originated work retains its existing `svitlo-course-lesson:v1` identity marker and real parent Course integration branch. Before selecting or finalizing Quiz candidates, the Lesson agent must:

1. Read the approved Course `course.yaml` source revision (or its Stage 5 materialized Course sources/methodology), resolve the exact **upstream Lesson slot keys, UUIDs, Skills and intended Question Bank owners**, and record the Course review SHA. Never infer dependency edges from titles or create additional Engine fields.
2. Record **each upstream Lesson PR, Question Bank child PR URL, head/source and independent review SHA, actual target/base branch, merge/integration status and required locales** in this Lesson PR. If a branch/PR does not yet exist, record that as a dependency, not as an invented ID or approval. The upstream Lessons are allowed to contain their own Questions with **no Quiz Section**.
3. Verify that each required bank was authored and independently reviewed, is **actually present in the assessment Lesson branch ancestry**, and that its Questions have been published with the expected owning Lesson UUID and complete selected resource/locale files. A successful GitHub check on an unmerged child branch is not integration. When bank selection spans Lessons, the global UUID resolver and locale/build gates from [PR #668](https://github.com/KiT-Maverik/svitlo/pull/668) must be integrated and **verified**, not merely described in a Draft PR.
4. Until all gates are satisfied, leave final `params.selection.questionIds`, Quiz resource validation and publication **blocked** with the precise missing owner/PR/SHA/locale. Independent methodology/content work may continue if it does not falsify a completed Quiz; the earlier Course Stage 4 methodology approval is unaffected.
