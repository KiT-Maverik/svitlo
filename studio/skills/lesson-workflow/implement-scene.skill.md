# Implement Scene

> **Current Lesson flow:** [Create Lesson Flow](./create-lesson-flow.skill.md) owns three ordered Stage 6 steps: **6.1 materialize**, **6.2 complete valid typed Lesson resources**, **6.3 implement and integrate Scenes**. This skill is the **mandatory Stage 6.3 procedure for Lessons with Scene Configs**, not a later optional final-QA task. The Scene implementer may own a separate child Draft PR, but the parent Lesson's Stage 6.3 cannot close until all required Scenes are implemented, registered, tested and integrated. No new mandatory Lesson Production Issue; existing Issue and approval evidence must be reconciled.

**Persona:** [Coding Agent](../../personas/coding-agent.persona.md) — read it fully before any work. Also read applicable root/package `AGENTS.md`, [Lesson entity](../../docs/entities/lesson.md), [Lesson Content](../../docs/entities/lesson-content.md), accessibility/offline architecture and the **actual current** Engine schemas and UI Kit renderer, textbook Scene registry, tests and package scripts.

**Purpose:** Implement, integrate and test the **entire approved Scene inventory** for an authorized Lesson as Stage 6.3. Assign nonoverlapping batches/child PRs where useful; preserve one parent Stage 6.3 acceptance gate. This engineering specialization **does not replace** the YAML-to-typed Lesson Builder (6.1) or source/type correction (6.2). If there are no Scenes, record evidence of the zero-Scene inventory and Stage 6.3 N/A.

## Responsibility / source-of-truth boundaries

- **Deterministic builder/finalizer (separate work):** reads an independently reviewed, completed `lesson.yaml` and emits typed Lesson/Section/ContentBlock drafts plus co-located `specification.md` handoffs through [Stage 6 finalization](../../../shared/engine/scripts/finalizeLesson/README.md). **Do not implement or reimplement that builder in this Skill.** Do not manually recreate the entire Lesson or its ContentBlocks; use verified generated source modules and assigned Scene specifications.
- **Educational Screenwriter:** owns the Lesson's reviewed `lesson.yaml` production specifications (including the per-Scene instructions persisted through finalization); legacy `scene-spec.md` files may be independent, verified migration inputs. Learning purpose, scientific subject behavior, expected interactions, explanations and constraints are fixed by the **source-revision-specific approved specification**.
- **Learning Experience Expert / Methodologist:** their accepted reviews and editorial sign-offs are separate prerequisites. Coding Agent must not silently alter learning outcomes, Quiz requirements, assessment evidence, Course narrative or scene semantics.
- **Implement Scene Coding Agent (this Skill):** writes the React Scene implementation, typed localizable-text shape, **only the approved source-language strings**, internal model, styles, accessibility, tests and integration with the existing content block and Scene registry. Identifies unfinished assets and questions with actionable source `TODO` annotations; resolves/removes each when actually completed.
- **Translation agents:** later supply all remaining supported Lesson locales; their production/review process is [Translation Production](../translation-workflow/manage-translation-production.skill.md). Coding Agent **must not translate** other languages or copy source text into them.
- **Resource specialists:** create pending media/3D/audio/video assets. The implementer may integrate existing verified, authorized assets, but not fabricate URLs or claim incomplete media exists.

## Hard prerequisites and scope

1. **Require the authorized Lesson Draft PR, not a newly created Production Issue.** Locate its verified Lesson UUID, Stage 6.1 materialization/source SHA, Stage 6.2 typed resource verification and **complete Stage 6.3 Scene UUID inventory** through [Create Lesson Flow](./create-lesson-flow.skill.md). Read the parent Course and child PRs if applicable, reconcile historical review/Issue evidence, and claim nonoverlapping Scene paths. Assign Scene batches to specialist child PRs targeting the actual Lesson branch when parallel work is authorized; no Scene may be silently omitted from the Stage 6.3 gate. Missing editorial approval blocks only the affected Scene and Stage 6.3 completion; proceed with other approved Scenes.
2. Confirm the **current Lesson PR's** reviewed `lesson.yaml` source SHA and Stage 3–5 independent acceptance, or its successfully finalized permanent methodology, generated Config modules and Scene `specification.md`. A Scene name/key alone is **not** a behavior specification. Preserve any accepted legacy `methodology.md`/`scene-spec.md` evidence when present.
3. The scene specification must identify educational purpose, learner actions, meaningful states/transitions, correct domain rules, feedback, copy/source language and accessibility expectations. Check it against the existing typed source/partial scaffold. If **missing, unapproved or materially ambiguous**, **stop the affected Scene** and record a precise blocker in the Lesson PR and current Scene handoff. Don't invent missing teaching steps, algorithms, physics or assessment rules. Other ready Scenes may proceed independently.
4. Inspect current textbook Scene implementation and testing conventions rather than copying historical references. Modern Scenes live in a textbook-owned `content/<textbook>/scenes/` subtree, separate from build-time `data/lessons/<bucket>/<uuid>/`. The latter holds authored data/scaffold; do not assume `content/playground/src/data` or old `resources/scenes/scenes.data.ts` exists.
   For a Lesson scaffold generated by the modular YAML Builder, the handoff
   `specification.md` now lives beside its nested Scene Config `index.ts`
   under the Lesson UUID tree. Resolve its **Scene UUID** from the Config,
   cross-check the approved Screenwriter Scene specification, and still create
   the executable Scene implementation in the existing UUID-addressed
   `scenes/<bucket>/<scene-uuid>/` registry location. Never register the
   technical specification as executable Scene code.
5. Confirm the target renderer supports the intended type, media, input modality and offline behavior. For a textbook without a Scene registry, TSX compilation, `./scenes` export or required renderer tests/dependencies, **Stage 6.3 must arrange the textbook-owned infrastructure first** (or consume a separately reviewed infrastructure PR); do not mark the Scene as implemented or the Stage as complete while that dependency is missing. Never invent an unrelated framework or change shared contracts solely to silence errors. If a prerequisite is outside the authorized Lesson scope, record the blocking integration PR and continue other independently ready Scenes.

## Current Scene contract and implementation

Read these actual sources in the target branch:

- [Engine Scene schemas](../../../shared/engine/configurators/contentBlocks/defineScene/defineScene.schemas.ts) define `scene_Config_Schema` and `scene_Props_Schema`. Scene values use field-level localization; published Props retain the stable block identity and `type: 'scene'` discriminator.
- Use the **current** `@svitlo/engine/build` configurators and Zod Config/Build contracts for Lessons, Sections and ContentBlocks; the removed `shared/engine/src/lessons/create*` creators are not supported APIs. Inspect actual source/tests and keep authored Config outside runtime imports.
- `content/playground/scenes/5/72d22bea-d787-4c6d-9a83-144830c6d325/LightRayDiagram.tsx` and `content/playground/scenes/3/968926d3-7b15-4575-8f57-a5a2a5054783/LightPropagationSimulation.tsx`: examples of **current typed `locales` props** and UI interactions. Treat as references, not a mandatory architecture for every textbook.
- `content/playground/scenes/createSceneRegistry.ts` and `scripts/textbook-tooling/generate-scenes.mjs`: current lazy Scene registration; use the equivalent existing package setup.
- Actual UI Kit Scene renderer/registry integration, current unit-test fixtures, package dependencies and accessibility APIs.

**The Scene root component must follow the renderer's current typed public API.** In the current Playground, it accepts `locales` from the localized Scene response, rather than being prop-free or using the retired `SceneLocaleContext` pattern. Infer the minimal response prop type from the owning Scene block's `'response'` type, for example `Pick<SceneBlock<'response'>, 'locales'>`; do not invent a second translation provider or pass a whole multilingual dictionary to the Scene. Internal child components may receive typed props. Honor the current registry's default-export adapter.

Implement deterministic model logic in pure functions when complex enough to test independently; ensure input bounds, state transitions, reset semantics, cleanup of timers/listeners, reduced-motion, render stability, keyboard/touch parity, sensible focus, a11y names and correct scientific behavior. Prefer existing UI Kit primitives and CSS logical properties; handle **semantic** LTR/RTL (reposition directional geometry only when meaning demands it, never mirror text, formulas, physical invariants or whole scenes indiscriminately). Design for narrow screens, slower devices, offline availability of bundled dependencies and no unnecessary initial bundle weight.

## Localizable content: type the full shape, author **one** language

1. Extract _every_ learner-facing string from the approved Scene spec into a typed nested `LocaleShape`: labels, title/description, controls, hints, feedback, errors, ARIA names, SVG `<title>`/`<desc>`, captions, transcripts and descriptions for accessible alternatives. Reuse the target textbook's existing pattern for `ContentBlock_Scene<'data'>` and source-locale strings.
2. Set the exact `supportedLanguages` required by the approved Lesson and create all **necessary type references** to them. Populate authored messages **only for `lesson.yaml` root `production.documentLanguage`**, or the verified final source language after YAML deletion; if this differs from Methodologist prose language, use the **Screenwriter** source language. Do not hardcode English because an example Scene uses it.
3. **Never write translations** for other locales. No copied English/source text, machine translations, fake placeholders, empty strings, `as any`, weakened locale unions, `Partial<Record<...>>`, silent fallbacks, optional chains masquerading as valid text, or suppression of missing-locale errors. If a builder already generated the source-language locale object, reuse it; do not overwrite generated owned files with a competing dictionary.
4. A temporarily failing **full TypeScript check from _only_ missing target locale values** is an acceptable intermediate authoring state, **not** a completed Lesson. Verify and report concrete diagnostics by file/line/type: distinguish expected `missing target locale` errors from Scene logic, type/API, imports, tests and registration errors (these must be fixed). Do not assert a passing typecheck or publish/bundle incomplete supported locales. Source-locale unit tests may use explicit **test-only** LTR/RTL message fixtures to verify direction handling; they are not authored production translations.
5. Record localization TODOs at the **actual authored dictionary/builder output boundary**, pointing at the owning Translation Draft PR or historical Issue when applicable. Avoid adding meaningless TODOs for every missing locale when one precise TODO with the required locale list and missing fields is sufficient. Remove the TODO only when real translated values have been supplied and coverage verified.

## Unfinished requirements and **code-visible TODO lifecycle**

A Scene may still have pending illustrations, meshes, media, captions, interaction details or technical decisions. Keep the partial implementation honest and **visible in the source**, not only in an Issue or chat.

- For **every real unresolved item affecting implemented code**, add a local, actionable `TODO(scene)`, `TODO(asset)`, `TODO(i18n)`, `TODO(test)`, `TODO(perf)`, or `TODO(a11y)` comment **beside the code path or type/dictionary responsible**. Each TODO states **what is missing, why it matters, the needed action/acceptance condition and a traceable Issue/resource/spec key**. If ownership is unknown, state which specialist must decide.
- Example (illustrative, not permission to ship fake content):

```ts
// TODO(asset): scene-key=solar-system-orbits, Issue #123 — replace the pending
// orbit textures only after the Media Agent delivers approved, licensed files
// and accessible alternatives; verify offline packaging and image descriptions.
```

- If an asset is missing, do **not** fabricate a URL, pretend a broken import works, or use arbitrary substitute educational content. Implement independently valid states and keep the missing branch explicitly gated by the existing product mechanism. A feature that cannot meet the approved learning purpose must remain **blocked/incomplete**, never marked production-ready.
- If a substantive scientific/educational decision is unresolved, **stop that affected logic**, leave a clear TODO only in an existing genuinely incomplete scaffold/implementation where relevant, and return the question to the Screenwriter/Methodologist; do **not** invent behavior just to have a runnable demo.
- For unresolved accessibility-equivalence barriers: investigate and implement reasonable alternatives first. If one truly remains, add **`TODO(a11y)` at the end of the main Scene component file** with affected learners, precise barrier, attempted alternatives and remedy; add a local comment near the affected code if useful. Explicitly disclose the barrier in the chat/Issue. A TODO is a **tracked limitation**, not an exemption from accessibility requirements.
- Maintain a concise `requirements.md` / resource handoff **only when the separate builder or existing Scene workflow owns such a file**; otherwise record pending dependencies in the production Issue, without creating an alternative YAML-to-scaffold requirements generator. Keep source TODOs and Issue entries synchronized and actionable.
- **Before each Scene PR completion and after any fix:** inspect all relevant TODO comments. For each resolved item, **remove the TODO in the same change** (and close/update the associated tracked task after verification). For unresolved items, confirm the comment still describes the current code and is referenced in the PR/Issue handoff. Never retain stale TODOs after completing an implementation, and never delete an unresolved TODO to make the code look complete. No permanent blanket TODOs, no silent suppression, no fake "done" checkmark.

## Registration, integration and tests

- **Starting point:** after Stage 6.1 and 6.2, cross-check every `defineScene` UUID and `specification.md`; optionally run [Scene Scaffolding](../../../shared/engine/scripts/sceneScaffolding/README.md) with the exact reviewed `lesson.yaml` in Scene-capable textbooks. Its TSX, tests and stories are **intentionally incomplete drafts**, never an implementation PASS. Do not infer generation from the prior Lesson Builder run.
- Keep the approved, stable Scene block UUID and authored Lesson identity. The builder owns Lesson/Section/ContentBlock creation; this Skill only wires implemented Scene modules to their **existing assigned** Scene references. If the scaffold or Scene UUID is missing, report it rather than inventing a competing source.
- For textbook packages using `scripts/textbook-tooling/generate-scenes.mjs`, place Scene code in the expected textbook-owned `scenes/<last-hex-digit>/<uuid>/` with a valid `index.ts` default export. Obtain the path from `resolveEntityPath(scene.id)`. Run the textbook workspace's `content:generate:scenes` followed by `content:check:scenes`; **never manually edit generated `sceneLoader.ts`**. If the selected textbook uses different existing registration, follow its documented mechanism.
- Test the actual loader-to-Scene path, that the Scene UUID resolves to the expected module, that the Scene is included in the right Section, and that only localized response text (not source multilingual dictionaries) reaches it. Verify the shared build-time resource generator and published package boundaries when relevant.
- **Co-located automated Scene tests are mandatory for every Scene**, not just parent Lesson coverage. Follow repository/package conventions (e.g. `*.unit.spec.tsx` or `*.unit.spec.ts` and `*.unit.fx.ts`). Cover rendering with source locale, state machine/initial/reset/edge transitions, user interactions and feedback, scientific invariants and pure-model functions, accessible keyboard flow and names, meaningful nonvisual alternatives, semantic RTL using test-only fixtures, reduced-motion, responsive behavior where testable, asset-missing handling and registration/integration. Do not manufacture assertions that merely check an element exists.
- Run available **focused** Scene tests, source-shape TypeScript verification/isolated tests that do not require unfinished translations, lint/format, generated Scene registry check, and any applicable package build/portability tests. Run the full typecheck too when possible and **classify** failures; do not claim a clean production build while locale/resource gaps remain.
- If test infrastructure cannot exercise real rendering, declare precisely which test is missing or skipped and record `TODO(test)` linked to the needed harness. Don't substitute invented passing results.

## Execution, PR and acceptance

1. **Require** the verified Lesson Draft PR (Course parent PR when applicable), exact UUID, verified Stage 6.1 materialization and 6.2 typed resource handoff, current independent editorial approvals and generated Scene Configs/specifications. Reconcile historical Issues, but do **not** create a mandatory new Issue. Missing Config/specification blocks 6.3 and returns to the owning Stage 6.1/6.2 repair; do not independently fabricate Lesson source.
2. Inspect exact current Scene contracts, renderer, lazy registry, textbook directories and locale conventions. Identify the type/shape of all source text, pending resources and unanswered questions before coding.
3. Implement all **unblocked** assigned Scenes in owned code paths, with typed source-locale content only, source-visible TODOs for unresolved dependencies, meaningful accessibility/RTL behavior and co-located tests.
4. Generate/verify registration, run focused checks, categorize expected missing-locale errors distinctly from actual engineering defects, and audit/remove resolved TODOs.
5. Create/reuse appropriately scoped **Draft child PR(s)** targeting the verified active Lesson branch when separate Scene ownership warrants one; otherwise remain in that Lesson branch. Update the parent **Stage 6.3 tracker** with one row per Scene UUID: source/spec SHA, implementing PR/head, code/test/registry paths, actual checked results and blockers. **A child PR not yet reviewed and integrated is not 6.3 completion.** Work other ready Scenes without unnecessary prompts, and do not silently advance independent editorial/translation approvals.
6. Report exact Scene spec and revision, implementation and test paths, test commands/results, registry validation, source locale and remaining target locales, **all unresolved TODOs with location and issue**, blockers including media/a11y, and what specialist/agent should run next.

### Definition of done — engineering vs publication

**Stage 6.3 Scene implementation complete (engineering):** the full Lesson Scene UUID inventory (including nested Scene blocks) is implemented in real components; approved behaviors work; the correct source-locale data contract is typed; meaningful co-located tests pass; the registry resolves all UUIDs and the Lesson Section actually loads each Scene; source-level accessibility/offline requirements are demonstrated. All child work is integrated into the Lesson branch with exact evidence. **No essential behavior, required asset or TypeScript engineering error may remain pending.** Non-source target-language translations remain owned by Stages 9/10; distinguish those legitimate future gaps from 6.3 code defects. For a verified zero-Scene inventory, record N/A instead of fabricating a Scene.

**Scene production ready:** separately verified complete actual translations for every supported locale, all approved assets and accessibility alternatives available, no unresolved blocking TODOs, full TypeScript/build/registry/package/QA validation passing. **Only translation/release owners may mark these later gates complete.**

**Scope guard:** no YAML parser, no builder or generator for Lesson data, no Assessment Architect duties, no unauthorized translations, no new Course narrative, no hidden contracts refactor, and no false completion of incomplete features.

## Quest Task Scene specialization (future runtime integration)

A Quest Task contains exactly one Scene; see [Quest](../../docs/entities/quest.md). An approved Task Scene may eventually use Quest State/Actions contexts to request temporary media reaction playback and imperative transitions. Explicitly specify outcomes, retries, focus/keyboard interaction, nonvisual equivalents, pause/busy behavior and cancellation in the Screenwriter Scene spec. Quest-specific runtime actions are **not available** in the current Scene renderer; do not invent them, ship a mock controller as production, or use a ContentBlock workaround. Record this dependency until platform work adds the Quest controller and Section integration.
