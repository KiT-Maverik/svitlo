## Quest Section plans (Build contract exists; runtime pending)

A Quest is neither an ordinary ordered `blocks` Section nor a Quiz; see [Quest](../../docs/entities/quest.md). When the approved learning experience requires an isolated, stateful interactive workspace, the editorial `lesson.yaml` may describe `type: quest` with named Stage and Task proposals, including mandatory `start`, at least one Scene specification for each Task, all planned media/caption/accessibility production requirements and explicit branches determined by Scene actions. Never invent a `blocks` list or positional `order` inside Quest; record story-free learning flows in neutral Lessons and story missions in Episodes. This plan is _not_ a publishable Engine Quest: The YAML draft scaffolder and editor schema may support Quest, but the Lesson/Episode runtime Section union and UI remain pending. Maintain a specific nested `production` specification of the pending runtime dependency until implemented and independently validated.

## Source-content and implementation-quality requirements

The Stage 2 authored Config is **learner-facing material**, not a list of instructions for later agents to invent the material. For Text and Markdown, provide the real explanatory copy, questions and feedback in source-language `locale` fields. For Code, provide the actual source in the current `params.codeAsText` contract. Markdown must contain full examples, inline and displayed math where appropriate, with accessible verbal alternatives and correct literal-dollar handling; consult [Markdown ContentBlock](../../docs/entities/markdown-content-block.md). The Builder later extracts authored Markdown/Code into adjacent files. An empty block with `production.specification` alone is **not** a complete teaching block.

- **Structure and sequence:** organize coherent Sections into explicit ordered collections, identify their educational purposes, and provide meaningful teaching transitions. Avoid one-topic-per-UI-element padding; a single well-developed explanation can be better than artificial interaction.
- **Conceptual learning:** for each target outcome, provide grounded definitions, worked examples and counterexamples, error/misconception diagnosis, practice or thought exercises when useful, and accurate feedback with opportunities to adjust understanding. Different learner actions should serve different cognitive goals rather than mechanically repeating a pattern.
- **Assessment boundaries:** actual Quiz remains a Section, not a ContentBlock. Honor all Methodologist Quiz intents/target Skills/Assessment Methods. A checkpoint or exploratory Scene is formative interaction, not a substitute for the independent full Question Bank or scoring policy. Distinguish reviewed Question intentions from implemented Question IDs.
- **Media and Scenes:** use verified local media IDs or clearly marked pending resources; write production specs precise enough for a separate specialist to implement without guessing. State learner purpose, inputs/actions, transitions, expected feedback, numerical/content invariants, failure/recovery paths, text equivalents, captions/transcripts and device/accessibility constraints. Never bake unique user-facing copy into nonlocalizable image pixels without accessible text.
- **Technology honesty:** inspect implemented UI Kit/renderer before promising Scene/Quest interaction, graded behavior, offline availability or animations. Planned behavior can be reviewed at Stages 3–5 but must not be presented as shipped.
- **Source provenance:** maintain stable UUIDs/slugs and only actual source-locale copy; preserve exact teaching and source revisions through authorized edits. Do not infer `requireQuiz: false` just because the plan omitted an `assessmentPlan`.

This content quality checklist informs editorial reviews; schema validity at Stage 6 remains a separate technical check.
