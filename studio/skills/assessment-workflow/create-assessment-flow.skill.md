## Source ownership and paths

Follow the [canonical Assessment source layout](../../docs/entities/assessment.md#canonical-source-layout). Use the exact reserved placement under the Course tree, using `content/<assessmentSlug>/` at the immediate Course/Module/Chapter owner, without inventing intermediate `content/` folders for Chapters. The entity-owned `draft.ts` and final `index.ts` share this directory. Course Stage 5 initially emits only the inline placeholder in the immediate parent's configurator. Full materialization replaces that exact placeholder with the relative child import and emits slug-named Section/Block folders using the existing materializers. Never relocate a nested Assessment to a global directory.

## Relationship to the ten-stage Course Workflow

Course **Stage 6 Verify Questions Readiness** identifies real Lesson-owned Question Banks needed by Course-owned evaluations. Course **Stage 7 Design Assessments** applies only when the approved Course Stage 2 structure contains at least one `type: 'assessment'` slot, including nested Module/Chapter placements. It coordinates approved independent Assessment design via this eight-stage flow, preserving the actual UUID, path, selected Questions and separately authorized child PR. If the complete verified Course tree has zero Assessment slots, record Course Stage 7 **Skipped** at a verified source SHA in the **Course PR**, and do **not** create an Assessment PR. There are no Course/Module/Chapter Assessment-required flags or separate opt-outs. This does not skip any stage of an existing Assessment. Course Stages 8–9 handle only Course-owned translations; Stage 10 requires independent Assessment completion and human integrated QA before the Course may pass.

## One typed draft and direct trusted handoff

The allocated Course Stage 5 `draft.ts` starts as `assessmentSeed satisfies AssessmentWorkflowSeed`; it contains only the immutable Course-owned UUID, source-language title, ordered placement, exact reviewed Course blob, language plan, purpose and upstream Lesson placement paths (including additional Lessons). It is **not** Assessment Stage 1 completion. Authorized Stage 1 advances the **same** `draft.ts` to `AssessmentWorkflowStage1` with a concrete assessment design. Stage 2 advances that same source to `AssessmentWorkflowStage2`, using the existing Zod-inferred `lessonWorkflowContentSection_Schema` and `lessonWorkflowQuizSection_Schema` nodes, real selected Question UUIDs and documented resource requirements. Do not create a second source or manually edit a completed Quiz to bypass validation.

Before the independent Stage 3 review is finalized, the existing reviewed Stage 2 source must include precisely one ordinary direct call `materializeAssessment(reviewedAssessment)` imported from `@svitlo/engine/build`; the call is executed only by the credential-free worker after separate authorization, not during editorial authoring. The Engine Build export owns the Zod entry validation; no separate framework, parser or source replay is introduced. Record the final reviewed source Git SHA and ensure the Course handoff, upstream/extra Lesson integrations and reviewed Question selections are still the current revision. Use real Section/Block `index.ts` modules under that **same** nested Assessment path.

The trusted `/assessment materialize` command is implemented as default-branch `assessment-materialization.yml`, currently only in Draft PR #826. The gate accepts a same-repo Draft Assessment child PR that targets exactly the current owning Course branch, with only the allocated `draft.ts` changed and the Course-generated seed/parent source pinned. The tokenless analyzer loads the one TS entrypoint, verifies actual integrated upstream Lesson Question Banks, selected IDs, source/parent bytes, scope and bounded output. The write-token publisher never executes the reviewed source; it independently verifies all sealed SHA256 bytes and replaces the immediate parent's **one** inline placeholder, emits Sections/Blocks and consumes the draft in **one non-force commit**. Human review evidence remains editorial, not parsed by the technical gate. Do not invoke this command until deployed on default `develop` and validated using an authorized real Assessment PR; commenting does not itself prove success.

## Stages

1. **Design Assessment — Methodologist + Learning Assessment Architect.** Verify Course-approved purpose, placement, dependencies (including additional Lessons), actual completed upstream Lesson and reviewed bank sources, target Skills, scope, evidence and accessible assessment strategy. Author typed Stage 1 at the canonical Assessment-owned draft path. Do not duplicate upstream methodology or create banks.
2. **Create Assessment content — Learning Assessment Architect, with Screenwriter for supporting content if needed.** Advance the same draft to Stage 2 using existing Quiz/Content Section and Block contracts. Import the actual reviewed Lesson Question Configurators (not hand-copied UUID strings), use their `.id` in Quiz `params.selection.questionIds`, and specify scoring, feedback, locale and media requirements; no copied Questions or invented IDs.
3. **Independent review — separate qualified Assessment Architect context.** Correct the same source, independently check evidence coverage, selection ownership, scoring, accessibility and actual dependency readiness, record baseline/final SHA and verdict. Final typed direct materializer invocation uses the Stage 2 Zod-inferred contract.
4. **Materialize — Coding Agent, explicit owner authorization.** Use direct Engine materializer, ordinary TS imports, Zod validation at entry, bounded output manifest and trusted atomic Git publication. Generate the modular Configurator, Section/Block files and genuine resource specifications using existing materializers; replace the exact inline Course placeholder with the completed import while preserving UUID/order, consume draft atomically. No PR-prose parsing or alternate YAML. Keep unresolved resource blockers.
5. **Complete resources — Coding Agent / authorized media owner.** Verify assets, Scenes if supported, global assessment UUID resolution, required locales and all actual technical dependencies; retain blockers until genuine completion.
6. **Translation — Technical Translator.** Translate Assessment-owned text and resources only; upstream Question localization stays with its bank owner. Same entity PR.
7. **Independent translation review — separate translator context.** Verify exact source/locale scope and record pinned final verdict in same PR.
8. **QA — human.** Inspect Assessment in its owning Course, including navigation, selected Questions, feedback, grading, accessibility and locales. Record tested revision and explicit human verdict. Never infer QA from CI.

Track stages and revision evidence in the existing Assessment PR. Draft during edits; Ready after the authorized work is complete; merge is separately authorized. Missing upstream dependencies block Assessment authoring, not Course planning or draft preview. The Course's human QA must verify completed Assessment placements as part of integrated experience. No automatic creation of child PRs, bank production or next stage.

The implementation uses merged #823 direct materialization and the exact `/assessment materialize` command, **but it is not available on default `develop` until #826 is merged**. Verify the workflow and an authorized pinned Actions run before claiming it works end to end. Independent media/locale production, child human QA and Course Stage 10 human QA are separate release gates.
