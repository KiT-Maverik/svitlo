# Historical Translation Production Issue procedure

**Archived operational evidence, not the authoring protocol for new campaigns.** This is the pre-PR-only protocol retained to help authorized agents resume an already-open Translation Production Issue without losing its original scopes, review decisions or branch ownership. For new work use [Manage Translation Production](./manage-translation-production.skill.md); existing Issues remain live under their original approvals until individually reconciled. Do not open a new Production Issue, retroactively relabel an old review as approved, or treat this archive as authorization to merge.

# Manage Translation Production Skill

**Purpose:** Coordinate the **complete translation and independent linguistic-review campaign** for a fixed scope of one or more locale-bearing entities in a **single GitHub Issue**. Dynamically plan the number and content of parallel agent batches based on actual entity count, translatable fields, target languages, file ownership and complexity. Four translation agents is a common planning option, **not** a mandatory number. The PR topology is always **one integration PR targeting `main`**, plus bounded agent-subtask PRs targeting the integration branch. The _same_ Issue persists through the subsequent review phase.

Read applicable `AGENTS.md`, [GitHub labeling rules](../../rules/github-labels-and-naming.md), [Translation Workflow](./README.md), [Technical Translator Persona](../../personas/technical-translator.persona.md), [Technical Translation](./technical-translation.skill.md), [Review Translation](./review-translation.skill.md), current [Agent CI Artifacts architecture](../../docs/architecture/agent-ci-artifacts.md) and actual generator scripts/workflow. Inspect owner package instructions and live Contracts. GitHub facts must be rechecked rather than inferred from historical Issues.

## Issue scope and lifecycle

1. Use [historical Translation Production Issue Form](https://github.com/KiT-Maverik/svitlo/blob/65eb6b91d2fc4b67ee9a75157f0348b1d19b36a0/.github/ISSUE_TEMPLATE/translation-production.yml). An Issue is for **one fixed entity + locale campaign**, not one Issue per agent, locale, Lesson or stage. Input may be a list of Lesson UUIDs, Skill Domain/Group/Skill subtree, Course subtree, UI Kit dictionary or other specifically named locale-bearing resource. Resolve symbolic scopes to an **ordered, immutable inventory** of actual IDs and canonical source paths before dispatch. A later TOC/taxonomy change does not expand membership without documented owner approval.
2. Search for existing in-progress Translation Production Issues or integration PRs with the same scope, reuse or reconcile rather than duplicate. On issue creation apply real `content: *`, `shared: *`, `studio` or `repo: *` scope labels as applicable, `work: translation`, `work: review` and correct `source: *` label (not invented per-stage labels). `attention: blocked` only when actually blocked.
3. Verify the canonical source language, approved meaning, target locales and exact owning localized fields from Contracts and real files. "All remaining supported" must become an **explicit recorded language-code list** from the active registry, with intentional language-invariant fields excluded. Report missing source approvals and inconsistent identities instead of generating translations.
4. Record in the Issue an inventory source SHA, entity IDs/paths and count, locale roster, translatable field count/weights, required entity × target-locale coverage, exclusions, batch ownership, integration branch/PR, stage table and next handoff. Maintain the marker `<!-- svitlo-translation-production:v1 -->`. The Issue and PR links are the persistent cross-chat state; source code is authoritative for text.

**Creating an Issue authorizes planning only.** Never start unapproved content translation/merges merely because a form was submitted; follow its explicit authorization and established editorial gates.

## Automatic workload partitioning

Plan translation batches **before** agent branches are created:

- Enumerate a required work matrix of concrete `(entity ID or canonical field-group, target language code)` pairs. Record each pair in **exactly one** translation batch. Never omit a required target language or silently translate extra languages.
- Estimate work using actual entity volume, source-string counts/length, learner complexity, RTL, terminology difficulty, Quiz/Scene content, pending media captions/transcripts and file organization. Choose an efficient **number of parallel translators** (often four for substantial work; one or two for tiny work; more only if useful and independently executable). Aim for balanced effort rather than equal entity counts at all costs.
- **Prefer exclusive editable-file/subtree ownership**, e.g. divide Skills by complete Domain subtree or Lessons by entire Lesson UUID directory, with **all requested target languages for each owned entity** when locale dictionaries are co-located. This minimizes merge conflicts and lets each fully owned entity pass real typechecks. Divide a single entity across languages only when localization is actually stored in **independent locale-owned files** (or a tested safe, exclusive edit boundary). Do not assign concurrent agents overlapping `*.data.ts` files just because their requested language keys differ.
- For each planned batch specify exact entity/path list, exact language list, estimated workload, file-edit ownership boundary, agent label `Translation Agent N`, and proposed branch + Draft PR. Clearly record uncovered or conflicting pairs. Ensure `union(batches) == all required pairs` and `intersection(batches) == empty`.
- Read earlier completed translations and actual code; do not repeatedly translate already approved values unless the Issue explicitly requests retranslation. Distinguish missing translations from approved values in the inventory.
- The **owner sets review timing and scope per batch**, not the existence of an integrated all-translators baseline. Record assigned reviewer (different from original translator), source PR/SHA, selected mode (pre-integration on translator PR or post-integration on dedicated reviewer PR), correction/merge authorizations and mutually exclusive editable paths. Do not infer permission to start reviews or merge from Issue creation.

The coordinator can produce this plan without a fixed agent count and can continue authorized work **without asking "next" after every language/entity**. These instructions do not claim that ChatGPT automatically spawns separate asynchronous agents: agent sessions must be launched through available execution mechanisms or explicit assignments, while the Issue persists between them.

## Translation subtasks and owner-directed independent review

1. Create/reuse one Draft integration PR targeting `main`; each translator owns exclusive entity/locale fields in a Draft subtask PR targeting integration, with `Refs #N` and correct labels. Follow [Technical Translation](./technical-translation.skill.md), verify changed typed files and preserve actual language requirements.
2. **Start independent review only when the repository owner explicitly instructs it.** Pin the authorized reviewer, source PR/SHA and entity/locale scope. The reviewer must be independent of the author for that scope. There is **no all-translators-merged review prerequisite** unless the owner deliberately chooses that sequence.
3. **Pre-integration mode:** Review directly on the **existing translator Draft PR**, not a new reviewer PR. Generate the specific Code-derived localized Markdown there with a scoped command from a user with repository `write`, `maintain`, or `admin` access, such as `/agent-artifacts generate skills content/astronomy it` or equivalent verified Actions dispatch/local CLI. Verify that `manifest.json` reflects the reviewed PR source commit and assigned documents are complete (`missing === 0`, `reviewReady === true`, no relevant failures). Review the complete assigned document, not merely the Git diff.
4. **Post-integration mode (optional):** If the owner requests a later review, pin its integrated source SHA and create a separate Draft reviewer subtask PR targeting integration. Generate and validate the assigned Markdown on that reviewer PR branch, never on integration itself.
5. **Artifact stop gate for either mode:** Verify an actual working entity/locale-specific Code→Markdown generator. If absent, unsupported, incomplete, failing or stale, stop **the affected review**, report the exact script, entity and locale in chat/Issue, and do not fabricate translations or replace required generated views with manual source scanning.
6. Review all assigned content independently against approved meaning, grammar, terminology, register and accessibility. Review is initially read-only. If the owner/Issue authorizes fixes, follow Technical Translation and edit **only approved canonical typed locale fields on the working PR branch**. Regenerate the affected Markdown after correction and verify it again.
7. **When the owner authorizes handoff after review**, clean `.agent-ci-artifacts/` from the **translator PR** using `/agent-artifacts cleanup`, verify final diff and source SHA, pass meaningful scoped validation, inspect current PR head/base and GitHub merge requirements, then merge **that same reviewed translator PR** into integration. Confirm and record the merged SHA in the Issue. Unrelated global CI failures must be diagnosed and disclosed, not treated as linguistic evidence, silently ignored or bypassed by weakening gates. Other translator PRs may remain unmerged.
8. For optional dedicated reviewer PRs, clean artifacts before merging approved corrections. Re-review materially altered source when necessary. Keep the parent integration PR Draft until separately authorized Ready/final merge to `main`.

**Permission boundaries:** A Production Issue authorizes planning only by default. Review start, permitted fixes and per-subtask merge authority must be explicit in the owner's request or Issue. Never claim all translation checks passed merely because one scoped review succeeded.

## Recording completed reviews without Markdown reports

For entities with a typed `review.ts` contract, **that entity-owned file is the canonical persistent index of verified review PRs**; do not create a second permanent `*-review.md` or per-locale review-history file. The PR and production Issue hold detailed findings, exact reviewed source SHA, review scope and evidence of authorized sign-off. Do not label a PR value as approval without verifying the real gate.

For Lessons once Engine `LessonReview` and assembled-Props revision binding exist, the integration coordinator records **one** completed AI language-review integration PR in `ai.locales` after all Lesson locales have been reviewed, not one PR per language/agent. Individual verified **human** language reviews are recorded in `human.locales[language]`; only the owner/authorized coordinator fills `human.acceptance`. Do not invent Review schemas for other entity kinds; use their actual Engine type if available, and leave a precise pending handoff in the Issue when the target `review.ts` does not exist or the Props revision cannot yet be checked.

If a review adopts a **narrow entity- or locale-specific linguistic decision**, add a brief `//` comment immediately above its PR number in `review.ts` (or above the single AI `locales` integration PR, naming the locale). Do not propagate such a comment as a system-wide rule or make a long Markdown report. Reviewer PRs stay read-only unless corrections are explicitly authorized; the coordinator makes this final verified record without changing translation meaning.

## GitHub Issue as persistent coordination state

Use the Issue Form fields **Package or owning workspace**, **Entity type**, **Entity scope**, **Source and target languages**, **Requirements and integration constraints**, **Coordinator work plan**, **Integration and review gates**, **Durable handoff, blockers and evidence**. Maintain a single stable table with **translation/review phase**; batch scope, exact locales, workload, owner, branch, PR and status: `planned`, `in-progress`, `ready-for-review`, `merged`, `blocked`, `complete`. Distinguish translation `merged` from linguistically `reviewed`.

For `Continue Translation Issue #N`: read the actual current Issue body/comments, integration PR & branches, related agent PRs, source code, supported-language registry, generator and current artifacts. Compare to the recorded plan, reconcile stale state and check parallel ownership before continuing. Work all available tasks **within the assigned agent's authorized phase/role**. Do not silently perform independent review of your own translation to "finish" the Issue.

The Issue-level gates summarize verifiable state; check only when **all required entity-locale pairs** have passed that gate. Link meaningful PR/commit/CI/artifact evidence; avoid copy-pasting large translation source data into Issue. Re-fetch/reconcile the Issue before edits (GitHub Issue comments/edits are not a lock). Never close the Issue because one agent PR merged.

## Final promotion and close

After verified complete translations, full independent review coverage, resolved blockers, successful checks and **no tracked `.agent-ci-artifacts/` in integrated tree or diff**, report completion with totals and PR references. **Final integration PR → `main` requires explicit user authorization; do not auto-merge**. Only after successful final integration merge may the coordinator close the production Issue as completed (`Closes #N` only on the parent integration PR if authorized).

No universal "four agents" constant, no fixed language-bucket table, no new GitHub Actions workflow, no automatic reviewer start from an unmerged subtask. Every stage is resumable from the same Issue across agents/chats.
