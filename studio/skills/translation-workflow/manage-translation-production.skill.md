# Manage Translation Production Skill

**Purpose:** Coordinate the **complete translation and independent linguistic-review campaign** for a fixed scope of one or more locale-bearing entities in a **single GitHub Issue**. Dynamically plan the number and content of parallel agent batches based on actual entity count, translatable fields, target languages, file ownership and complexity. Four translation agents is a common planning option, **not** a mandatory number. The PR topology is always **one integration PR targeting `main`**, plus bounded agent-subtask PRs targeting the integration branch. The _same_ Issue persists through the subsequent review phase.

Read applicable `AGENTS.md`, [GitHub labeling rules](../../rules/github-labels-and-naming.md), [Translation Production architecture](../../docs/architecture/translation-production-workflow.md), [Technical Translator Persona](../../personas/technical-translator.persona.md), [Technical Translation](./technical-translation.skill.md), [Review Translation](./review-translation.skill.md), current [Agent CI Artifacts architecture](../../docs/architecture/agent-ci-artifacts.md) and actual generator scripts/workflow. Inspect owner package instructions and live Contracts. GitHub facts must be rechecked rather than inferred from historical Issues.

## Issue scope and lifecycle

1. Use [Translation Production Issue Form](../../../.github/ISSUE_TEMPLATE/translation-production.yml). An Issue is for **one fixed entity + locale campaign**, not one Issue per agent, locale, Lesson or stage. Input may be a list of Lesson UUIDs, Skill Domain/Group/Skill subtree, Course subtree, UI Kit dictionary or other specifically named locale-bearing resource. Resolve symbolic scopes to an **ordered, immutable inventory** of actual IDs and canonical source paths before dispatch. A later TOC/taxonomy change does not expand membership without documented owner approval.
2. Search for existing in-progress Translation Production Issues or integration PRs with the same scope, reuse or reconcile rather than duplicate. On issue creation apply real `content: *`, `shared: *`, `studio` or `repo: *` scope labels as applicable, `work: translation`, `work: review` and correct `source: *` label (not invented per-stage labels). `attention: blocked` only when actually blocked.
3. Verify the canonical source language, approved meaning, target locales and exact owning localized fields from Contracts and real files. "All remaining supported" must become an **explicit recorded language-code list** from the active registry, with intentional language-invariant fields excluded. Report missing source approvals and inconsistent identities instead of generating translations.
4. Record in the Issue an inventory source SHA, entity IDs/paths and count, locale roster, translatable field count/weights, required entity × target-locale coverage, exclusions, batch ownership, integration branch/PR, stage table and next handoff. Maintain the marker `<!-- svitlo-translation-production:v1 -->`. The Issue and PR links are the persistent cross-chat state; source code is authoritative for text.

**Creating an Issue authorizes planning only.** Never start unapproved content translation/merges merely because a form was submitted; follow its explicit authorization and established editorial gates.

## Automatic workload partitioning

Plan translation batches **before** agent branches are created:

- Enumerate a required work matrix of concrete `(entity ID or canonical field-group, target language code)` pairs. Record each pair in **exactly one** translation batch. Never omit a required target language or silently translate extra languages.
- Estimate work using actual entity volume, source-string counts/length, learner complexity, RTL, terminology difficulty, Quiz/Scene content, pending media captions/transcripts and file organization. Choose an efficient **number of parallel translators** (often four for substantial work; one or two for tiny work; more only if useful and independently executable). Aim for balanced effort rather than equal entity counts at all costs.
- **Prefer exclusive editable-file/subtree ownership**, e.g. divide Skills by complete Domain subtree or Lessons by entire Lesson UUID directory, with **all requested target languages for each owned entity** when locale dictionaries are co-located. This minimizes merge conflicts and lets each fully owned entity pass real typechecks. Divide a single entity across languages only when localization is actually stored in **independent locale-owned files** (or a tested safe, exclusive edit boundary). Do not assign concurrent agents overlapping `*.data.ts` files just because their requested language keys differ.
- For each planned batch specify exact entity/path list, exact language list, estimated workload, file-edit ownership boundary, agent label `Translation Agent N`, and proposed branch + Draft PR. Clearly record uncovered or conflicting pairs. Ensure `union(batches) == all required pairs` and `intersection(batches) == empty`.
- Read earlier completed translations and actual code; do not repeatedly translate already approved values unless the Issue explicitly requests retranslation. Distinguish missing translations from approved values in the inventory.
- Review batches are **planned after translations are integrated** from the actual final baseline, rather than copy-pasting the translator allocations. Rebalance independently by language/domain and complexity; use reviewer identity different from the translator responsible for the assigned content whenever feasible. Maintain exclusive correction-file ownership across concurrent review PRs. If language-based review of co-located files would cause conflicts, sequence corrections in a single integration coordinator while reviewers produce independent reports, or partition by files instead.

The coordinator can produce this plan without a fixed agent count and can continue authorized work **without asking "next" after every language/entity**. These instructions do not claim that ChatGPT automatically spawns separate asynchronous agents: agent sessions must be launched through available execution mechanisms or explicit assignments, while the Issue persists between them.

## Phase A — Translation through a single integration PR

1. Check whether the designated integration branch and its **Draft integration PR → `main`** already exist. Reuse both. If absent, branch from current `main` and create a real, minimal, legitimate coordination/source-baseline commit if a diff is needed to open the PR; do not alter educational content just to manufacture a diff. Immediately link the PR and branch in the Issue.
2. If source-locale typed entities need to be generated, the authorized coordinator creates/validates the **shared baseline on the integration branch once**, before translator branches start. Ensure stable UUIDs and field definitions. A generator missing for initial authoring is a separate blocker; do not improvise unsupported contracts.
3. **Every Translation Agent N** branches from the **current integration SHA**, and opens a **Draft agent-subtask PR → integration branch**. Never target `main`; use actual repo labels `pr: agent-subtask`, `work: translation` and the owning package scope. Reference the parent Issue with `Refs #N` and list exact assigned entities/locales; no `Closes` on subtasks. Do not edit another batch's files or shared baseline.
4. Follow [Technical Translation](./technical-translation.skill.md) and Persona requirements: real source meaning, audience-appropriate prose, correct terminology, RTL/bidi, placeholders, `qm` orthography and **no fake copied translations**. Use the actual field and locale types, preserve IDs, source content, imports, format and methodologically English-only metadata.
5. Run relevant typechecks covering **actual changed `data/**/*.ts` files** and localization tests; don't weaken types to get green. Full workspace checks can fail while other integration work is unfinished; accurately report that state and run the strictest meaningful scoped checks, respecting Technical Translation's acceptance gate. Do **not** mark a batch fully complete on false CI success.
6. Once a batch passes its assigned translation gates and the permitted PR/approval policy, coordinator merges the **agent PR into integration**. Independently verify the merged commit and update the Issue, before other agents base new edits on that integrated state. Keep the parent integration PR Draft. Agents should not independently merge to `main`.
7. Before review, confirm **every required pair has one real translation, all translation agent PRs are actually merged into the integration branch**, and the integrated tree passes a valid completeness/structural/typecheck gate (or exact outstanding blockers are recorded). Record **immutable integrated translation SHA**, inventory/locale roster and explicit `translation-integrated` milestone.

**HARD REVIEW BARRIER:** no Translation Review Agent may start reviewing while _any_ required translation agent PR remains unmerged or integrated translations are incomplete. An agent PR's green checks or a nonmerged source branch are not enough.

## Phase B — Independent Translation Review of integrated content

1. On the **integration branch after all translation subtask merges**, verify the entity-specific **Code → localized Markdown generator exists**, supports the requested entity type, exact language codes and current folder/contract schema, and emits complete human-readable learner-facing content for every assigned entity. Inspect actual script(s), CLI, Agent CI Artifacts adapter, workflow and [manifest](../../docs/architecture/agent-ci-artifacts.md) contract. Example existing CLI families: Skills `scripts/generate-skills-taxonomy.mjs` and Lessons `scripts/generate-lessons-markdown.mjs`. **A script existing by filename is insufficient**: prove it supports the actual scoped entities (including nested types and Question/Section content where applicable).
2. **ABSOLUTE STOP GATE:** If the required generator is absent, does not support the entity type, fails for the selected locales, or cannot generate faithful per-entity localized Markdown, **immediately stop the assigned review stage**. Explicitly tell the user **in chat** which generator/adapter/output is missing, which entity/locale scope is blocked and what must be built or repaired. Set the Issue stage to `blocked` with exact generator dependency. **Do not** substitute manual traversal of `*.data.ts`, guess localized strings, mark the review done, or silently change its scope. Resume only after the real generator is available and verified.
3. Freeze review baseline SHA from integration after translation. Plan independent review-agent batches with **exhaustive, disjoint `(entity, locale)` coverage**, balanced effort and separate ownership from translation where feasible. Link the baseline SHA, exact review document paths and review agent PR plans in the Issue.
4. Each **Review Agent N** creates a branch from the **frozen integrated translation SHA**, not from `main` or an unmerged translator branch. Open a **Draft review subtask PR → the same integration branch**. A legitimate temporary review seed is allowed only if necessary for GitHub to create a PR and must be removed before merge. Reference the parent Issue; PR is review work, not the parent integration.
5. Generate _real_ `.agent-ci-artifacts/<entity-kind>/.../<language>.md` on that reviewer PR branch, using on-demand `/agent-artifacts generate` (repo owner action), manual workflow dispatch, or verified supported CLI in a local checkout. The current workflow may generate **all languages at once**; reviewers read the assigned subset. Do not claim per-locale generator switches exist unless actually supported. Only agent PR branches own temporary Markdown, **never the integration branch or main**.
6. Inspect `.agent-ci-artifacts/manifest.json` for generator success, `sourceCommit` matching the **expected integrated translations source** (or a later explicitly verified reviewed correction commit), all assigned document paths and no relevant failures. The exact generated content must come from merged integrated translations, not stale initial baseline or unmerged translator work. An absent/stale/failed artifact is a **hard blocker** with explicit chat+Issue report, not a permission to read raw source instead.
7. Apply [Review Translation](./review-translation.skill.md) and [Technical Translator Persona](../../personas/technical-translator.persona.md): independently compare each localized entity to approved source meaning, terminology, educational register, RTL/bidi and UI context; record reviewed count, errors by category, specific source links, evidence, coverage and unresolved uncertainties. Reviewers must not review only the changed diff: inspect their **complete assigned entity × language coverage**.
8. Review is independent and initially **read-only**. If corrections are authorized, follow [Technical Translation](./technical-translation.skill.md) on canonical typed source, not generated Markdown. Coordinate exclusive correction-file ownership. Recreate/refresh artifact reference if the underlying source changed and re-verify manifest/locale meaning. A no-change review may be reported in Issue with verified artifact proof and need not fabricate a source diff.
9. **Before merging each reviewer PR**: use `/agent-artifacts cleanup` (or workflow dispatch) on the reviewer PR and verify `.agent-ci-artifacts/` is absent in its final diff/tree. A PR carrying temporary references MUST NOT be merged into integration. If cleanup isn't available, stop and report the blocker. Mark reviewer coverage `complete` only after actual inspection + necessary corrections + cleanup and verification; do not infer it from CI alone.
10. Merge approved reviewer corrections to integration as allowed, preserving traceable report/Issue evidence. Revalidate integrated translations, and if later corrections materially change a locale, re-review that affected scope against a newly generated artifact. The integrated PR remains Draft until owner explicitly requests review readiness/final merge.

## GitHub Issue as persistent coordination state

Use the Issue Form fields **Package or owning workspace**, **Entity type**, **Entity scope**, **Source and target languages**, **Requirements and integration constraints**, **Coordinator work plan**, **Integration and review gates**, **Durable handoff, blockers and evidence**. Maintain a single stable table with **translation/review phase**; batch scope, exact locales, workload, owner, branch, PR and status: `planned`, `in-progress`, `ready-for-review`, `merged`, `blocked`, `complete`. Distinguish translation `merged` from linguistically `reviewed`.

For `Continue Translation Issue #N`: read the actual current Issue body/comments, integration PR & branches, related agent PRs, source code, supported-language registry, generator and current artifacts. Compare to the recorded plan, reconcile stale state and check parallel ownership before continuing. Work all available tasks **within the assigned agent's authorized phase/role**. Do not silently perform independent review of your own translation to "finish" the Issue.

The Issue-level gates summarize verifiable state; check only when **all required entity-locale pairs** have passed that gate. Link meaningful PR/commit/CI/artifact evidence; avoid copy-pasting large translation source data into Issue. Re-fetch/reconcile the Issue before edits (GitHub Issue comments/edits are not a lock). Never close the Issue because one agent PR merged.

## Final promotion and close

After verified complete translations, full independent review coverage, resolved blockers, successful checks and **no tracked `.agent-ci-artifacts/` in integrated tree or diff**, report completion with totals and PR references. **Final integration PR → `main` requires explicit user authorization; do not auto-merge**. Only after successful final integration merge may the coordinator close the production Issue as completed (`Closes #N` only on the parent integration PR if authorized).

No universal "four agents" constant, no fixed language-bucket table, no new GitHub Actions workflow, no automatic reviewer start from an unmerged subtask. Every stage is resumable from the same Issue across agents/chats.
