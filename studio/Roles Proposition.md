# Roles Proposition — AI-команда для створення навчального контенту

> **Світло · Architecture proposal / knowledge preservation**
>
> **Дата:** 27 жовтня 2026 року  
> **Статус:** погоджена на концептуальному рівні **чотирирольова модель**; це **пропозиція для майбутніх repository skills**, а не вже реалізований multi-agent runtime або готові інструкції агентам.  
> **Мета:** зберегти, _навіщо_ ми розділили відповідальності, _які альтернативи_ розглядали, _що має передаватися між ролями_ і _як_ згодом оформити це в custom skills.

## 1. Навіщо взагалі потрібні ролі

Svitlo має створювати багато повторно використовуваних, локалізованих, доступних і педагогічно коректних інтерактивних уроків. Є ризик доручити одному AI-агенту одразу **визначення компетенцій, педагогіку, сценарій, запитання, мультимедіа, код та тести** — і отримати результат, який виглядає завершеним, але має непомітні методичні або технічні проблеми.

Ролі — це **логічні способи мислення та контракти відповідальності**, а не обов'язково чотири різні моделі, процеси або платні AI-виклики. На першому етапі їх можна використовувати як послідовні repository skills/prompts з окремими результатами. Одна модель може виконувати різні ролі по черзі, якщо чітко відокремлює артефакти й критерії перевірки.

**Головне правило:** кожна роль вирішує _своє_ питання і не підмінює результат попередньої ролі без явного повернення на відповідний етап.

## 2. До якого складу прийшли

**Чотири основні ролі:**

| Роль                                                      | Головне питання                             | Основна відповідальність                                                                                   |
| --------------------------------------------------------- | ------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| **Methodologist / Методист**                              | **ЧОГО та НАВІЩО навчати?**                 | Компетенції, цілі навчання, передумови, очікувані результати та педагогічна коректність                    |
| **Educational Screenwriter / Навчальний сценарист**       | **ЯК це пояснити й пережити?**              | Подача уроку, послідовність секцій, приклади, інтерактиви, медіа та навчальний досвід                      |
| **Learning Assessment Architect / Архітектор оцінювання** | **ЯК достовірно перевірити засвоєння?**     | Завдання, критерії оцінювання, типові помилки, валідність перевірки й покриття компетенцій                 |
| **Coding Agent / Технічний виконавець**                   | **ЯК реалізувати це в архітектурі Svitlo?** | Типізовані конфіги, інтеграція з компонентами/генераторами, реалізація, тести та відповідність репозиторію |

Це **логічні ролі**. Людина залишається редактором і власником остаточного рішення, особливо для математики, оцінювання, доступності, чутливих контекстів і зміни архітектури.

## 3. Methodologist — методист

**Місія:** перетворити широку тему на чіткий педагогічний результат, який можна незалежно перевірити.

**Вхідні дані:** запитана тема/предмет, цільова аудиторія (як контекст програми, не як атрибут Skill), наявна Skills Taxonomy, відповідні предметні джерела, обмеження уроку й локалей.

**Відповідальність:**

- Визначає навчальну мету, необхідні знання, передумови, логіку руху від простого до складнішого та межі теми.
- Добирає **вже наявні** Skill ID; пропонує нові Skill або їхнє розділення лише за правилами [Skill entity rules](./docs/entities/skill.md), без непогодженої зміни каталогу.
- Розрізняє **окреме вміння** та **складену/інтеграційну компетенцію**. Підсвічує ризики, коли учень може знати A, але не B.
- Описує конкретний результат: _після навчання учень зможе…_; встановлює межі достатньої глибини, а не винаходить випадкові вправи.
- Перевіряє предметну точність та педагогічні ризики, зокрема хибні узагальнення, невірну складність і непідтверджені припущення.

**Вихід (майбутній формат):** короткий **Learning Brief**: мета, перелік Skill ID, prerequisites як **окрема зовнішня відповідність**, очікувані спостережувані результати, педагогічні обмеження, відомі misconceptions, критерії успішності _в загальному сенсі_, питання до сценариста й оцінювача.

**Не відповідає за:** написання всіх сцен/анімацій, побудову компонентів, конкретні UI-патерни, технічні тести, виставлення оцінки конкретному учню.

## 4. Educational Screenwriter — навчальний сценарист

**Місія:** з методичного задуму створити послідовний, зрозумілий та захопливий навчальний досвід.

**Вхідні дані:** затверджений Learning Brief, список Skill ID, контекст наявних інструментів/компонентів і обмеження доступності.

**Відповідальність:**

- Проєктує **Lesson** як композицію навчальних секцій: пояснення, приклади, візуалізації, спроби учня, практику, підсумок; не прив'язує кожен Lesson до одного жорсткого шаблону.
- Продумує структуру вступу, переходи, ритм, когнітивне навантаження, мову пояснень і педагогічно значущі ілюстрації.
- Визначає, **де потрібна інтерактивність**: маніпуляція об'єктами, симуляція, matching, ordering, практична сцена; не замінює взаємодію анімацією заради ефекту.
- Продумує **візуальну й медійну режисуру**: SVG/React/Remotion-анімації, озвучення, локалізаційні нюанси, адаптацію до мобільного екрана, RTL, reduced motion та доступність.
- Де потрібно, описує **Program-specific storytelling**: маскот, пригода, подорож, сюжетні вставки. Водночас **Lesson залишається самодостатнім**: основні знання не мають залежати від конкретної Program.
- В майбутньому може позначати **бажані injection slots** або реакції на події уроку, але **не вигадує, що поточний код уже підтримує ці механізми**.

**Вихід:** **Lesson Script / Storyboard**: секції з чіткою метою, пояснення, приклади, очікувані дії учня, умови показу/переходу, вимоги до ілюстрацій та локалізації, список ресурсів і можливі Program-enhancement opportunities.

**Не відповідає за:** визначення нових Skill без методиста, виставлення балів, проєктування статистичної достовірності оцінювання, необґрунтовану зміну правильної відповіді, самовільне розширення TypeScript-контрактів.

## 5. Learning Assessment Architect — архітектор оцінювання

**Місія:** отримати достовірне свідчення того, що учень **справді володіє** потрібним Skill, а не лише переглянув матеріал чи вгадав відповідь.

**Вхідні дані:** Learning Brief, пов'язані Skill ID, Lesson Script, наявні Question/Quiz/Generator контракти.

**Відповідальність:**

- Формує план перевірки: **яку компетенцію** підтверджує кожне запитання, яке спостереження є достатнім та що не можна зробити висновком з однієї відповіді.
- Проєктує Question, Flashcard, Practice, Assessment та завдання-генератори з чіткими правильними відповідями, поясненнями, допустимими альтернативами та діагностичними distractors.
- Розділяє **тренування** (можливі hints, instant feedback, retry) і **діагностичне оцінювання** (задані правила, поріг, ваги, стійкість до вгадування та підказок).
- Перевіряє, чи не тестується випадково інша навичка: складна мова умови, прихована вимога читання, залежність від швидкості, випадковий формат тощо.
- Враховує типові помилки, крайні випадки, повтори, змішані компетенції, пояснюваність помилки та рівень доказовості.
- Для програмно згенерованих задач визначає обмеження аргументів, інваріанти правильності, seed-based reproducibility й перевірку відсутності неможливих варіантів.

**Вихід:** **Assessment Specification**: mapping `question → Skill ID(s)`, формат та умови, правильність, критерії оцінювання, hints/retry policy, validation rules, expected misconceptions і перевірки якості.

**Особливо важливе правило:** якщо Question має два Skill ID, **один правильний результат не автоматично є незалежним доказом mastery обох**. Методист визначає сутність компетенцій, Assessment Architect — що реально можна оцінити через запропоноване завдання.

**Не відповідає за:** сюжет і маскот, дизайн усіх медіа, створення архітектурних ID та сутностей за власною ініціативою, реалізацію UI або зберігання персонального прогресу без зовнішнього контракту.

## 6. Coding Agent — технічний виконавець

**Місія:** перетворити погоджені педагогічні артефакти на **підтримуваний, типобезпечний, тестований** код Svitlo.

**Вхідні дані:** Learning Brief, Lesson Script, Assessment Specification, чинні `AGENTS.md`, `src/types`, builders, компоненти, локалі та супровідні `Experience` документи.

**Відповідальність:**

- Використовує наявну архітектуру, типи й компоненти; не винаходить другу паралельну систему Question, Skill або Lesson.
- Створює/оновлює необхідні `*.data.ts`, `*.ids.ts`, контентні локалі, інтерактивні сцени, адаптери та компоненти.
- Дотримується правил [Implement Skill Code](./skills/skill-taxonomy-workflow/implement-skill-code.skill.md) для UUID, локалізацій, іменованих словників і collection-scoped exports.
- Перевіряє типізацію, unit/integration/component/E2E-тести там, де це доречно, а також accessibility, поведінку на мобільних пристроях, SSR і performance.
- Зберігає коректну сепарацію: Lesson content ≠ Program narrative ≠ Assessment results ≠ Skill mastery; не прошиває випадкові дані одного уроку в універсальні компоненти.
- Якщо специфікація неможлива в поточному API, **не вигадує мовчки новий контракт**: описує обмеження, пропонує вузьку зміну та погоджує або явно фіксує рішення відповідно до умов задачі.

**Вихід:** робоча зміна коду (branch/PR), результати тестів, перелік створених сутностей, технічні ризики, невирішені питання та відхилення від вихідної специфікації.

**Не відповідає за:** самовільну зміну методичних цілей, семантики Skill, навчальної правильності чи критеріїв оцінювання заради спрощення реалізації.

## 7. Чому саме чотири: які ролі розглядали й об'єднали

Обговорювали детальніший розподіл, але є ризик зайвих handoff-ів та ролей із дубльованою відповідальністю.

| Запропонована допоміжна роль        | Підсумкове рішення                                         | Причина                                                                                                                                  |
| ----------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **Creative / Media Director**       | **Включити до Educational Screenwriter**                   | Візуальна мова, медіа та анімації мають підтримувати навчальний сценарій, а не існувати самі по собі                                     |
| **Interactive Experience Designer** | **Включити до Educational Screenwriter**                   | Інтерактивність — частина педагогічної подачі; окрема постійна роль створювала б перекриття з режисурою уроку                            |
| **Subject Expert**                  | **Не додавати як п'яту постійну core-role на цьому етапі** | Предметні вимоги входять у відповідальність методиста, але **людська предметна експертиза** все одно потрібна для складних/ризикових тем |
| **QA Reviewer / Editor**            | **Не додавати як п'яту core-role зараз**                   | Перевірка якості має відбуватися на кожному етапі; за необхідності незалежний review може бути окремим проходом або skill                |
| **Technical Producer**              | **Не виділяти окремо зараз**                               | Технічна композиція й інтеграція належать Coding Agent; потребу в окремому coordination role можна оцінити пізніше                       |

**Це не заборона на спеціалізовані ролі в майбутньому.** Якщо стане зрозуміло, що дизайнер анімацій або незалежний рецензент знижує кількість помилок, його можна оформити як допоміжний режим/skill — без зміни основної чотирирольової схеми.

## 8. Потік роботи та handoff-и

```text
User / Editor: тема, цілі, обмеження, домен
                │
                ▼
          [Methodologist]
            Learning Brief
             /         \
            ▼           ▼
 [Educational Screenwriter]   [Assessment Architect]
      Lesson Script            Assessment Specification
            \                   /
             \                 /
               ▼             ▼
                  [Coding Agent]
                      │
                 Code + Tests
                      │
                      ▼
              Review / Feedback
                      │
               (повернення до
               відповідної ролі)
```

**Уточнення:** сценарист і архітектор оцінювання можуть працювати паралельно після методиста, але перед реалізацією потрібна **узгоджена версія** Storyboard і Assessment Specification. Це не «конвеєр без зворотних зв'язків».

### Мінімальні критерії приймання кожного етапу

1. **Після методиста:** є вимірювані learning outcomes, обрані Skill IDs, обґрунтовані prerequisites та явні припущення.
2. **Після сценариста:** кожна активність має педагогічну функцію; є порядок секцій і зрозумілий сценарій без обов'язкової сюжетної надбудови.
3. **Після архітектора оцінювання:** кожен assessed Skill має релевантні задачі; критерії та edge cases однозначні; немає фальшивих висновків про mastery.
4. **Після виконавця:** code review, контрактні/типові перевірки, тести, локалізації, доступність і підтверджені відомі обмеження.
5. **Перед публікацією:** людська або незалежна редакційна перевірка, особливо правильності математики, пояснень, перекладів, accessibility та policy-sensitive матеріалів.

### Приклад одного розділу

**Тема:** «Лічба з кроком 2».

- **Methodologist:** вибирає вже наявний Skill, наприклад `steps_Skills_Ids.countBy2`; формулює, що учень має вміти продовжувати послідовності по два й розуміти групування, не лише завчити ряд.
- **Screenwriter:** створює історію пояснення з предметними парами, інтерактивним групуванням і поступовим переходом до символів. Можлива пригода з маскотом — **необов'язкова Program-надбудова**.
- **Assessment Architect:** проєктує декілька незалежних перевірок (побудова послідовності, групи предметів, типова помилка з пропущеним кроком) і пояснює, що саме кожна з них доводить.
- **Coding Agent:** реалізує урок, вправи, ресурси та тести, посилаючись на статичний UUID із `*.ids.ts`, без копіювання Skill-конфігу в урок або генерації нового UUID.

## 9. Інваріанти: що не можна змішувати

- **Skill** описує компетенцію; не зберігає оцінку, mastery, клас, формат Question або сюжет Program.
- **Lesson** — самодостатній навчальний контент; **Program** — зовнішній сценарій, обгортка/маршрут/маскоти/ін'єкції/реакції на події. Система подій та ін'єкцій поки **концептуальна**, не оголошена стабільним контрактом.
- **Assessment** визначає, як перевірити знання; **Progress/Evidence/Analytics** інтерпретують результати конкретних спроб і учнів.
- **Creative decisions** не повинні підміняти learning goals; а **coding convenience** не повинна підміняти педагогічну істину.
- Переклади, RTL, доступність, предметна коректність і непорушення вихідних авторських прав — наскрізні вимоги для всіх чотирьох ролей.
- Відсутність деталізації в upstream-spec — **підстава зафіксувати ризик/питання**, а не вигадати ключове методичне рішення під час написання коду.

## 10. Як це може стати repository skills

**[Пропозиція; не створювати автоматично зараз.]** Спочатку варто спроєктувати **4 незалежні skills**, кожен із чіткими входами, виходами, checklist і правилами відмови від позарольових рішень.

| Майбутній skill (робоча назва)    | Очікуваний artifact                              |
| --------------------------------- | ------------------------------------------------ |
| `svitlo-methodologist`            | `LearningBrief` / mapped learning goals          |
| `svitlo-educational-screenwriter` | `LessonScript` / storyboard                      |
| `svitlo-assessment-architect`     | `AssessmentSpec` / coverage mapping              |
| `svitlo-coding-agent`             | PR із конфігами, компонентами, тестами та report |

Ці назви — **робочі**, не затверджені шляхи чи маніфести. Не вводити відразу обов'язковий MCP orchestration layer: спершу перевірити, чи чотири незалежні prompts/skills з однаковими артефактними контрактами покращують якість.

**Практична структура кожного skill:**

- **Purpose + trigger:** коли запускати, що не робити.
- **Required context:** потрібні документи, типи, історія предмета, набори локалей.
- **Input contract:** які артефакти попередньої ролі обов'язкові; що робити, коли їх бракує.
- **Procedure:** етапи роботи без прихованих змін scope.
- **Output contract:** machine-readable або перевірний Markdown/JSON/TS формат (після вибору).
- **Quality gates:** рольові критерії, інваріанти і review checklist.
- **Handoff:** кому передати, що є рішенням, а що пропозицією чи нез'ясованим питанням.

### Відкриті рішення для майбутньої реалізації

1. Чи зберігати артефакти ролей у Git поруч із Lesson, в окремому каталозі специфікацій, чи генерувати тимчасово під задачу.
2. Як версіонувати `LearningBrief`, `LessonScript`, `AssessmentSpec` та зв'язувати їх з Lesson/Skill UUID без дублювання сутностей.
3. Де розмістити незалежний factual/pedagogical review: quality gate між етапами, окремий optional skill чи людська перевірка.
4. Як передавати зміни з Assessment Architect назад до Methodologist або Screenwriter без створення суперечливих «джерел істини».
5. Коли залучати локалізацію та accessibility review: обов'язково на кожному етапі чи окремим фінальним проходом.
6. Як оцінити ефективність: частота методичних дефектів, покриття Skill, стабільність схем, кількість повернень між ролями, витрати/час, точність контенту.
