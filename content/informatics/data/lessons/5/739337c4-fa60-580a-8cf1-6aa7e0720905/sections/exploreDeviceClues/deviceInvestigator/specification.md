# Сцена «Як працює ця річ?» — окремий виробничий ресурс
Мета: дати дитині дослідити роль вхідних даних, обробки та результату в шести побутових випадках; не замінює Question Bank чи оцінювання mastery. Компонент Scene для цього UUID НЕ реалізовано й НЕ зареєстровано; це повний бриф для окремої санкціонованої Scene Production, не інструкція Stage 6 реалізувати його.

## Дані й послідовність
Використовувати саме `config.locale.value` цього Scene як єдине джерело всіх українських назв, підказок, пояснень та написів кнопок (окремі словникові ключі для майбутніх перекладів). Колекція `cards` — об'єкт із ключами, без масиву; відображення у фіксованому порядку: calculator, paperCalendar, simpleFlashlight, screenlessPlayer, windupCar, unknownLamp. `decision` — незмінний машинний ключ digital/notDigital/needMoreInformation, не напис для дитини. Жодних випадкових карток, балів чи результатів навички. Рухатися одним предметом за раз без таймера й балів. Для calculator і paperCalendar як керованих прикладів спочатку показати три локалізовані поля `input`, `process`, `output` з назвами з `phaseLabels`, потім запросити дитину назвати критерій і обрати одне з трьох рішень. Для simpleFlashlight, screenlessPlayer, windupCar і unknownLamp спочатку показати назву та два доступні описи `input` і `output`, попросити подумати й лише тоді обрати рішення; повне `process` за кнопкою «Подивитися, як працює» доступне без штрафу будь-коли (включно до вибору). Відсутність даних для unknownLamp — суттєва умова, не загадка за словом у назві. Відкрите `process` може допомогти навчанню, але правильний вибір сам по собі не є показником засвоєння. Після «Перевірити думку» розкрити `process` та відповідне пояснення, залишивши можливість повернутися до опису, спробувати ще або перейти далі. Коли предмет змінено, нова картка відкривається у початковому для її групи стані, попередні вибори не переносяться.

Для кожної картки показати нейтральну назву та доступну схематичну 2D піктограму. Спершу показати передбачені для групи факти `input`/`output` (для перших двох також `process`), потім за запитом або після перевірки розкрити відсутні факти й послідовність «отримує → що відбувається → результат» із ТЕКСТОВИМИ значеннями `input`, `process`, `output`. Видимі/доступні назви трьох фаз отримувати лише з перекладних `phaseLabels`. Для нецифрових випадків поле `process` описує фізичне явище, а не удавану цифрову обробку. Для unknownLamp опис прямо каже, що фактів бракує; не вигадувати прихованої будови. Це концептуальна модель: стрілки не показують справжні внутрішні електричні схеми. Іконки не повинні містити невіддільний текст, а текстовий список є рівноцінним змістом. Кнопки «Так, цифровий», «Ні, не цифровий», «Треба дізнатися» мають бути доступні у стані ознайомлення з фактами; не робити вибір залежним від миші, drag або проходження таймера. «Перевірити думку» активується після вибору; до нього можна змінювати відповідь. Критерій — `decision`. Правильний вибір показує текст `explanation` і загальне `goodReason` як запрошення до власного пояснення, не як mastery. Сам лише правильний вибір НЕ доводить, що дитина обґрунтувала його: не приписувати їй невисловлене міркування. Помилка: `tryAgain` + конкретне `hint`; відкрити `process`, залишити змогу змінити вибір або відкрити `explanation`, а також перейти до іншого предмета без осуду. Якщо пояснення відкрите після хибної відповіді, не вимагати повторювати вже показану правильну відповідь заради умовного «успіху». Для unknownLamp лише needMoreInformation є обґрунтованим, бо назва не розкриває внутрішньої роботи; показати `uncertain`. Кнопка «Почати знову» скидає локальний прогрес карток, не дані дитини. Ніяких сповіщень про перемогу, відсотків чи збереження оцінки.

## Педагогічні межі
Калькулятор обчислює 2+3=5; дитина не зобов'язана знати арифметику наперед — дорослий може озвучити. У паперовому календарі надруковані числа, але він нічого не опрацьовує; у простому ліхтарику батарейка живить коло, без цифрової обробки. Заводна машинка має механічний рух. Цифровий аудіоплеєр без екрана доводить, що екран не обов'язковий. Для лампи без характеристики потрібно уточнити функцію, не вгадувати за назвою чи зовнішністю. Не стверджувати, що всі ліхтарики/лампи або всі музичні пристрої належать до однієї категорії; оцінюється конкретно описана реалізація. Не малювати цифрові пристрої як тих, що «думають самі».

## Доступність і взаємодія
Один предмет за раз; великі touch-цілі, заголовок і зрозуміле ім'я кнопки, фокус/таб-порядок, Enter/Space, Escape лише за потреби; жодного drag-only, hover-only, color-only чи timeout. Вибрану відповідь озвучувати доступною семантикою radio/pressed, помилки й пояснення — ARIA live із ненав'язливим оголошенням та поверненням фокусу на відповідний контент. Текст картки повністю читається програмою екранного доступу; піктограма decorative якщо повністю дублюється назвою, інша — з унікальним alt. Усі стани (первинні факти, розкрите `process`, вибір, помилка, підказка, пояснення та перехід) мають однаковий зміст і доступний фокус/оголошення без зору/слуху, мови чи тонкої моторики; для дитини, що не читає, дорослий читає текст і дитина показує/торкається, для клавіатури і screen-reader — функціонально рівноцінний маршрут. Не розкривати правильну відповідь тільки в alt-підказці піктограми до вибору. RTL: логічний порядок інформації, читання тексту та правильна семантика стрілок, не просто дзеркало всієї сцени. Без автоанімації, яскравих спалахів, звукової залежності, таймерів; respect reduced motion. Стаціонарні SVG/HTML і plain text достатні.

## Офлайн і слабкі пристрої
Усі шість сюжетів, текстові підказки та правила вибору — локальні, без зовнішніх запитів, акаунта, камери, мікрофона, запису ідентифікаторів або аналітики дитини. Без WebGL, великого відео чи мережевих моделей. Стан лише локальний у компоненті. Підсумкові еквіваленти в сусідньому Markdown-блоці плюс повний сценарій для дорослого у цьому брифі: назвати/показати шість предметів у наведеному порядку, запитати «Що отримує? Що робить з інформацією? Який результат?», запропонувати три рішення, пояснити згідно з кожним `explanation`. Фізична версія з картками/предметами має ті самі шість випадків включно з невизначеною лампою; це педагогічний маршрут, а не твердження про вже реалізовану офлайн-поставку.

## Критерії приймання майбутньої реалізації
Кожна з 6 карток має незалежний вибір, повторну спробу, конкретну підказку і правильне змістовне пояснення; «не знаю без додаткових відомостей» визнається валідним лише для невизначеної лампи. На мобільному/клавіатурі/screen-reader усі сценарії рівноцінні; без GPU/аудіо/мережі немає втрати змісту. Переклади передають усі вкладені ключі; Arabic/Hebrew/Urdu проходять RTL-перевірку. У поточному UI Kit `Scene.tsx` незареєстрований UUID призводить до `Unregistered scene id` (помилка, а не автоматичний рендер цього Markdown-маршруту). Перед runtime-тестами окремий санкціонований Coding Agent мусить зареєструвати Scene та забезпечити контрольований fallback/еквівалентний безпечний шлях у разі недоступності, перевіривши, що інші ContentBlocks не губляться при збої. Окремо перевірити відтворення, повний keyboard/screen-reader/RTL/reduced-motion, упаковку, слабкі пристрої й offline runtime — це майбутні виробничі/QA завдання, не Stage 4 реалізація.
