# UI Kit agent instructions — cross-platform React runtime

**Scope:** `shared/ui-kit/**`. Read the repository-root [AGENTS.md](../../AGENTS.md), applicable Studio rules, and the [Cross-Platform Lesson Runtime](../../studio/docs/architecture/cross-platform-lesson-runtime.md) before modifying this package. This file adds package-specific constraints; it does not override repository-wide rules.

## Why the boundary exists

Svitlo intends to render **the same React DOM components** in a Next.js web host, a React/Capacitor mobile host (iOS and Android), and a React/Electron desktop host. Textbooks will supply authored configurations and build-bundled interactive Scenes; they are **not separate UI implementations per target**. These hosts are a **target architecture**, not a claim that the mobile/desktop clients already exist. The UI Kit must remain portable without rewriting components for each host.

## Required design rules

1. **React DOM, not framework-specific runtime.** Components may use React, DOM, CSS, supported UI peers and public `@svitlo/*` package APIs. Do **not** import `next/*`, Next.js route handlers, `@/...` aliases belonging to applications, `electron`, `@capacitor/*`, or source files under another package's private `src/`. Do not rely on Next.js-only asset or navigation components. Storybook's Next.js dev adapter is not a production runtime dependency.
2. **Inject host behavior.** Navigation, authentication, content fetching, routing, persistence, synchronization, native permissions, notifications and OS-specific APIs belong to host-side adapters. Expose small, typed, platform-neutral props/hooks/interfaces for capabilities a component actually needs. Never silently bind the UI Kit to an application's global singleton.
3. **Separate data, state, commands and services.** Lesson content arrives as a complete, serializable configuration (for example `LessonResponse`); interactive client state belongs to a session store owned by the host/lesson root. React Context can provide stable dependencies, read-only state views and an operations interface. Operations update the common store, **not independent provider states directly**. Keep state scoped per lesson session; avoid a single Context with high-frequency mutable values that re-renders every consumer.
4. **Respect Next.js server/client boundaries without depending on Next.js.** Hooks and interactive components may have a focused `'use client'` boundary. Do not pass functions or service instances from a Server Component into a Client Component: the host creates them client-side. Client Components can still be server-prerendered by Next.js; do not assume `'use client'` means browser-only execution.
5. **SSR/hydration safe.** Do not access `window`, `document`, `localStorage`, `indexedDB`, native bridges or DOM measurements at module load or during the initial render. Use effects, event handlers or explicitly guarded client-only adapters. Initial output must be deterministic between server prerender and hydration. Reserve stable space for images, deferred Scenes and loaders to avoid layout shift.
6. **No hidden runtime code loading.** Scenes are statically registered with analyzable imports **at build time**. React.lazy/code-split chunks are permitted, provided the target deployment packages or precaches required chunks for offline operation. Never implement arbitrary network JavaScript fetching or `eval` as a portability shortcut. Scene registries are textbook-owned, not duplicated in the UI Kit.
7. **Keep authoring data out of runtime.** Runtime UI accepts published, localized response/configuration contracts, not imports of authoring `*.data.ts`. Require only the selected locale at runtime when practical; localization is supplied by host/config or shared contract, not by an app-private locale provider.
8. **Accessibility and responsiveness everywhere.** Preserve semantic LTR/RTL, all required localizations, keyboard/touch/pointer use, screen-reader support, reduced motion, accessible fallbacks, and equivalent learning on small/weak devices. Do not depend on hover, viewport shape or a particular desktop browser.
9. **Keep security boundaries explicit.** UI props and client code are inspectable; UI Kit must not embed private content keys, licensed material, secrets, or entitlement decisions as trusted client-side authority. Host-side delivery/licensing are separate concerns.
10. **Use public exports and supported bundling.** Declare necessary peers, keep imports package-local or through public `@svitlo/*` exports, and ensure styles/assets can be bundled by different clients. Do not introduce Next.js-required build transforms into published runtime modules without a platform-neutral fallback.
11. **Shared static assets belong to UI Kit, deployment copies belong to each host.** Canonical SVG flags live in `shared/ui-kit/assets/flags/`; a host's build/development preparation copies them into its own public assets (`apps/web/public/flags/` for Web). Textbook packages do not seed or duplicate shared flags. The Web host's `prepare:assets` phase is independent of `SVITLO_TEXTBOOK`. Future mobile/desktop hosts should use the same packaged UI Kit assets through their own build pipelines, not assume access to a Web-only URL.

## Review and verification

- Explain which host capability a new dependency needs and how Web/Mobile/Desktop hosts can supply it.
- Check TypeScript, relevant unit/Storybook tests and packaging. For integration changes, verify a Next.js SSR/hydration path **and** an ordinary React DOM bundler/client path (Vite/Capacitor/Electron when harnesses exist); include mobile viewport, RTL/keyboard and offline asset/Scene checks where affected.
- Document any host-specific feature or missing test harness as an explicit limitation. Do not claim portability solely because a Next.js build passes, and do not claim proposed clients or offline licensing are already implemented.
