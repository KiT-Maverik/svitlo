# Course Stage 5 source orchestration — declarative target

**#857 target contract, not a claim of default-branch deployment.** The final independently reviewed, UUID-addressed `draft.ts` is one inert `export default { ... } satisfies CourseWorkflowStage3` literal. It does **not** import or call `materializeCourse()`, execute `build.overrides()`, value-import a Lesson Configurator or construct built `base/locale` values. The [canonical architecture](../../../../../studio/docs/architecture/typed-production-materialization.md) defines the shared Draft Reader; the [Course runbook](../../../../../scripts/ci/courseMaterialization/README.md) defines permission, pinned-source and transaction boundaries.

- A tokenless **trusted** analyzer statically parses exact reviewed source bytes without evaluating author code, checks the real final Course Stage 3 Zod schema, and calls real Engine Course source materializers using trusted code. The static reader is not a Lesson resolver, PR-readiness oracle or pedagogical reviewer.
- `materializeStage5.mjs` composes concrete Course, Module and Chapter renderers, builds deterministic child UUIDs and generates reproducible methodology from reviewed data. **Generated** `index.ts` files remain normal executable Configurator modules.
- New Lesson placements create only `CourseWorkflowLessonSeed` inert default-exported `draft.ts`, preserving source language, approved methodology and four independent bank/Section decisions. Course Stage 5 does **not** finish Lesson Stage 1, create a Lesson PR or generate Lessons/Question Banks/Scenes.
- Existing Lessons are identified in authored plans by `production.existing.id` and verified matching evidence; each Course-local adaptation carries a plain sparse `production.sourcePatch`, checked via a **type-only** imported existing Lesson export. Separately trusted materializer code verifies the real Lesson Configurator and invokes its actual `build.overrides()` with the placement-specific patch. Reused Lesson imports belong only in **generated** Course/Module/Chapter `index.ts`, never in authored draft.
- Course Stage 5 maintains exact `content.items/order` ownership at the Course, Module and Chapter levels. Each pending Lesson, Episode or Assessment placement owns an explicit `<placement>/stub.ts` exporting its typed `define*Stub` preview, with a canonical actionable `TODO (BLOCKER)` and exact UUID/slug. The immediate Course/Module/Chapter `index.ts` imports this stub into `content.items` without changing `content.order`; each child keeps its **independent** inert `draft.ts` handoff. Existing verified Lessons import completed Configurators directly, with no stub. Episode/Assessment trusted transactions verify the pinned stub and immediate parent AST read-only, then create only child source and delete only the reviewed `draft.ts`. The parent remains on the original stub for all three pending child kinds, each with an import-adjacent `TODO (BLOCKER)`. Only a Coding Agent may switch a validated, resource-ready child to its real Configurator import and delete that child's stub in a separate integration step.
- One Course-root `constants.ts` owns active source-language `languages` and `Languages` type. Generated child modules import these rather than creating their own tuples. Required locale restoration, physical media, Scenes, banks, independently produced child work and human QA remain explicit blockers.
- The tokenless analyzer seals the bounded `publishable:false` plan with hashes and immutable provenance. The privileged Git publisher reauthorizes actor, HEAD/blob, dependencies, paths and no-clobber, then commits new files and deletes the exact draft **once**, without importing authored code, regenerating or reformatting output.
- The old executable-draft isolated worker and direct `materializeCourse()` path remain historical implementation until Agent C's integration replaces them. Do not remove isolation prematurely or treat old passing direct-runner tests as evidence of static-reader deployment.
