# Runtime assembler architecture

**Status:** Skills runtime assembly is implemented in `skills/assembleSkills.ts`; Lesson Data assembly is implemented in `assembleLessonProps.ts`, and Course-context Lesson composition in `assembleCourseLesson.ts`. Other entity assemblers remain planned. The rules below are the cross-entity target contract. Follow the root `AGENTS.md`, applicable Studio guidance, and the authoring/publication contract in [`../configurators/AGENTS.md`](../configurators/AGENTS.md).

## Responsibility and dependency boundary

- Assemblers are lightweight, **pure runtime functions** that accept already-loaded published resource/override data and a selected locale, resolve the effective values, and return frontend-ready Data. Locale files are already Data-shaped (including nested `locale` fields), so assemblers **must not** recursively add or strip `locale` wrappers. They do **not** open files, call `fetch`, or know about authoring configurator instances.
- Hosts or host-supplied loaders handle filesystem, network, offline caches, authorization and file availability. The same assembly logic must work with data supplied by Next.js, Capacitor, or Electron.
- Validate final results using the **existing entity `*_Data_Schema`**, which is declared alongside that entity's Config Schema. Do not create a competing Data schema in the assembler.
- Prefer a **per-entity, strongly typed resolver API**: a resource argument with complete required base fields, a distinct optional override argument with sparse/partial base and locale fields, and an explicit selected language. A generic resolver/factory is not required when the concrete entity owns its types. Keep the four merge layers internal rather than accepting them as an unstructured variadic argument list. Type checking helps reject an incomplete override in a required resource slot, but structural TypeScript types alone **cannot guarantee merge precedence** (especially for two sparse locale layers); preserve the fixed sequence below and enforce it with regression tests.
- Runtime imports must avoid heavy `define*` factories, authored `*.data.ts`, generator code, Node-only APIs, and UI-framework dependencies. Existing exports may need later separation to enforce this; do not assume that boundary is already implemented.

## Resolution rules

- Resolve only the resource and override data associated with the requested publication context. Independently published overrides are not automatically layered on one another.
- Merge **named plain objects recursively by key** unless an owning field defines atomic replacement. Scalar values replace previous values. **Every published Data array override replaces the entire array** (for example, `applyStyle` or an already materialized child collection); never merge by index or concatenate. The canonical `children` array is a Data-layer ordering index; any published override replaces it atomically. Authoring-only `items/order` is never a runtime field. Direct placement `false` tombstones from sparse Data overrides must be removed before final validation.
- **Required precedence for one publication context and selected language:** `resource.base` → `resource.locale?.[language]` → `override?.base` → `override?.locale?.[language]`. Each later layer takes precedence over earlier layers; do not change the order to group base layers ahead of locale layers. The merge is pure and skips absent layers. Equivalently, resolve the resource base + chosen language first, then apply the override base + chosen language.
- Apply localized values for the requested language. A locale-specific patch changes the specified language without requiring its siblings. An explicit invariant string for a localized field replaces its dictionary: stale language-specific values from the original resource must not override that decision.
- **Regression case: deleted localized collection entry.** Suppose a published resource has a localized answer `A` and an invariant answer `B`: `resource.base.answer = [A, B]` and `resource.locale.uk.answer = [translatedA, B]`. A build-time configurator disables `A` and publishes `override.base.answer = [B]` with `override.locale === undefined`. For `uk` (and every other locale), the effective `answer` **must** be `[B]`. Because arrays replace atomically and `override.base` comes _after_ `resource.locale.uk`, no locale file needs to be generated for unchanged invariant `B`. Applying resource locale after override base would silently resurrect disabled `A` and violates this contract. The same precedence applies to reordered or newly added entries.
- Preserve the difference between an absent override field and an explicit supported value. Disabled-child markers and authoring-only collection metadata (`items`, `order`, `additional*`) must have been resolved by Configurator Build before publication: runtime Assemblers **must not filter disabled children, interpret `false` as a collection deletion, or sort collections**. A legitimate boolean `false` in published Data remains an ordinary field value. Do not invent deletion semantics for `null` or `undefined` without a field contract.
- Parent/child composition and invariants (such as a Checkpoint requiring an enabled question) are validated during Configurator Build. Runtime Assemblers validate the resolved Data with existing entity `*_Data_Schema`, without rerunning authoring-only collection validation.
- If a future use case genuinely requires multiple override layers for a **single resolved result**, explicitly specify their precedence and validation rules then. Do not introduce speculative multi-layer composition into the present publication contract.

## Implemented Course-context Lesson contract

- `assembleCourseLesson({ lesson, course, lessonId, courseId, language })` consumes four published layers and validates the resulting Lesson with `lesson_Data_Schema`. Both publication arguments contain `base` and optional locale-keyed JSON bodies. The standalone Lesson must be a Course member and support the requested language; the Course must support it too.
- Published Course/Module/Chapter Data uses one `children: string[]` index and direct slug-keyed child placements, without any `content.items/order` wrapper. Lesson entries carry `{ type: 'lesson', id, overrides? }` with **only sparse published Lesson overrides**, never a second full Lesson. The selected Course locale file carries sparse changes along the direct base-tree placement path, without duplicating sibling subtrees or identity fields. Published Data arrays _inside_ Lessons still replace atomically.
- Ambiguous Lesson ID matches without an explicit placement, Course/Lesson identity mismatches, forbidden Lesson override fields, unsafe JSON keys, and malformed final Data are errors. The assembler does not mutate inputs.
- `assembleCourseTree` validates a selected localized hierarchy once, rejects locale changes to immutable Course/Episode/Assessment language scopes, and indexes exhaustive `children` membership. `findCourseActivityByPlacement` requires that validated result and uses direct own-key lookup plus indexed membership in O(path depth); passing raw JSON directly is an error. `assembleCourseLesson` verifies the raw published hierarchy once per resource instance before caching its direct membership index. Treat returned Course Data and loaded publication objects as immutable snapshots; reassemble/reload after changing a hierarchy, rather than changing `children` in place. An explicit placement avoids all-Lesson ID scans; the no-placement ambiguity fallback remains a full traversal.
- The Next.js host helper `loadPublishedCourseLessonProps` reads Lessons from `public/data/lessons/<bucket>/<uuid>` and Courses from `public/data/courses/<uuid>`. It validates both IDs using the shared UUID resolver, and its roots are configurable. The current legacy `LessonResponse` / old Course patch loader remains untouched.
