# Materialize a reviewed Course plan (Stage 5)

This Engine utility consumes **one temporary Course YAML** under content/<book>/data/courses/<bucket>/<course-uuid>/course.yaml. It creates Course-owned TypeScript/Markdown drafts and any required Lesson methodology-only YAML handoffs. It never writes intermediate config.yaml and never opens Lesson PRs. The resulting Course TS/Markdown files are the durable source of truth.

## Usage

Run the maintained script shared/engine/scripts/materializeCourseFlow/materialize-course-flow.mjs with:

- --package content/<book> --course <uuid> --write
- --package content/<book> --course <uuid> --check

## Inputs and outputs

The single Course YAML has independently reviewed pedagogy, audience and Skills, Modules, Chapters, reuse references to existing Lessons, and full inline methodologies for new Lessons. Episode nodes, when authored, include independently specified Sections and content. Source language must belong to intended languages. Reviewer approval is tracked separately in the parent Course PR: this CLI cannot grant it.

Output files include the Course root `index.ts`, `constants.ts`, `methodology.md`, and `review.ts` (unapproved skeleton). All Course-owned Modules, Chapters, and Episodes live under a **single root `content/` directory** following their authored parent-child placement: `content/<moduleSlug>/index.ts`, `content/<moduleSlug>/<chapterSlug>/index.ts`, and `content/<moduleSlug>/<chapterSlug>/<episodeSlug>/index.ts`. A direct Course Chapter lives at `content/<chapterSlug>/index.ts`. There are no additional `content/` directories or type-grouped `modules/`, `chapters/`, or `episodes/` barrels. Each owned entity has a sibling `methodology.md`; the root Course methodology retains only Course-wide rationale and placement notes for directly referenced Lessons. A Module/Chapter methodology retains its own rationale, competency details and immediate Lesson placement decisions. No duplication of nested methodology in the root file.

Episodes use the Stage 5-owned `episode-draft-renderer.mjs` for typed Sections/blocks and resource placeholders. Course, Module and Chapter sources use `define*<Slug, Items, CourseLanguages>`; Episode sources use `defineEpisode<Slug, Languages, Sections>`. Source imports use the textbook's `#coursesData/*` package import alias for children and `constants.ts`, and `#lessonsData/*` for standalone Lessons. This keeps imports stable under deeper nesting and avoids upward parent imports. Module/Chapter/Episode slugs need only be unique within their own parent directory.

Whenever the materializer writes a new standalone Lesson YAML, it simultaneously returns a bounded in-memory assignment of its UUID, slug, source-language title and canonical file path. The trusted Stage 5 CI records these IDs, titles, slugs, canonical paths, original Course YAML blob SHA and the single resulting commit SHA in the **Actions summary**. It is a source-pinned handoff, not an editable PR-description registry or a second authored Course source. Lesson PRs start only through later separate authorization; no generator reads or updates PR-body Markdown.

For each new Lesson with inline methodology and no ID, Stage 5 derives a stable UUID from the Course UUID and canonical placement path. It creates only content/<book>/data/lessons/<last-hex>/<uuid>/lesson.yaml, with a minimal Config identity/Skills/language/title/empty-Sections shell and the reviewed source-language production.methodology text. Optional quizRequired on the slot supplies initial Quiz intent; absent values are provisional authoring shells, not independent approval. No Lesson TS, Questions, Flashcards, assets, translations, review or PR is created. Later Lesson Production reuses this exact ID and YAML.

Existing matched Lessons retain their actual IDs and source ownership. For a reused Lesson with explicitly authored inline `params`, `locale`, `events` or `section` fields, the Course materializer now collects the patch under its **Course placement key** and exports the typed, raw `authoredCourseOverrides` patch adjacent to the root Course configurator. The Course Props publisher loads that input and invokes `course.build.overrides(authoredCourseOverrides, { languages })` at its existing authoritative publication boundary. Exporting a computed Build output rather than the raw patch is incorrect; the publisher cannot accept that as an input. Existing Lesson sources and IDs remain unchanged; pure import/reuse emits **no** override resource. `title` and `objective` remain editorial placement text, not implicit Lesson mutations. `params.languages`, identity fields and Skill IDs may not be patched. **Course-local Section additions:** the Course-local `section.additionalItems` entries are complete, Engine-shaped Section Config objects, keyed by their `slug`, with genuine UUIDs and any required nested ContentBlocks. The materializer checks them against the existing Zod-generated Engine `section.schema.json`, then reuses the canonical `yamlFactoryByType` renderer to generate real `defineContentSection` / other Section and nested ContentBlock calls in the `course.build.overrides` expression. The `section.order` must be present when adding sections and must describe the final full Lesson Section order, including already-existing sections. This adds no separate authoring file and does not change the standalone Lesson. The Build API and full publication checks remain authoritative for patch applicability to the actual reused Lesson, including unknown/duplicate Section keys and language constraints.

Existing matched Lessons retain their actual IDs and source ownership. Source modules refer to standalone Lessons using the textbook's `package.json#imports` mapping `#lessonsData/*` (PR #595). For an implemented Lesson, retain its verified exported name; otherwise, use the canonical Lesson UUID and the `config.slug` from the existing `lesson.yaml` or newly materialized Lesson shell, targeting the **future** `index.ts` and its plain `slug` export (no `_Lesson` suffix). These imports intentionally remain unresolved until independent Lesson Production creates the modules. Do not use `UNRESOLVED_LESSON_N` or fabricate a Lesson configurator. The Course never owns or duplicates reusable Lesson implementations.

The generated `constants.ts` uses Engine's nonempty `SupportedLanguages` type and a `TODO (BLOCKER):` for the planned full language set. It follows the Lesson Builder convention: an active `languages` tuple containing **only `documentLanguage`**, `CourseLanguages = typeof languages`, and a commented-out alternative declaration retaining the complete planned `supportedLanguages` tuple. Root Course `params.languages` uses the active tuple. An editor can activate the complete tuple only after genuine translations are authored; neither this CLI nor a type error is permission to copy/fabricate translations. No separate `courseId` or `sourceLanguage` constant is necessary.

**A successful Course materialization is not required to pass TypeScript typechecking.** Unimplemented future Lesson imports, locale gaps and not-yet-authored Scene/media dependencies are valid Draft-only TypeScript errors. The CLI checks deterministic output bytes and **TypeScript syntax**, not complete typechecking or Props publication. This is intentional and should not be worked around with fake resources or `as any`. Before production acceptance, the actual textbook production build, external review evidence and full locale/resource coverage are required.

`review.ts` uses Engine's existing shared `Review` base type (`ai.locales`, `human.acceptance`, `human.locales`). Required numeric references start at `0` so the file is type-valid, but `0` is **not approval evidence**. Its top-of-file `TODO (BLOCKER): Conduct review` and the independent CI zero-evidence guard prevent Ready/merge until real review evidence exists. Engine has **no Course-specific `CourseReview` contract**; do not invent stages or approvals. Independent reviews remain in the parent PR until verified against the real Course revision.

## Safety and lifecycle

`--write` validates the source and **every planned output before modifying files**, rejects explicit YAML `params: null` and divergent/symlinked targets, creates files exclusively, internally verifies every result, then deletes **only the exact temporary `course.yaml`** on full success. The trusted Action publishes all source creations plus the YAML deletion in **one Git Data API tree and one commit** after verifying its SHA-pinned manifest. No second CLI invocation or finalization commit exists. `--check` remains an optional, independently invoked **read-only diagnostic**, never used by materialization CI. A rerun after successful deletion safely refuses to write without the original YAML rather than reallocate IDs or overwrite any output. Independent Lesson YAMLs remain for their own subsequent workflow. Git history preserves the approved Course YAML.

This is the only supported Course YAML authoring/materialization path. It never publishes Props, fabricates media/Quiz answers/translations, or starts Lesson Production.

Stage 5 Course roots live under `data/courses/<bucket>/<uuid>/index.ts`. The existing Course Props publisher discovers these alongside legacy root-level `*.data.ts` Courses. An incomplete, unmaterialized `course.yaml` is never executable source; a Course with no authored overrides is published by pure Lesson reference. Within a Course, a Lesson placement key can intentionally differ from the immutable standalone Lesson slug. Engine Build preserves the standalone identity and uses the placement key only in embedded Course Props; sparse patches are associated with their exact placement so the same Lesson may be reused contextually without copying its content.

For Episodes, the materializer validates the entire derived Episode Config against the current Zod-generated Engine Episode YAML Schema before writing any durable artifact. Nested YAML `params:` without a value parses as `null`, is never silently normalized to `{}`, and fails at its exact nested field path. Missing physical media still require the separate visible `TODO(asset)` draft handoff; this does not constitute completed publication or a real asset.
