# Engine scripts: mandatory agent handoff

These instructions apply to permanent scripts under `shared/engine/scripts/`. Read the repository root `AGENTS.md` and Studio rules/personas/skills first.

## Before changing ANY script

1. Open the target named workflow directory. Read its `README.md`, **the full leading JSDoc/fileoverview of the actual entrypoint**, relevant in-function JSDoc, and its adjacent `*.spec.mjs` / `*.test.*` tests **before proposing behavior changes**. Do not infer behavior from a directory or command name alone.
2. Inspect its npm-script callers, other generator/assembler consumers, and the owning Engine Config/Props schemas. Verify write destinations and overwrite safety against the implementation. Read any referenced Studio architecture/entity documents and the actual current Build API.
3. Distinguish **observed implementation**, **explicit intended contract**, **historical editorial workflows**, and **proposed changes**. When they differ, report the difference. Do not reinterpret a documented non-goal as missing functionality.
4. Keep each permanent script in a named directory with nearby tests. Never move build-only imports into `@svitlo/engine/runtime`. For temporary one-off transformations use the owning package's ignored `temp/` instead.

## Legacy converter scope during typed-production migration

The YAML-centric instructions below are the **observed existing scripts' contracts**, not the canonical starting format for **new** Course/Lesson/Questions/Flashcards work. New staged editorial sources and Stage 1 handoffs are owned by #775/#782/#783/#784. Lesson-owned YAML Builder/Finalizer and CI commands were retired in #797; remaining YAML consumers and shared schemas belong to independent Course/Question/Flashcard cutover work. Never feed incomplete editorial `index.ts` files directly to Props publication or use a publisher as a source materializer. Existing Scene/specification, Section draft and no-clobber requirements stay mandatory for legacy PRs.

Parent #775 continues to coordinate independent Course/Bank transitions. ## Independent assessment resource publication

The new `generateAssessmentResources/` command compiles already-authored typed Question/Flashcard banks into separate generated resources and metadata manifests. It does not consume or generate `questions.yaml` or `flashcards.yaml`; those are approved editorial sources requiring separate conversion. The named `flashcardBuilder/` now supports a narrowly scoped create-only typed TS scaffold for reviewed, Engine-shaped source-language Flashcard YAML (Text/Markdown/Code and incomplete Audio/Image/Video/Subtitles placeholders). It is NOT an assessment publisher, media resolver, Question-reference resolver, translator or approval system. Every generated media draft contains a visible `TODO(asset)`, plus
a CI-visible `TODO (BLOCKER):`, and must be completed using verified existing physical files at the pinned Lesson SHA before TypeScript validation/publication. Its output is staged by textbook tooling, **not** inserted into Lesson Build Props. The typed Lesson materializer rejects missing/disabled required assessment Sections and preserves incomplete resource blockers; independent Question/Flashcard production remains separate. Do not invent bank data or erase pending source references. Independent bank flows complete those sources. Do not silently rewrite or migrate the user-edited #557 prototype.

## Single-source authoring boundaries

- **Lesson source:** one progressively reviewed `index.ts satisfies LessonWorkflowStage1/2` object. Trusted typed Stage 6.1 materializes its exact reviewed Stage 2 bytes to the final `defineLesson` tree. Legacy Lesson YAML tools are retired; publication still requires separate readiness verification.
- **Course source (new typed workflow):** [Create Course Flow](../../../studio/skills/course-workflow/create-course-flow.skill.md) owns Stages 1–3 in one `CourseWorkflowStage1/2/3` TypeScript object and an independent corrective Stage 4. `production.languages` owns planned languages. **Legacy path still present:** `validateCourseFlow` and `materializeCourseFlow` consume a `course.yaml` governed by the old Course schema; do not feed them TS or remove them before typed Stage 5 and the trusted CI replacement are tested and integrated. No second editable Course YAML or Config/TOC workflow should be started.
- **Course Episode renderer:** `materializeCourseFlow/episode-draft-renderer.mjs` handles nested authorized Sections, Quests, Scenes and visible `TODO(asset)` media placeholders. No completed asset/translation or playable Quest is implied. Its output is an internal Stage 5 source-draft representation, not a second authored Course.
- **Course overrides:** the only supported mechanism is the stateless `course.build.overrides(patch, { languages })` API in durable typed authored Course code, using current slug-keyed Configurator patches. No separate `overrides.yaml`, second Config input or operations language.
- **Lesson media:** the typed Lesson materializer preserves real authored specifications and emits explicit `TODO(asset)` and `TODO (BLOCKER):` where assets are incomplete; authors provide genuine assets in subsequent specialized work. Scene React implementation is completed and verified in Lesson Stage 6.3 after generated source correction in 6.2; translations (Stages 9/10) and unrelated external imports remain separate dependencies, never reasons to fabricate resources.
- **Modular Lesson handoffs:** put verified `specification.md` beside the nested Configurator source module. Authored standalone Scene code stays in the registered textbook Scenes directory. Neither builder may invent physical binary assets or overwrite edited specifications.

## Lesson ownership and file safety

- A standalone Lesson is an independently authored, reusable entity. A Course `type: lesson` child is a **reference via `lessonId`**, never an embedded `defineLesson` declaration.
- In the **legacy Course YAML materializer**, `source.path` and `source.export` are **optional import coordinates**, not an existence flag, approval status or instruction to create a Lesson. Missing/unusable coordinates produce an explicit unresolved Lesson handoff. New Lesson UUIDs and minimal YAML handoffs are deterministically assigned during reviewed Course Stage 5; opening a Lesson PR remains a separate owner-authorized Lesson workflow.
- The trusted typed Lesson Stage 6.1 transition only changes a verified canonical UUID Lesson tree and archives its exact reviewed `index.ts` source. Existing destinations, symlinks, stale SHAs and partial trees fail closed. The independent legacy Course Stage 5 materializer still has separate handoff contracts pending parent #775 cleanup. Course references or overrides must not edit Lesson directories without explicit authorization and independent verification.
- Course-owned overrides must not mutate standalone Lesson authoring files. **The only supported override mechanism is the stateless `build.overrides(patch, { languages })` API and its typed, slug-keyed patch shape.** Do not consume, generate, preserve as a supported alternate format, or auto-translate the former Studio operation-based `overrides.yaml` DSL; it is obsolete. Do not resurrect `createLessonOverrides` or emit `_OverrideEditorial`. Reject obsolete input explicitly rather than silently treating it as a valid patch.
- `production.languages.document` is source-language provenance for the typed Lesson and Course workflow; it is not proof of translation readiness. The **legacy** Course `course.yaml` declares `documentLanguage` and `supportedLanguages`. In the **new typed** Course Stages 1–3, language planning belongs only in `production.languages.document/planned`; there is no early `config.params.languages`. When final Config is materialized, do not fabricate locale coverage or rewrite intended languages to hide missing translations.
- Draft outputs may be incomplete or fail TypeScript checks **by design**, especially unfinished media/Scene work. Pending assessment Sections are a specific exception: their generated Config is structurally valid with reserved UUID-shaped references, but never production-ready. A successful scaffolder run is neither editorial approval nor proof of verified bank resources.

## Intentionally failing TypeScript is the expected draft handoff

- **Unfinished media/Scene drafts may still fail TypeScript until their dependencies are resolved.** During typed Lesson materialization, incomplete authored Quiz/Flashcards Sections remain explicit non-publishable blockers, and the Lesson retains its approved `quizRequiredForCompletion` value. Do not modify this value to fabricate validity. Other generated source modules remain draft handoffs. Required Config structure includes reserved Nil UUID media placeholders with adjacent TODO(asset) and a real `TODO (BLOCKER):` per unresolved media Configurator, not assigned asset identities. Missing Scene implementations/imports, additional locales and unresolved references are work for the next AI agent, not scaffolder bugs.
- The scaffolder's job is to emit a deterministic, syntactically well-formed, recognizable `define*` source draft and preserve its unresolved work. **Assessment exception:** unfinished Quiz/Flashcards Sections stay in build-facing Lesson modules in their approved order with valid Config parameters, temporary reserved references, and real root/Section/field `TODO (BLOCKER):` markers. Original approved authoring and bank references must be preserved in the independently owned bank source. Production/Ready cannot accept these placeholders. The Lesson's authored `quizRequiredForCompletion` remains unchanged; only the independent bank flow may complete and integrate those Sections. **Review registers:** generated Lesson/Course `review.ts` files must parse and typecheck with named declarations and numeric `0` evidence placeholders. Lesson stage languages use the true source language for type shape only. The top-of-file `TODO (BLOCKER): Conduct review` and Ready/merge CI zero-evidence guard block unfinished reviews even if the TODO is removed prematurely. Verified PR/revision evidence remains a separate specialist responsibility. All generated modules must parse. **Successful TypeScript compilation, Engine Config validation or Props generation alone are explicitly NOT evidence of publication approval for a draft scaffolder.** Regression tests may verify these operations on provisional assessment Sections; actual publication and reviewed resource ownership/locale completeness remain separate strict gates. The scaffolder run itself should succeed for otherwise supported incomplete draft inputs; it must not execute or gate on TypeScript checks.
- **Do not "fix" draft TypeScript diagnostics inside a scaffolder** by inventing `src`, `fileLocation`, import targets, Scene components, other language strings, default educational content, or values that pretend a pending resource exists. Do not silence errors with `as any`, `@ts-ignore`, weakened Config types, or fictitious passing fixtures. For Lesson drafts, preserve explicit `TODO(asset)` and release blockers until the specialist supplies real media. The current Course Stage 5 materializer retains outstanding dependency diagnostics for the finishing agent.
- Preserve the distinction between **expected type errors** and **generator defects**. YAML syntax/dispatch failures, incorrectly emitted TypeScript syntax, lost authored data, wrong file placement, unintended overwrites, and incorrect factory selection remain defects. If a completely authored input happens to produce valid TypeScript, do not inject artificial errors merely to make it fail; the deliberate failure applies to incomplete drafts, not every possible input.
- A later specialist agent completes media/Scene assets, translations and Config fields, then uses TypeScript diagnostics to verify and finish its own work. The separate publication pipeline runs only after those dependencies are actually resolved.

## Change verification

For modifications involving these workflows, update adjacent tests for their actual contract and check both positive and negative cases: nested factory selection, missing references, source-language filtering, deterministic output, immutable identity and no unintended writes. Separately run relevant schema-generation checks when changing `configurators/yaml` or the editor JSON Schema generator. Never claim a command passed unless it was executed.
