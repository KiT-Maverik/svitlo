# Engine scripts: mandatory agent handoff

These instructions apply to permanent scripts under `shared/engine/scripts/`. Read the repository root `AGENTS.md` and Studio rules/personas/skills first.

## Before changing ANY script

1. Open the target named workflow directory. Read its `README.md`, **the full leading JSDoc/fileoverview of the actual entrypoint**, relevant in-function JSDoc, and its adjacent `*.spec.mjs` / `*.test.*` tests **before proposing behavior changes**. Do not infer behavior from a directory or command name alone.
2. Inspect its npm-script callers, other generator/assembler consumers, and the owning Engine Config/Props schemas. Verify write destinations and overwrite safety against the implementation. Read any referenced Studio architecture/entity documents and the actual current Build API.
3. Distinguish **observed implementation**, **explicit intended contract**, **historical editorial workflows**, and **proposed changes**. When they differ, report the difference. Do not reinterpret a documented non-goal as missing functionality.
4. Keep each permanent script in a named directory with nearby tests. Never move build-only imports into `@svitlo/engine/runtime`. For temporary one-off transformations use the owning package's ignored `temp/` instead.

## Independent assessment resource publication

The new `generateAssessmentResources/` command compiles already-authored typed Question/Flashcard banks into separate generated resources and metadata manifests. It does not consume or generate `questions.yaml` or `flashcards.yaml`; those are approved editorial sources requiring separate conversion. The named `flashcardBuilder/` now supports a narrowly scoped create-only typed TS scaffold for reviewed, Engine-shaped source-language Flashcard YAML (Text/Markdown/Code and incomplete Audio/Image/Video/Subtitles placeholders). It is NOT an assessment publisher, media resolver, Question-reference resolver, translator or approval system. Every generated media draft contains a visible `TODO(asset)`, plus
a CI-visible `TODO (BLOCKER):`, and must be completed using verified existing physical files at the pinned Lesson SHA before TypeScript validation/publication. Its output is staged by textbook tooling, **not** inserted into Lesson Build Props. The Lesson Builder now consumes `lesson.yaml` exclusively. For explicitly incomplete assessment Sections it creates source-only `sectionDrafts` inside separate Questions/Flashcards YAML drafts, never independently authored assessment bank TypeScript; previously existing YAML is never overwritten. Both editorial bank YAML files are siblings at the Lesson UUID root. Stage 6 can create a **one-time empty bank YAML handoff** containing `sectionDrafts` from deferred Quiz/Flashcards Sections, but it does not author Questions or Flashcards, overwrite existing bank YAML, or publish banks. Independent bank flows complete those sources. Do not silently rewrite or migrate the user-edited #557 prototype.

## Single-source authoring boundaries

- **Lesson source:** one `lesson.yaml` with the Engine Config under `config` and authoring-only `production` specifications at the root and nested nodes. Its stable IDs are in Config. Zod-generated Lesson Config schemas and manual Production schemas guide the draft editor; scaffolding does not approve/validate the full editorial Lesson.
- **Course source:** one temporary **`course.yaml`** matching `studio/skills/course-workflow/course-flow.schema.json`. The [seven-stage Course Flow](../../../studio/skills/course-workflow/create-course-flow.skill.md) owns authoring, approval and independent review. The `validateCourseFlow` CLI runs read-only stage checks; `materializeCourseFlow` directly emits Course TypeScript/Markdown and initial independent Lesson YAMLs from that exact reviewed source. No generic Config-shaped Course Builder, optional second editor YAML or old TOC conversion exists.
- **Course Episode renderer:** `materializeCourseFlow/episode-draft-renderer.mjs` handles nested authorized Sections, Quests, Scenes and visible `TODO(asset)` media placeholders. No completed asset/translation or playable Quest is implied. Its output is an internal Stage 5 source-draft representation, not a second authored Course.
- **Course overrides:** the only supported mechanism is the stateless `course.build.overrides(patch, { languages })` API in durable typed authored Course code, using current slug-keyed Configurator patches. No separate `overrides.yaml`, second Config input or operations language.
- **Lesson media:** technical Lesson YAML intentionally omits `fileName` and `posterFileName`. The Lesson Builder inserts reserved Nil UUID placeholders with adjacent `TODO(asset)` and `TODO (BLOCKER):` markers; authors provide genuine assets in subsequent specialized work. Scene implementation, translations and imports remain separate dependencies, not reasons to fabricate resources.
- **Modular Lesson handoffs:** put verified `specification.md` beside the nested Configurator source module. Authored standalone Scene code stays in the registered textbook Scenes directory. Neither builder may invent physical binary assets or overwrite edited specifications.

## Lesson ownership and file safety

- A standalone Lesson is an independently authored, reusable entity. A Course `type: lesson` child is a **reference via `lessonId`**, never an embedded `defineLesson` declaration.
- In Course YAML, `source.path` and `source.export` are **optional import coordinates**, not an existence flag, approval status or instruction to create a Lesson. Missing/unusable coordinates produce an explicit unresolved Lesson handoff. New Lesson UUIDs and minimal YAML handoffs are deterministically assigned during reviewed Course Stage 5; opening a Lesson PR remains a separate owner-authorized Lesson workflow.
- The Lesson Builder writes TypeScript in its selected Lesson UUID directory plus explicitly documented Markdown/specification and one-time bank YAML handoffs. The Course Stage 5 materializer writes only its specified Course source files and deterministic new Lesson `lesson.yaml` handoffs after owner authorization; authorized `specification.md` handoffs are written to paths derived from nested `config.id`. **Creation is non-destructive:** if any `*.data.ts` already exists inside that entity's UUID directory, `generate`/`--write` must log `SKIP` and leave every file unchanged. For the modular Lesson Builder, a root `index.ts` is also an authored Lesson entrypoint that requires the same `SKIP`; pre-existing separately generated `questions/` or `flashcards/` directories must not block a Lesson-only draft; for a new Lesson, a partial Lesson-owned `sections/` tree without `index.ts` must trigger an explicit no-mixing diagnostic. Known canonical source directories skip before parsing YAML; staged file inputs derive the UUID from `config.id` before applying the exact same no-overwrite rule. No update of generated files is implicit. Separate `check`/`--check` remains read-only and strict about stale output. Do not treat editorial YAML files as existing entity data. A task about Course references or overrides **must not add writes to Lesson directories** without a separate, explicit architectural decision and safety tests.
- Course-owned overrides must not mutate standalone Lesson authoring files. **The only supported override mechanism is the stateless `build.overrides(patch, { languages })` API and its typed, slug-keyed patch shape.** Do not consume, generate, preserve as a supported alternate format, or auto-translate the former Studio operation-based `overrides.yaml` DSL; it is obsolete. Do not resurrect `createLessonOverrides` or emit `_OverrideEditorial`. Reject obsolete input explicitly rather than silently treating it as a valid patch.
- `production.documentLanguage` is source-language provenance for the technical YAML (required for Lessons, optional for Courses); it never enters `defineLesson` / `defineCourse`. The current Course `course.yaml` declares `documentLanguage` and `supportedLanguages` explicitly. `params.languages` expresses intended supported locales and must not be rewritten to match available translations.
- Draft outputs may be incomplete or fail TypeScript checks **by design**. A successful scaffolder run is neither editorial approval nor validation of an Engine Config.

## Intentionally failing TypeScript is the expected draft handoff

- **Unfinished media/Scene/review drafts may still fail TypeScript until their dependencies are resolved.** During Lesson materialization, unfinished Quiz/Flashcards Section Configurators are not emitted: their original source is preserved in bank YAML `sectionDrafts`, while the Lesson retains its exact `quizRequiredForCompletion` value and a merge-blocking root TODO. Do not modify this value to fabricate validity. Other generated source modules remain draft handoffs. Required Config structure includes reserved Nil UUID media placeholders with adjacent TODO(asset) and a real `TODO (BLOCKER):` per unresolved media Configurator, not assigned asset identities. Missing Scene implementations/imports, additional locales and unresolved references are work for the next AI agent, not scaffolder bugs.
- The scaffolder's job is to emit a deterministic, syntactically well-formed, recognizable `define*` source draft and preserve its unresolved work. **Assessment exception:** unfinished Quiz/Flashcards Sections are excluded from build-facing Lesson modules and preserved completely in temporary bank-owned `questions.yaml`/`flashcards.yaml` `sectionDrafts`, with real root `TODO (BLOCKER):` markers. The Lesson's authored `quizRequiredForCompletion` remains unchanged; only the independent bank flow may complete and integrate those Sections. **Explicit exception:** the Lesson `review.ts` draft is intentionally syntactically invalid until its assembled Props hash becomes the const identifier and verified review PR/language values are supplied; all other generated source modules must parse. **Successful TypeScript compilation, Engine Config validation, Props generation, and publication are explicitly NOT acceptance conditions for a draft scaffolder.** The scaffolder run itself should succeed for otherwise supported incomplete draft inputs; it must not execute or gate on TypeScript checks.
- **Do not "fix" draft TypeScript diagnostics inside a scaffolder** by inventing `src`, `fileLocation`, import targets, Scene components, other language strings, default educational content, or values that pretend a pending resource exists. Do not silence errors with `as any`, `@ts-ignore`, weakened Config types, or fictitious passing fixtures. For Lesson drafts, preserve the automatically inserted Nil UUID filenames and adjacent `TODO(asset)` markers until the specialist supplies real media; technical Lesson YAML omits these media fields entirely. The current Course Stage 5 materializer retains outstanding dependency diagnostics for the finishing agent.
- Preserve the distinction between **expected type errors** and **generator defects**. YAML syntax/dispatch failures, incorrectly emitted TypeScript syntax, lost authored data, wrong file placement, unintended overwrites, and incorrect factory selection remain defects. If a completely authored input happens to produce valid TypeScript, do not inject artificial errors merely to make it fail; the deliberate failure applies to incomplete drafts, not every possible input.
- A later specialist agent completes media/Scene assets, translations and Config fields, then uses TypeScript diagnostics to verify and finish its own work. The separate publication pipeline runs only after those dependencies are actually resolved.

## Change verification

For modifications involving these workflows, update adjacent tests for their actual contract and check both positive and negative cases: nested factory selection, missing references, source-language filtering, deterministic output, immutable identity and no unintended writes. Separately run relevant schema-generation checks when changing `configurators/yaml` or the editor JSON Schema generator. Never claim a command passed unless it was executed.
