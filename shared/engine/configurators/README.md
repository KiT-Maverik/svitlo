# Engine entity configurators

`configurators/` contains the `define*` authoring configurators and their Zod-backed schemas. Additional Course creators are located in `configurators_old/`.

**ContentBlock Build API:** The nine flat ContentBlock configurators, `CheckpointItem`, and `Checkpoint` expose `build.props()` for complete resources and `build.overrides(patch)` for validated sparse changes. A Checkpoint composes an ordered collection of CheckpointItems; each item has a Text question and ordered answer blocks. Follow [the configurator rules](./AGENTS.md); [generators](../generators/AGENTS.md) serialize publication results, and [runtime assemblers](../assemblers/AGENTS.md) resolve published fragments into Props.

Private helper directories follow `_shared__<owningDirectory>` (for example `_shared__configurators` or `_shared__contentBlocks`) and are imported **only inside their owning directory**. Shared contracts needed by other groups belong in public `*.constants.ts`, `*.types.ts` or `*.schemas.ts` files, exported through the group's `index.ts`. Public indexes must not re-export a private helper directory.

The new Skill, SkillGroup, SkillDomain and AssessmentMethod factories intentionally use a minimal shape:

- `config.base` — non-localized fields such as `id`, `slug` and methodological description.
- `config.locales()` — localized fields such as names, titles and frontend descriptions.
- SkillGroup and SkillDomain configurators expose child configurators as slug-keyed `skill` and `group` maps.
- `*_Config_Schema` and `*_Props_Schema` validate the two representations.

ContentBlock configurators share top-level identity (`id`, `slug`, `type`), nested `params` and `locale`, and Zod-backed `*_Config_Schema` / `*_Props_Schema`. `build.props()` publishes complete `{ base, locale }` resources, and `build.overrides(patch)` publishes sparse fragments in exactly the same Props-shaped language format. For example, Text publishes `locale.uk = { locale: { value: 'Привіт' } }`: the inner `locale` is the ContentBlock Props field, while `uk` identifies the published language file. Invariant values stay in `base`. Flat ContentBlocks also expose `config.base` and `config.locales()` for authored configuration access. Their Build methods are stateless and do not mutate the original configuration or other publication contexts.

Every `define*` directory has an `index.ts` that exports its implementation and schemas; parent barrels export each directory once. Configurators expose `id` and `type` directly, plus `slug` where the authored entity has one. Validation and `config.*` accessors are specific to each entity; the presence of `config.base` does not imply a mutable override API. All flat ContentBlocks also expose top-level `validate` and `build` methods.

`configuratorArrayToSlugMap([defineText(...), ...])` converts a list of configurators into a slug-keyed object, preserving literal slug types. It is useful for AI-authored content because authors need not duplicate slugs as object keys.

Checkpoint authoring uses `content: { items, order }`: `items` is a slug-keyed map of `defineCheckpointItem` configurators, and `order` lists every active slug exactly once. Each CheckpointItem owns a mandatory Text question and an ordered `answer: { items, order }` collection of ContentBlocks except Checkpoint. `build.props()` publishes a complete, sorted `content` Props array. `build.overrides(patch)` accepts sparse `params`/`locale` changes and `content: { items, additionalItems, order }`; `items` patches existing items (or sets them to `false`), while `additionalItems` supplies new configurators. Adding or disabling items requires an explicit full `order` array. Validation rejects unknown, duplicated, disabled, or missing slugs, duplicate additions, incompatible children, identity changes, and an empty effective collection. Build output contains only sorted Props arrays, never configurators, `items` maps, or authoring-only `order` lists. Each Build call is stateless and leaves the authored configurators untouched.

Text ContentBlocks keep visible localized fragment values inline as `%_%id: personName; value: Maria%_%`. Optional `params.variables` is a camelCase-keyed map of styling rules, e.g. `{ personName: { applyStyle: ['variable', 'bold'] } }`; its keys are checked against every supplied text locale. No array entries or repeated `id` fields are needed, and the UI Kit selects each rule by key. Unlike Code, Text does not substitute values from a separate localized variables object.

Code ContentBlocks are **static, display-only source text**. `params.codeAsText` always contains the complete source string, not a file reference. An authored definition can read its neighboring source file via `readFileSync(new URL('./example.py', import.meta.url), 'utf8')`; Node throws if the file does not exist. The configurable `config.validate(config)` checks `%_%UPPER_SNAKE_CASE%_%` markers against the keys of `locale.variables`, a map from variable names to invariant or per-language strings, directly from `params.codeAsText`. The published Code response carries `codeAsText`, and the UI Kit presents it as highlighted, non-executable text while preserving whitespace. No Node file loader is needed inside Engine.

Lesson and all six current Section configurators follow the ContentBlock authoring lifecycle: top-level identity, `params` and `locale`, metadata-only `*_Config_Schema`/`*_Props_Schema`, `config.base`, `config.locales()`, `config.overrides`, `config.validate`, `override`, and `disable`. **Each Section owns its schemas and lifecycle directly**; no Section schema/configurator factory exists. Deliberate duplication is preferable to hiding per-section behavior behind shared factories. Lesson owns a `section: { items, order }` collection of Section configurators; every Section (including Quiz) owns `content: { items, order }` of ContentBlock configurators. Section validation checks only its metadata, collection keys, allowed child kinds and ordering; nested ContentBlocks validate themselves. `override.content.add/disable/order` keeps sparse patches without changing authored content. `false` disables a child only inside an override, never authored content. Lesson's independent collection helper remains unchanged.

The optional Lesson `programId` marks course-owned, non-reusable Lessons; universal Lessons omit it. Quiz `params.screen` references named Section content items by slug, rather than embedding ContentBlock configurators.

Course, Module and Chapter now use their own explicit ContentBlock-style lifecycle, without a shared creator or schema factory: top-level `id / slug / type`, `params`, `locale`, `config.base / locales() / overrides / validate`, `override.params`, `override.locale` and `disable`. Course owns `params.languages`, optional `scenarioMode` and prerequisite IDs; its `locale` owns title, Markdown description and optional prerequisites text. Module and Chapter own localized title and optional `params.iconKey`. Course content may contain Modules, Chapters or Lessons; Modules may contain Chapters or Lessons; Chapters may contain Lessons. Each uses `content: { items, order }` keyed by child slug. Episode and the obsolete Scenario Section linkage are removed. Validators check metadata and ordered child boundaries, not child internals. Authoring code can mutate `content` directly, then call `config.validate()`; no collection mutation helpers or generic Course factory are introduced.

Publication consumers still need deliberate migration: configurator `build` methods prepare Props-shaped publication data; build-time generators serialize completed results without invoking configurators, while runtime assemblers resolve published fragments into final Props. Neither layer is implemented by the new guidance alone. Never serialize configurator functions or import build-time configurators into runtime bundles.
