# Direct Lesson Stage 6.1 technical boundary

This document supplements the [current direct Lesson runbook](./README.md). The one supported PR command is `/lesson materialize`, executed through a trusted default-branch workflow. Successful Draft CI does not establish workflow deployment.

The authorized same-repository Draft Lesson PR must contain exactly one canonical UUID-addressed Lesson `draft.ts` in its pinned base/HEAD comparison. Its final accepted object must satisfy `LessonWorkflowStage2` and invoke `materializeLessonStage6(reviewedLesson)` once through `@svitlo/engine/build`.

The trusted resolver checks actor privileges, source path, HEAD and exact Git blob. The read-only analyzer installs/builds only trusted Engine code. It runs the exact authored TypeScript entrypoint once inside the shared `scripts/ci/directMaterialization/` Docker worker, with non-root identity, read-only filesystem, no network, no GitHub credentials and bounded time/resources. The Engine's Zod Stage 2 contract and concrete Lesson/Section/ContentBlock source materializers validate and produce the actual plan. No AST literal parser, TypeScript semantic rechecking of generated source, or separate authored JSON is part of the current execution path.

The worker returns a nonpublishable source plan. Trusted analysis checks canonical filenames, hashes, file byte limits, UUID ownership and create-only targets; a SHA256-attested artifact contains the exact generated bytes plus the original `draft.ts` deletion. The write-token publisher **never loads candidate code or reruns any materializer**. It checks actor and HEAD again, source blob, file hashes, branch lease and no-clobber before creating one non-force Git commit. Original reviewed source remains reachable in Git history.

Materialization is not a publication certificate. Stage 6.2/6.3 resources, Scenes, Questions, Flashcards, translations, TODO blockers and runtime acceptance are separate. Old YAML-based builders are retired, but historical authored YAML files remain untouched pending explicit migration.

Validation (do not claim results without executing):

```sh
npm run package:build --workspace @svitlo/engine
npm run code:check:types --workspace @svitlo/engine
node --test scripts/ci/lessonMaterialization/lesson-typed-materialization.spec.mjs
node --test scripts/ci/lessonMaterialization/lesson-typed-publish.spec.mjs
node --test scripts/ci/directMaterialization/run-isolated.spec.mjs
```

Operational validation additionally requires an owner-authorized synthetic source PR, real deployed default-branch workflow, verified pinned SHA and commit, and negative checks for stale or unauthorized sources.
